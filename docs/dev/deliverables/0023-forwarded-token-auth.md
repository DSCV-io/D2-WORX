# Deliverable 0023 — Forwarded-token auth plumbing (dev-first) + service-identity retirement

**Status:** SHIPPED 2026-06-20 — converged + governed. **Branch:** `n/forwarded-token-auth` (off `n/typespec-emitters`; base `6c126321`). **Predecessors:** 0021-auth-pivot (the decision records) + 0022-mtls-workload-identity (the mTLS workload-identity half + the forwarded-token *shape* pinned). This deliverable IMPLEMENTS the forwarded-token *plumbing* half of ADR-0022 (mint-once-at-Edge, forward unchanged) and RETIRES the already-built code that still implemented the superseded re-mint-per-hop (`client_credentials` service-identity) model.

## Goal

Build and UNIT-TEST the reusable, dev-first plumbing that lets a .NET service **forward the Edge-minted internal transaction-token (an RS256 JWT) byte-for-byte unchanged** on cross-process gRPC calls — captured inbound without ever being logged, re-attached outbound per request — and reconcile the code + docs that still implemented the OLD re-mint-per-hop model. This is the **mirror of 0022**: 0022 built the reusable mTLS workload-identity plumbing and PINNED the forwarded-token shape; 0023 builds the reusable **forwarded-token plumbing** (inbound raw-credential capture → a never-logged wrapper → outbound per-request `CallCredentials` attach → the emitter auto-wire) and RETIRES the dead `client_credentials` service-identity surface that ADR-0022/0023 made obsolete.

**End state shipped:** the reusable forwarded-JWT plumbing exists, is adversarially tested, and composes orthogonally with the 0022 mTLS rail — proven in isolation (unit + an in-memory exact-bytes-on-the-wire assertion + a real-`TestServer` gRPC-inbound e2e), exactly as 0022 proved the mTLS plumbing without an Edge host. The two orthogonal rails per hop: (1) `Authorization: Bearer` = the forwarded user token (re-validated each hop); (2) mTLS client cert = workload identity (0022, established per connection, NOT forwarded); (3) `x-d2-context` = operational enrichment + call-path. The forwarded token REPLACES the old per-service `client_credentials` identity; that workload-identity role is now mTLS's. **Genuinely deferred (tracked):** wiring the plumbing into a running Edge gRPC host (Edge `api/` is `.gitkeep` — no host exists). The Edge boundary mint itself (`POST /oauth/token`) is Phase-3.

## Cross-cutting decisions

- **Structural isolation is the load-bearing invariant.** The forwarded JWT lives in a dedicated request-scoped holder, never on `IRequestContext`. Two-pronged proof: (a) a different DI registration / different type than the context; (b) a structural test asserting the ~42-field enrichment LOG-OK projection + the `IRequestContext` spec contain no forwarded-JWT field. This is what keeps the never-logged guarantee from depending on every future enricher edit being careful.
- **Reveal-once seam.** `.RevealForForwarding()` is the single reveal point; its only production caller is `ForwardedJwtCallCredentials`. A live-tree source-scan test (non-vacuously guarded, test files excluded) pins exactly one allowed caller.
- **Per-request vs per-channel.** The whole design hinges on `CallCredentials.FromInterceptor` resolving ambient request-scoped state at call time (not capturing at channel build). Every outbound test exercises the two-requests-one-channel case (`T-CONC`).
- **The ambient seam is a framework-free port.** `IAmbientRequestScopeAccessor` lives in `DcsvIo.D2.Auth.Abstractions` (no AspNetCore framework reference); the `IHttpContextAccessor`-backed adapters (`HttpContextAmbientRequestScopeAccessor`, `GrpcHttpContextAmbientRequestScopeAccessor`) live in the transport libs that already reference the framework. This kept the outbound lib framework-free and avoided forcing an `auth/http → auth/outbound` edge.
- **Additive-not-replace mirror of 0022.** Forwarded token (user identity) ⊥ mTLS (workload identity) — orthogonal rails that compose on a channel; neither rescues the other (JWT on `options.Credentials`, mTLS on the handler `SslOptions`). A test wires both and asserts neither is clobbered.
- **Codegen + generated-file discipline.** Emitter fix + regen, never hand-edit `.g.cs`; the emitter emits the OOTB-extension chain into the generated DI registration (real chained method calls, never a string-literal of the method path); the telemetry spec is the source of truth for the removed tags. The shared-registry regen (telemetry tags) was verified by the full-solution test run (§26.13).

## Kinds-of-misses log (evidence behind the candidate rules)

- **M1 — A captured live credential entered request-scoped state asymmetrically across transports (FINAL-REVIEW M-1).** The HTTP middleware captured the raw bearer into the forwarded-JWT holder BEFORE the session-liveness gate; the gRPC interceptor captured AFTER all gates. The capture comment listed only harmless / bearer-missing / validation-failure — not liveness — so the stated "captured after validation success" guarantee diverged from the gRPC posture and from the ADR text, on a security-surface path, untested. The targeted per-step S2 audit verified each transport's capture-after-validation in isolation but did not cross-check transport-to-transport symmetry against the full inbound gate sequence (liveness included). → candidate rule: a captured live credential enters request-scoped state ONLY after ALL inbound auth gates pass (incl. session-liveness), and that ordering is SYMMETRIC across transports + pinned by a holder-state test per gate per transport.
- **M2 — A net-new live-credential wrapper needs its full leak-surface proven as a matrix, not a single redaction test.** The `ForwardedJwt` never-logged guarantee is only as strong as the four-layer proof: ToString-redacts AND field-set-exclusion AND log-capture-across-a-real-cycle AND the no-`[LoggerMessage]`-param scan AND the sole-reveal-caller scan. R1's leak-path-exhaustion table enumerated 18 distinct leak vectors (ToString / `{@x}` destructure / `{x}` plain / public property / implicit-conversion / IFormattable / ISerializable / System.Text.Json / Newtonsoft / `[LoggerMessage]` param / enricher projection / unexpected reveal caller / reveal-result re-log / channel-build capture / cross-request bleed / forged-token capture / revoked-token capture). A wrapper that redacted `ToString()` but leaked via any one of the others would defeat L3. → candidate rule: a live forwarded credential in request state is a redacting value type proven by a leak-surface matrix (the enumerated vectors), not a single redaction assertion.
- **M3 — A DI seam registered by an extension was resolution-tested only cross-module (FINAL-REVIEW M-2).** The `IAmbientRequestScopeAccessor` adapter was `GetRequiredService`-resolved in a cross-module composed-host test but not in `AddD2AuthHttp`'s OWN extension test — descriptor-presence-adjacent for that extension specifically. → candidate rule (§1.3 sharpening): a DI seam an extension registers is `GetRequiredService`-resolved in THAT extension's own test, not only a cross-module integration test.
- **M4 — A shared abstraction's home is the lowest common layer both consumers already reference.** The `IAmbientRequestScopeAccessor` port was first locked into `auth/outbound`; the Implementer relocated it to `auth/abstractions` (the framework-free leaf both the outbound credential AND the transport adapters already reference) and the Auditor ratified it — this killed a would-be `auth/http → auth/outbound` edge and kept the outbound lib framework-free. → candidate rule (§9): a shared port/abstraction lives in the LOWEST common layer both consumers already reference, to avoid forcing a new cross-package edge.
- **M5 — Security-critical cross-cutting every generated client needs is AUTO-WIRED, never a forgettable docstring (S4).** The emitter had been emitting a "host MUST chain `.AddD2ServiceIdentity()`" guidance docstring — a forgettable footgun pointed at a (now dead) surface. The fix was not a docstring swap but auto-emitting `.AddD2ForwardedJwt().AddD2WorkloadCertificate()` into the generated DI registration so the safe path is the only path. → candidate rule (§26): security-critical cross-cutting that EVERY generated client needs is AUTO-EMITTED into the generated DI registration (fail-safe), never left as a "host MUST chain X" docstring; the host's residual surface is limited to config the generator cannot invent.
