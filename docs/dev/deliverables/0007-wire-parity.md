# Deliverable 0007 — Cross-language wire parity

**Branch**: `n/wire-parity` (off `nova` @ `32b71ffb`; previously `n/problem-details-spec`)

**Per user direction**: ONE deliverable, multiple steps OK, single commit after manual review

## Context

Started life as `0007-problem-details-spec` (narrow §11.30 cleanup of 3 ProblemDetails extension keys). Mid-execution a full parity audit (`01-problem-details/full-parity-matrix.md`) surfaced 5 active drift problems beyond ProblemDetails — including a 🚨 CRITICAL type lie on `D2Result.messages` (.NET emits `IReadOnlyList<TKMessage>` objects; TS declares `string[]`). User direction: address them ALL in one deliverable because "they're all structures we use for communication that are highly coupled and SHOULD be contract driven and parity tested across BOTH TS and C#".

**Mental model**: D²-WORX has multiple wire formats (HTTP ProblemDetails + D2Result envelope Shape B + gRPC trailers + AMQP envelope). Every identifier (field name, key string, URI prefix, fallback value) that crosses .NET ↔ TS should be cataloged in `contracts/`, codegen-emitted on both sides, and parity-tested with byte-equal pins. Hand-mirrored constants are §11.30 violations regardless of which wire format they belong to.

## Scope

**IN — wire formats covered**:

1. HTTP ProblemDetails (RFC 7807) — standard fields + extension keys (Step 1)
2. ErrorCodes catalog — D2Result internal error code enum (Step 2)
3. TKMessage + InputError shapes — wire-format types for messages + field-level validation errors (Step 3)
4. D2Result envelope Shape B — BFF gateway response shape (Step 4; depends on Steps 2+3)
5. gRPC trailers + AMQP envelope — cross-service async wire identifiers (Step 5)

**OUT — explicit non-goals**:

- `ProblemDetailsBody` RFC 7807 shape (external IETF standard, KEEP hand-written)
- TS-only programmer-error constants `REDIRECT_INVALID_TARGET` / `REQUIRE_SCOPE_NO_ARGS` (TS-only; not cross-language)
- Per-tenant custom error code mapping (out of v2 Phase 0 scope)

- **Flaky tests in `D2.Shared.Tests.Integration.ServiceDefaults`** (LOW; surfaced 2026-05-16 during Step 1 Auditor R2; closed-for-Step-1 as PRE-EXISTING by Fixer R2). Two tests can fail under certain full-suite parallel-execution orderings with the diagnostic `System.InvalidOperationException : No service for type 'OpenTelemetry.Metrics.MeterProvider' has been registered.` at `WebApplicationTelemetryExtensions.MapD2PrometheusEndpoint:66`:
  - `AspNetCoreMiddlewareE2ETests.Cors_FromConfiguredOrigin_Get_AllowOriginInResponse`
  - `LoggingPipelineE2ETests.RequestLogging_OptionsBound_ServiceNameFromOTelEnvVar`

  **Evidence of pre-existing status**: Step 1 (`n/wire-parity` working tree vs `nova @ 32b71ffb`) touches neither `server/shared/dotnet/telemetry/` (where `MapD2PrometheusEndpoint` lives) nor `server/shared/dotnet/service-defaults/` (the aggregator) nor `server/shared/dotnet/tests/Integration/ServiceDefaults/` (the failing tests + their fixtures). The `aspnetcore` csproj's new ProjectReferences (`result`, `problem-details-abstractions`, `headers-http`) cannot cause MeterProvider to be unregistered — they only add downstream deps consumed by the new ProblemDetails customizer + CORS allowed-headers default. Subsequent Fixer R2 verification runs confirm intermittent reproduction: both tests pass when run as scoped test classes (19/19 + 14/14) AND in a full `dotnet test server/shared/dotnet/tests/D2.Shared.Tests.csproj` run (3189/3189) post-Fix-1; Auditor R2 captured a transient failure during their concurrent verification run.

  **Reproduction**: rare; appears to require concurrent ServiceDefaults TestHost instantiation across xUnit test collections competing for OpenTelemetry static-state initialization. The pattern is consistent with a known class of OpenTelemetry test-isolation issues where `MeterProvider` is briefly unregistered between disposal of one TestHost and registration in the next.

  **Recommended follow-up** (separate deliverable): investigate xUnit test-collection serialization for ServiceDefaults TestHost-based tests (likely `[Collection("ServiceDefaultsTestHostState")]` analogous to existing `[Collection("LogLoggerStaticState")]` pattern), OR force-serialize tests that touch the OpenTelemetry SDK via `xunit.runner.json`. Not blocking deliverable 0007 because the failures don't reproduce when each affected test class is run in isolation AND the full suite passes reliably in a single sequential invocation. Step 1 source changes neither introduce nor exacerbate the underlying race.
