## 1. Test Discipline
<a name="top"></a>
_[← rules index](../rules.md) · §1 of the D2-WORX rules catalog._

**Predicate index:** §1.1–§1.33 · 33 predicates.

The #1 cost driver of multi-pass audits is "thin glue" code (DI extensions, gRPC plumbing, factory wrappers, source-generator emitters) shipped without tests. Every public path needs at least one test on the FIRST pass.

### Predicates — §1 test discipline

- **1.1** Does every `public` method introduced in this scope have ≥1 test?
  - Evidence: `<method qualified-name> -> <test file:line>` for each, or "no public methods in scope."
  - **Why**: untested "thin glue" hides bugs until a later audit pass (e.g. a `GrpcClientBuilderExtensions` unused `<TClient>` generic; an OIDC `ConfigurationManager` 2-arg ctor silently using the static default `HttpClient` instead of `IHttpClientFactory`).
  - **How**: "hard to test in isolation" is a smell, not an excuse — use a compile-time test (existence proves the call shape compiles), a DI smoke test, or a runtime registration assert.

- **1.2** Does every public method / API surface / input parameter have EXHAUSTIVE adversarial coverage across EVERY applicable category below — NOT merely "≥1 adversarial test" (that's lazy and defeats the purpose of non-happy-path tests)? If you can think of an untested scenario that can be written into a test and has not been done yet, **WRITE IT**. "Too many tests" is never the failure mode; "production broke as soon as someone deviated from happy path" is.
  - **Mandatory adversarial categories** (write tests for EVERY category that applies to the surface — Implementer enumerates which apply in the Plan; Auditor flags absent applicable categories as FINDING-HIGH):
    1. **Input validation**: null / empty (`""`, empty collection, default-initialized struct) / whitespace-only / over-max-length / under-min-length / special characters / unicode edge cases (combining marks, surrogate pairs, RTL, zero-width chars, normalization forms NFC/NFD) / wrong type (where dynamic typing / JSON deserialization allows) / malformed format violations (regex / parse / schema) / boundary values (`int.MinValue`, `int.MaxValue`, min/max ± 1, `0`, `-1`, `Guid.Empty`).
    2. **Cross-field dependencies**: field A requires field B (test omitting B) / field A's value constrains field B's allowed values (test invalid combinations) / mutually exclusive fields (test both set) / conditional-required (field B required iff field A has specific value).
    3. **State / lifecycle**: calling method twice (idempotency where claimed; OR assert observable behavior either way when not claimed) / calling method in wrong order (e.g. `Close` before `Open`) / calling method on disposed / closed / completed object / calling method after an error state was returned (does the object remain usable or does it stay in error?).
    4. **Concurrency** (where the surface is reachable from multiple threads / requests): multiple concurrent readers / reader during writer / concurrent writers / cancellation token canceled mid-operation / timeout during operation / lost-update race.
    5. **Resource exhaustion** (where the surface allocates / opens resources): out-of-memory simulation (over-large input that would OOM if unbounded) / disk full (where applicable) / network failure (DNS / TCP / TLS) / external-dependency failure (DB down, RMQ down, Redis down, OIDC discovery slow / unreachable) / connection pool exhaustion.
    6. **Error propagation**: inner exception preserved (where appropriate) / error code surfaced correctly per `D2Result` semantics / partial-success state correctly reported (`SOME_FOUND` vs `NOT_FOUND` vs `OK`) / sanitized rendering used (no PII via `ex.Message`).
    7. **Domain-specific adversarial** (per the surface's domain — Plan enumerates):
       - Temporal: per §25.12 categories (IANA / DST / leap / cross-language parity / determinism / TestClock).
       - Auth / tokens: malformed JWT (missing segment / wrong algorithm / `none` algorithm) / expired token / not-yet-valid (`nbf` in future) / signature mismatch / wrong audience / wrong issuer / replayed token / oversized claim payload / unicode in claims.
       - Cache: TTL boundary (exactly-expired, expired-by-1ms, never-expires sentinel) / eviction race / serialization failure (corrupt cached blob) / key collision / Redis backplane down (degraded local-only mode).
       - Geo / location: lat/lng out of range (`> 90`, `< -90`, `> 180`, `< -180`) / antimeridian crossing / pole degeneracy / invalid postal code / invalid ISO 3166-1/2 code / mixed-case identifier normalization.
       - Messaging: oversized payload / corrupt envelope / replayed message / out-of-order delivery / DLQ routing on poison message / consumer-isolation (one bad message doesn't kill the consumer).
       - I/O / file: zero-byte file / corrupt file / wrong MIME type / oversized file / filename with traversal sequences (`..`, `/`, `\`, NUL, control chars) / symlink / file-system permission denied.
    8. **Security-adversarial** (where the surface is reachable from untrusted input): SQL-injection-shaped strings / path-traversal sequences / template-injection / log-injection (CRLF in user input) / unicode normalization attacks / IDOR (request with another user's ID).
  - **NOT every method needs every category** — only the categories that apply to that surface. But the Implementer MUST enumerate WHICH apply (and WHY the others are N/A) in the Plan section. The Auditor MUST cross-walk the test file against the enumeration — any applicable category with ZERO covering tests is a FINDING-HIGH (not "polish", not "borderline", not "follow-up").
  - **Evidence**: per public surface introduced or modified → an adversarial-coverage matrix in the Plan / Implementer journal entry listing (a) which categories apply, (b) per applicable category, the test name(s) covering it. The big-table row cites the matrix file:line + the test file. Missing applicable category = FINDING-HIGH (HIGH→CRITICAL if the missing category corresponds to a reachable production failure mode like PII leak / IDOR / unbounded resource consumption).
  - **Why**: happy-path-only tests pin behavior under good input, not the garbage production actually delivers. The prior "≥1 adversarial input" form was satisfied by a single `null` test — the lazy interpretation that shipped the 0009 Step 1 temporal-test gap. **"Better to have a shit ton of tests than code that breaks as soon as someone doesn't happy path input."**
  - **How**: at PLAN time, enumerate applicable categories per surface in the Plan "Adversarial coverage matrix" (surface × category × test name); Implementer writes one test per scenario with a behavior-descriptive name (§1.8); Auditor reads the matrix → opens the test file → confirms every applicable category has a covering test (one test = one scenario, not one test claiming several). Missing category → FINDING-HIGH; a category the Plan omitted but the Auditor finds applicable → FINDING-HIGH against §1.22 (Plan gap) AND §1.2 (test gap).
  - **Cross-refs**: §25.12 (canonical domain-specific application — temporal); §1.7 (factory wrappers) / §1.18 (per-VALUE pin) — complementary surfaces; §1.22 (Plan enumeration) / §1.23 (Auditor mandate) operationalize enforcement.

- **1.3** Are all DI extension methods (`Add*`, `Use*`, `Configure*`) tested via composition resolution (build a `ServiceProvider`, resolve the registered service, assert shape)? Does the composition test `GetRequiredService<>()` EVERY seam the extension registers — not a representative sample?
  - **Why every seam**: descriptor-presence in the `ServiceCollection` is NOT resolvability — a handler registered with a missing dependency compiles clean and appears in `services`, but throws at runtime when resolved. A test that resolves 3 of 8 handlers leaves 5 unverified and ships latent `InvalidOperationException`s. The only evidence a seam is resolvable is a successful `GetRequiredService<IXxxHandler>()`.
  - **Required**: the test iterates (or explicitly calls) `GetRequiredService<>()` for EVERY publicly-injectable seam the extension registers (`I<Op>Handler`, keyed resolvers, options-configured services), each seam listed individually. Missing a seam = FINDING-HIGH.
  - Evidence: `<extension method> → <test file:line>` resolving EVERY registered seam, each listed individually. A test that resolves only a sample = FINDING-HIGH.

- **1.4** Are all gRPC client/server registration helpers tested (call shape compiles + dispatches)?
  - Evidence: `<helper> -> <test that calls through it>`.

- **1.5** Are all source-generator emitters covered by snapshot tests (input spec → expected source, AST-equivalent)?
  - Evidence: emitter → snapshot test file.

- **1.6** Do reflection-based tests pin every `[LoggerMessage]` partial-method signature against accepting `Exception` (since `ex.Message` leaks broker URIs / user input)?
  - Evidence: `<partial method> -> <reflection test asserting param list>`.
  - **Pattern**: canonical form lives at `Telemetry/LoggerMessageDelegateContractTests.cs`.

- **1.7** Are all factory wrappers (`From*` / `Create*` / smart-constructor static methods on records / classes) tested EXHAUSTIVELY per §1.2's applicable adversarial categories — NOT merely "happy + one degenerate"? Factories are the validation gate for domain types; an under-tested factory is the silent-bug surface that lets malformed data through to handlers / repos / wire.
  - Evidence: per factory → adversarial-coverage matrix row (per §1.2 evidence requirement) showing which categories apply + which tests cover each. Single-category "degenerate input" coverage = FINDING-HIGH (insufficient per §1.2 strengthened form).
  - **Why**: factories are domain boundaries. A `Country.Create(string iso2)` that only tests `"US"` and `null` lets through `"us"` (case), `" US "` (whitespace), `"USA"` (length), `"u​s"` (zero-width) — each a wire-format bug that surfaces on real-world malformed input.

- **1.8** Do test method names use **behavior-descriptive** names? No `F2_`, `AuditN_`, `PhaseN_`, `Audit{Letter}_`, `R5_`, `H4_`, `M2_`, `L3_`, `O1_`, `S2_`, `Q1_`, combo labels like `F3F4L5_`.
  - Evidence: `grep -rEn 'public[[:space:]]+(async[[:space:]]+)?(void|Task|ValueTask)[[:space:]]+(Audit[0-9]+_|Audit[A-Z]_|Phase[0-9]+_|[HMFLORSQ][0-9]+_|F[0-9]+F[0-9]+L[0-9]+_)' <test files>` returns empty.
  - **Why**: future readers care what behavior a test pins, not which audit pass added it.

- **1.9** Are test files named after the FEATURE they cover, not the audit round? Forbidden: `Phase*Tests.cs`, `*Audit*Tests.cs`, `*Sweep*Tests.cs`, `*Round[0-9]*Tests.cs`, `AuditFixesRegressionTests.cs`, `SecondAuditFixesRegressionTests.cs`.
  - Evidence: `git ls-files` against the forbidden glob set returns empty.

- **1.10** Does the test project's `<ProjectReference>` graph include every new lib introduced in this scope?
  - Evidence: list new libs → `<ProjectReference>` line in test csproj.

- **1.11** Do integration tests exist for behaviors that genuinely need them (race conditions, broker behavior, DB constraint behavior, end-to-end gRPC dispatch, Redis pub/sub backplane, multi-instance coordination)? Unit tests against mocks aren't enough for those.
  - Evidence: per integration-needing behavior → integration test file.

- **1.12** Do tests cover graceful degradation under outages (DB unavailable, broker unreachable, cache miss + downstream timeout, JWKS endpoint slow, OIDC discovery failure)?
  - Evidence: per graceful-degradation behavior → test.

- **1.13** Are private helpers made `internal` (with `[InternalsVisibleTo]`) when needed for direct unit testing rather than fragile end-to-end tests?
  - Evidence: per `internal` promotion → corresponding test + `InternalsVisibleTo` attribute.

- **1.14** Test-scope `Random.Shared` discipline (no `new Random()` in test code). Covered by §4.7's repo-wide scope — walk §4.7 against `tests/` as the canonical predicate.

- **1.15** Are test fixtures (counter listeners, HTTP message handlers, time providers) one-type-per-file under `Fixtures/`?
  - Evidence: per fixture type → dedicated file.

- **1.16** Do test fixtures that touch the file system, env vars, or network use ISOLATED paths (TempDir, explicit non-existent file names, mocked env, sandboxed network)? Tests MUST NEVER load real-environment data into the test process.
  - Evidence: per file-system / env-var / network-touching fixture → isolation mechanism.
  - **Why**: a test calling `.env`-discovery with default file names walks up to the repo root and silently loads `.env.secrets` into the test process — real secrets in test memory, cross-test contamination, log-grep exposure. Same class: tests resolving `IConfiguration` from a real file, hitting a real localhost port, or reading `Environment.GetEnvironmentVariable` without a fixture-scoped override.
  - **Pattern**: pass an explicit non-existent file name (discovery short-circuits) OR scope to a `TempDir` fixture OR mock the env-var accessor.
  - **Critical security gap class.**

- **1.17** Tests with names of the form "X bypasses Y" / "X overrides Y" / "X wins over Y" must construct the scenario such that BOTH X and Y would individually trigger — proving the precedence, not just observing one outcome.
  - Evidence: per "bypasses" / "overrides" / "wins" test → setup confirms both predicates would fire individually.
  - **Why**: a test named `OceFromCt_BypassesTransientClassifier` run against a classifier that wouldn't classify `OperationCanceledException` as transient anyway passes WITHOUT exercising the bypass — it pins the classifier, not the catch filter. Invert the classifier (`IsTransient: _ => true`) so the test PROVES the catch filter is what bails out.

- **1.18** Do tests pin per-public-VALUE for every constant / enum value / static-class member (not just per-class smoke)? `nameof(X)`-captured constants need explicit wire-value `Should().Be("X")` pinning so a refactor that replaces `nameof(X)` with a literal can't silently change the wire value.
  - Evidence: per public constant / enum value → dedicated pin test (e.g. `[Theory] [InlineData(...)]` matrix or per-value `[Fact]`).
  - **Why**: a per-class smoke test asserting "the constants exist and aren't empty" passes after `CLIENT_ID` → `clientid` because nothing pins the wire value. The wire format (consumed by clients, audit-log queries, alerting) is the contract; a `nameof(X)` → literal replacement would silently change it without breaking the build.

- **1.19** For libs whose runtime composition / wire-up has its own failure modes that pure unit tests cannot surface (logging pipelines, telemetry SDK setup, middleware pipelines, message-bus subscribers, hosted services with cross-component handshake), are per-step integration tests with mocked inputs MANDATORY (not optional)?
  - **Convention**: harness lives at `public/packages/dotnet/tests/Integration/<lib>/Infrastructure/`; per-feature cases at `public/packages/dotnet/tests/Integration/<lib>/<Feature>Tests.cs`.
  - **Preferred**: in-memory capture (in-memory Serilog sink, in-memory OTel exporter, TestServer-hosted middleware) over external fakes (Testcontainers, real broker). External fakes belong to the broader integration bucket (§1.11), not per-step composition coverage.
  - **Negative-regression tests pin design decisions** that cross-cut runtime composition (e.g. "RemoteIp NEVER appears in the rendered log line", "the OTel resource always carries the `d2.*` attribute set", "the locked middleware order is preserved end-to-end").
  - Evidence: per wire-up-risk lib added or modified → integration test file path + test count covering the wire-up surface; per cross-cutting design decision → corresponding negative-regression test.
  - **Why**: unit tests against mocks pin the API surface, not the lib's composition runtime behavior. Cite: a logging-enricher expansion caught Serilog 9.x's `AddPropertyIfAbsent` silently dropping `IDiagnosticContext.Set` calls for HTTP `RequestId` / `RequestPath` after Serilog pre-bound them — a last-writer-wins assumption pure unit tests would have rubber-stamped.
  - **How**: the Plan section includes a "Runtime composition test plan" listing the wire-up surfaces to pin + the negative-regression assertions guarding the design decisions; the same step ships them. Distinct from §1.11 (real-broker / real-DB orchestration); §1.19 covers in-memory wire-up tests that must exist before any external-resource tests are considered.

- **1.20** For test infrastructure code (parity gates, contract tests, cross-language consistency assertions, security-critical assertions), does the Implementer prove fail-path DURING execution, not at audit? At minimum: introduce 3 deliberate-drift cases against shipped tests; verify each FAILS with a useful error message naming the drifted field/value; revert + verify clean. Document each in the journal as `negative-validation: <test name> failed when <drift introduced> with message '<excerpt>'; reverted; passed clean.`
  - **Why**: a test that always passes provides false confidence; the hazard applies to any test that ASSERTS a contract — a security gate that always grants, a comparator that always reports equal, a check that compares a value to itself. (0006: a tautological `PropagatedContext` parity test round-tripped a fixture into itself, caught only because deliberate-drift discipline was mandatory.)
  - **How**: the Plan enumerates the deliberate-drift cases (3+ spanning field-add / field-remove / value-change; 1+ cross-spec negative). The Implementer captures literal stderr excerpts in the journal, one per drift, before reverting. The Auditor verifies the entries exist + reads the test source to confirm it is non-tautological (not merely trusting the journal).
  - **When**: applies to test infrastructure that ASSERTS contracts (parity, cross-spec consistency, comparators, security gates, codegen-output validators). Standard single-language unit tests are §1.1 / §1.2 territory.
  - Evidence: per parity / contract / consistency test file → ≥3 negative-validation entries in the same Implementer round, each citing the drift + the literal stderr excerpt.

- **1.21** For every wire-serialized spec-driven record (any record carrying `[JsonPropertyName]` — or the TS-side equivalent — for wire-protocol field naming), does the scope ship a `Serialize_WireKeysSubsetOfCatalog`-equivalent **catalog-pin structural guard test** that: (a) serializes a fully-populated instance to JSON, (b) extracts the wire-key set, (c) asserts every wire-key is a member of the spec-emitted `FieldNames` catalog?
  - **Evidence**: per wire-serialized record introduced or modified → catalog-pin guard test file:line. Test asserts BOTH directions — every emitted key is in the catalog AND every catalog entry is reachable through some serialization path (prevents dead catalog entries).
  - **Why**: a wire-serialized record is a contract — every public property either carries `[JsonPropertyName(catalog.X)]` (cataloged wire key) or `[JsonIgnore]` (off the wire); the guard mechanically enforces "no third option". Without it a new public property ships with default JSON behavior — its name appears on the wire — with no compile error until production observability or a cross-language consumer surfaces the drift. (0007 Step 4: 17 `D2Result.Booleans.Is*` helpers + `Failed` leaked; the fix landed subset-of-catalog guards; final-review found `DlqFailureMetadata` lacked the same guard.)
  - **How**: ship a `Serialize_WireKeysSubsetOfCatalog` test (or rename-equivalent) ALONGSIDE the record — construct a fully-populated instance, serialize via the production `JsonSerializerOptions`, parse to a key set, assert subset-of-catalog. Pair with a `Serialize_DoesNotLeakX` test enumerating the specific derived-helper / debug-property names that MUST stay off the wire (§1.18 per-VALUE pin). A NEW catalog entry also gets a §1.18 per-VALUE pin test.
  - **When**: every cross-language wire-serialized record (HTTP / gRPC trailers / AMQP envelope / persisted JSON blob crossing code boundaries). Distinct from §1.18 (per-VALUE pin for individual constants) — §1.21 is per-RECORD structural pin for the property set.

- **1.22** Does the Plan section for any step introducing new public methods / API surfaces / input parameters include an **Adversarial coverage matrix** that enumerates (a) every public surface introduced, (b) per surface, which §1.2 categories apply (with one-sentence justification for any category marked N/A), (c) per applicable category, the specific test name(s) to be written?
  - **Evidence**: Plan section contains a table with columns `Surface | Category | Applicable? | Test name | Rationale if N/A`. Audit row cites the Plan file:line. Plan without a matrix for a scope introducing public surfaces = FINDING-HIGH (the matrix is the cheapest moment to catch missing coverage — before code is written).
  - **Why**: without a category enumeration the audit has nothing to walk against — the 0009 Step 1 temporal-test gap ran 4 audit rounds against a Plan listing only "≥1 test" + happy-path names. The matrix moves the catch to Plan-Audit Cluster A (§24.16) — orders of magnitude cheaper.
  - **How**: at PLAN time the Planner walks the §1.2 category list per surface, marks each Applicable / N/A, and assigns a behavior-descriptive test name (§1.8) per Applicable. Domain-specific categories (temporal / auth / cache / geo / messaging / I/O / security) require explicit domain-relevant scenarios — generic "category applies" without specifics = FINDING-MEDIUM. Plan-Auditor (Cluster A): missing matrix = FINDING-HIGH; matrix with gaps = FINDING-HIGH per gap.
  - **Cross-refs**: §1.2 (the category catalog); §1.23 (Auditor cross-walk); §24.16 (Plan-Audit cluster check); §25.12 (temporal application).

- **1.23** Does the per-step Auditor (and the final-review Auditor) cross-walk the test file(s) for each public surface against the §1.22 matrix AND against the §1.2 category catalog independently — flagging EVERY applicable category that lacks a covering test as FINDING-HIGH (severity HIGH minimum; CRITICAL if the missing category corresponds to a reachable production failure mode)?
  - **Evidence**: per public surface → the audit row cites (a) the matrix file:line, (b) the test file:line per applicable category, (c) per missing category, the findings-log entry with severity + suggested test name + production failure mode. Auditor MUST NOT mark §1.2 PASS from "the matrix says all covered" alone — MUST open the test file and verify the test exists AND exercises the scenario meaningfully (not a stub / mislabeled happy-path).
  - **Why**: the anti-pattern this prevents — "audit walked §1.2 and rubber-stamped because at least one adversarial test existed" — produced the 0009 Step 1 R1–R4 gap. §1.2 requires CATEGORY coverage, not "≥1"; the Auditor's bar must match or the predicate is non-functional. **No "polish" / "borderline" / "follow-up" / "deferred" — missing applicable category = FINDING-HIGH, fixed the same round, OR explicit user deferral per §13.4 / §13.14.**
  - **How**: Auditor opens the matrix → the test file(s) → for each applicable category, finds the named test and confirms it exercises the scenario. Auditor independently re-walks §1.2 against the surface — N/A-marked categories get re-validated against the domain. Missing category from the matrix that the Auditor finds applicable = FINDING-HIGH against §1.22 AND §1.2 (same finding under both per §24.13.3a).
  - **Cross-refs**: §1.2 (categories), §1.22 (matrix), §24.0 (3-artifact journal), §24.16 (Plan-Audit), §25.12 (temporal application).

- **1.24** Do test files that resolve the repo root / `public/contracts/` / `private/contracts/` / any shared fixture directory use a SENTINEL-BASED root finder (walk up until a marker like `.git` / a repo-root sentinel is found) rather than a hardcoded `..`-count walk-up (`Path.Combine(dir, "..", "..", "..")`, `path.join(here, "..", "..")`, a `[CallerFilePath]`-relative fixed-depth climb)? A fixed `..`-count breaks SILENTLY when the test file moves depth — the climb lands wrong, the fixture load throws ENOENT / FileNotFoundException, and if the suite isn't in the default run the failure stays LATENT.
  - **Scope**: every test (xUnit `.cs`, Vitest / Jest `.ts`, equivalents) that resolves a path OUTSIDE its own directory (a shared fixture from `public/contracts/` or `private/contracts/`, a spec file, the repo root for cross-language parity). Tests referencing only files within their own directory tree are out of scope.
  - **Required**: a sentinel-based resolver — walk up from `[CallerFilePath]` (.NET) / `import.meta.url` / `__dirname` (TS) until a directory containing a known marker (`.git`, `pnpm-workspace.yaml` / `D2.slnx`, or a dual-home contracts marker under `public/contracts/` / `private/contracts/`), then resolve relative to that anchor. Depth-invariant.
  - **Forbidden**: a fixed `..`-count walk-up (`Path.Combine(AppContext.BaseDirectory, "..", "..", "..", "..", "public", "contracts")`, `join(fileURLToPath(import.meta.url), "..", "..", "..")`) — the count silently mis-resolves the moment the file's depth changes.
  - **Evidence**: grep moved / new test files for `..`-count walk-ups (`Path.Combine(.*"\.\."`, `join\(.*"\.\."`, `resolve\(.*"\.\."` with 2+ consecutive `..`) → per hit, confirm sentinel-based (PASS) or rewrite (FINDING). Any fixed-count walk-up crossing the package boundary = FINDING-MEDIUM (latent ENOENT trap); a MOVED test whose count no longer matches its depth = FINDING-HIGH (active break, possibly masked by missing test-runner wiring).
  - **Why**: a hardcoded `..`-count encodes the file's CURRENT depth; a folder reorg makes it wrong and the failure is invisible if the suite isn't in the default run. A sentinel finder is depth-invariant. (0010 shared-folder reorg: moved test files carried stale `..`-counts, some failures masked by missing test-runner wiring.)
  - **How**: reorg audits grep MOVED test files for `..`-count walk-ups and re-verify depth; new tests use a shared `RepoRoot.Find()` / `findRepoRoot()` marker-walk from the start. Cross-ref §1.16 (sentinel resolution must anchor inside the repo, not walk up into `.env.secrets`-bearing parents) and §9.34 (the MSBuild-manifest sibling).

- **1.25** When a fix adds a required field / property to an existing type — OR changes an interface that tests construct inline — does verification confirm the AFFECTED TESTS EXECUTED (their names appear individually in runner output AND the skipped count is 0), NOT merely that the aggregate passed count held steady or increased?
  - **Evidence**: per change adding a required field / property / ctor parameter to a type constructed in a test → either (a) the runner output listing the specific affected test name(s) showing they ran, OR (b) a structural read of the test source confirming the construction site was updated before the count is trusted.
  - **Why**: a stable aggregate pass is NOT evidence the tests exercising the changed site ran — the only reliable evidence is the test name in output + skipped = 0. (0015 final-review: a Fixer's "5423 pass" held across a fix that left an inline entity missing two now-required properties; the throw at `SaveChangesAsync` went undetected.)
  - **How**: (a) grep the test source for ALL construction sites of the type, (b) update every site omitting the new required member, (c) confirm the specific test names appear in runner output. Auditors MUST NOT accept "total count held" as §2.3-equivalent evidence when the change touches a type constructed inline in existing tests. Cross-ref §2.1, §2.3.

- **1.26** Does any step that introduces or modifies an EF value-converter mapping, a `ComplexProperty` mapping, or an `IAnonymizationEngine`-driven erasure path ship at least ONE live-DB integration test (Testcontainers, real PostgreSQL / SQLite in-process) exercising the mapping end-to-end via a real provider, not only model-introspection (`GetEntityType` / `FindProperty` / `GetValueConverter`) unit tests?
  - **Scope**: any step that (a) adds/modifies a `HasConversion<T>` / value-converter registration, (b) adds/modifies a `ComplexProperty` mapping with column names / converters / `[RedactData]`, OR (c) adds/modifies a `D2:Anonymize` annotation an `IAnonymizationEngine` must execute. Model-introspection tests are NOT sufficient alone for these surfaces; pair with a live-DB round-trip.
  - **Evidence**: per step meeting scope → ≥1 Testcontainers (or equivalent) integration test file:line that: (a) inserts an entity carrying the changed mapping through a real `DbContext`, (b) reads it back and asserts the mapped value survives, (c) for anonymization: calls `IAnonymizationEngine.AnonymizeUserAsync` / `AnonymizeOrgAsync` through the real provider and asserts the tombstone was written (not merely that the annotation is present).
  - **Why**: model-introspection reads the EF metadata graph, not the SQL wire output — a real provider must materialize + execute the SQL for mapping bugs to surface. (0015: a same-VO-twice navigation bug and a value-converter coercion bug — cross-entity leakage + un-erased PII — were each caught ONLY by a live-DB test; model-introspection passed clean.)
  - **How**: the Plan enumerates (a) which value-converter / complex-property / anonymization paths need live-DB coverage, (b) the Testcontainers fixture shape, (c) per path the insert + read-back scenario + assertion. Ship the integration test in the SAME step (§11.1). Cross-ref §1.11, §1.19, §3.15.

- **1.27** In xUnit / AwesomeAssertions / FluentAssertions assertion closures containing a lambda, does the lambda capture only the non-disposable value (e.g. `CancellationToken` from a `CancellationTokenSource`, a `DatabaseFacade` from a `DbContext`) — NOT the enclosing `IDisposable` that owns it — when the outer variable is disposed before the lambda runs?
  - **The pattern**: extract the non-disposable value into a local BEFORE the lambda; close over the local, not the outer disposable. JetBrains `inspectcode` fires `"The expression is always closed over captured variable which is disposed in the outer scope"` when a lambda captures a `CancellationTokenSource` / `DbContext` / other `IDisposable` disposed in a surrounding `finally` / `await using` block.
  - **Why**: the `jb inspectcode` zero-warnings gate (§5.22) treats this as a real finding — the captured variable IS disposed in the outer scope and the lambda may or may not run before disposal; even when it runs synchronously `inspectcode` cannot prove it. Extracting the value eliminates the concern and makes intent explicit.
  - **How**: add a local before the assertion (`var ct = cts.Token;` / `var dbFacade = ctx.Database;`) and reference it inside the lambda. Applies to `Assert.Throws` / `await Assert.ThrowsAsync` / `act.Should().Throw` / any lambda-accepting assertion helper.
  - Evidence: `grep -rEn 'using var|await using var' <test scope>` → per outer `IDisposable`, confirm lambdas in the same block close over the extracted value, not the outer disposable. Zero `inspectcode` `AccessToDisposedClosure` / `"disposed in the outer scope"` warnings on the test project.

- **1.28** For any TypeSpec decorator package, does the test suite include BOTH (a) TypeSpec test-host integration tests that compile a `.tsp` program and read state back via `program.stateMap(key)`, AND (b) direct-unit tests that call each `$fn` body directly from `src/` with a lightweight mock `DecoratorContext`?
  - **Evidence**: the TypeSpec test host loads `$fn` bodies from compiled `dist/` JS; V8 only instruments `src/` for coverage. A suite of test-host round-trips passes `vitest run` but fails `test:coverage` with 0% on the `$fn` module because V8 never sees a direct call into `src/decorators.ts`. Per decorator `$fn` → ≥1 direct-unit test importing the function from its source module (not `dist/`) + a mock `DecoratorContext` spying on `program.stateMap(key).set`. Gate command = `test:coverage`, NOT bare `vitest run`.
  - **Why**: a 100% branch-coverage threshold gating CI catches regressions early, but without direct-unit tests for `$fn` bodies the gate is structurally unachievable (integration tests exercise `dist/`, V8-invisible) — so it permanently fails or is silently excluded. (0018 Step 1 — see Provenance.)
  - **How**: per `$fn` (typically `$d2Xxx`): (1) import it from its source module, (2) construct a `DecoratorContext` stub (`{ program: { stateMap: () => new Map() } }` or a spy), (3) call `$d2Xxx(ctx, target, ...args)` directly, (4) assert `stateMap(KEY).set` was called with the expected value. Run `test:coverage` (not `vitest run`) as the per-step gate. Keep the integration round-trips alongside — the two are complementary, not substitutes.
  - **When**: every TypeSpec decorator package. Per step adding/modifying a `$fn` → the same step ships the direct-unit test AND confirms `test:coverage` passes. Missing direct-unit test for a `$fn` = FINDING-HIGH.
  - *Provenance: deliverable 0018 Step 1 (FINDING-H F-A2).*

- **1.29** In any TypeSpec decorator package, does every rejection test assert BOTH (a) the expected diagnostic code is present in `program.diagnostics` AND (b) `program.hasError() === true`? Does the suite also include a dedicated catalog-integrity test confirming every `$lib.diagnostics` entry has `severity === "error"`?
  - **Evidence**: `program.diagnostics` holds both `"error"` and `"warning"` severities. A test asserting only code presence cannot detect an `"error"` → `"warning"` regression — it passes but the build no longer fails for the contract-violation case. Per rejection test → two assertions: (1) code present (`.some(d => d.code.endsWith("<code>"))`), AND (2) `expect(program.hasError()).toBe(true)`. Catalog-integrity test `lib_AllDiagnosticsHaveErrorSeverity` iterates `Object.values($lib.diagnostics)` and asserts each `severity === "error"`.
  - **Why**: the contract of a TypeSpec validation decorator is "invalid configs FAIL THE BUILD." A `"warning"` satisfies code-presence but not fail-the-build (no red build, only a squiggle). The two-level assertion is the minimum for the contract; the catalog-integrity test guards a future entry accidentally shipping `severity: "warning"`, making severity-regression visible at authoring time. (0018 Step 3 — see Provenance.)
  - **How**: standardize rejection structure: compile the invalid `.tsp` snippet, assert `.some(d => d.code.endsWith(...))`, assert `program.hasError() === true`. Ship one `lib_AllDiagnosticsHaveErrorSeverity` per `$lib`.
  - **When**: every TypeSpec decorator package. Per step adding a diagnostic code → the same step ships the catalog-integrity update AND the two-assertion rejection test; existing rejection tests retrofit to the pattern in the same deliverable. Missing `hasError()` assertion = FINDING-HIGH.
  - *Provenance: deliverable 0018 Step 3 Plan-Audit FINDING-H-1.*

- **1.30** For any test exercising a real socket or platform-dependent transport path (a mutual-TLS handshake over a real TCP connection, a Unix-domain-socket bind, a platform-specific TLS-stack behavior) that CANNOT run on the developer's OS, does the scope ship all three: (1) an HONEST platform-skip on the incompatible OS (reports SKIPPED, never a fake / auto / unconditional pass); (2) a deterministic cross-platform UNIT matrix for the underlying logic (validator, wire parser, policy decision) that runs everywhere; (3) a same-platform CANARY covering the platform-INDEPENDENT slice? Is the full real-socket path then proven in the deploy-target container (Docker / Linux)?
  - **Scope**: any test whose pass/fail depends on a transport behavior the developer OS cannot exercise (a real-socket mTLS handshake gated on the OS TLS stack, a UDS bind, platform-specific cert-chain validation, a kernel-level socket option). A test that runs identically on every OS (pure logic, in-memory streams) is out of scope — a normal unit test.
  - **The three required artifacts** (all three, not a subset):
    - **Honest platform-skip** — on the OS where the path cannot run, the test reports SKIPPED via a real mechanism (`[SkippableFact]` + `Skip.IfNot(...)`, an xUnit `Skip`, a runtime `OperatingSystem.IsLinux()` guard). A method returning early with a green assertion (`Assert.True(true)`), a `[Fact(Skip = ...)]` hiding a path never made to work, or any "auto-pass on this OS" is FORBIDDEN — it claims coverage that does not exist.
    - **Cross-platform unit matrix** — the underlying decision logic (cert / token validator, handshake-policy evaluator, wire parser) is extracted and unit-tested deterministically on EVERY OS, decoupled from the socket. This is where the adversarial coverage lives (malformed / expired cert, wrong SAN, untrusted issuer) — it must not be gated behind the platform-skipped socket test.
    - **Same-platform canary** — covers the platform-INDEPENDENT slice that DOES run on the dev OS (constructing the TLS options, building the cert chain in memory, pre-handshake validation).
  - **Forbidden**: marking a platform-incompatible test "green" on an OS where it cannot exercise the path. A fake-green real-socket test is strictly worse than an honest skip — it reports coverage that does not exist, so the gap is invisible until the container (or production) surfaces it.
  - **Evidence**: per platform-dependent transport test → (a) the skip mechanism file:line showing an HONEST skip (SKIPPED in runner output on the incompatible OS); (b) the cross-platform unit-matrix file:line covering the logic adversarially; (c) the same-platform canary file:line; (d) the deploy-target container invocation (the Docker/Linux CI job / `docker run`) exercising the real-socket path. A real-socket test GREEN on an OS that cannot run the path = FINDING-HIGH (fake coverage). Missing cross-platform matrix = FINDING-HIGH (adversarial logic gated behind a skip). Missing container proof = FINDING-HIGH (the real path never exercised).
  - **Why**: on a dev OS that rejects the handshake, the tempting wrong fix (`Assert.True(true)` / a hidden skip masking a broken path) reports green coverage for a path that never ran. The correct shape splits the concern — platform-independent LOGIC unit-tested everywhere with full adversarial coverage; the platform-DEPENDENT socket path skipped HONESTLY (visible in the runner) and proven in the container, so the honest skip keeps the gap VISIBLE and the container proof closes it.
  - **How**: the Plan enumerates the four artifacts above; use a real skip primitive (`[SkippableFact]` + `Skip.IfNot(OperatingSystem.IsLinux())`) so the incompatible-OS run reports SKIPPED. Cross-ref §1.2, §1.11, §1.16, §24.27 (a real-socket green depending on a diagnostic-installed trust root is a false-green — re-run from a clean state).
  - **When**: every real-socket / platform-dependent transport test where the dev OS cannot exercise the path. Transport tests that run identically on every OS (in-memory streams, pure protocol-parsing) are ordinary §1.1 / §1.2 units.
  - *Provenance: deliverable 0022 Step 5 (clean-Windows real-socket mTLS over a private CA is intractable — Schannel's `SslStreamCertificateContext.Create` throws for any non-OS-trusted-root chain; resolved by honest-skipping the 6 cert-presenting cases on Windows + running them in the Docker/Linux container, the `SpiffeSanPeerValidator` matrix proving the logic cross-platform + a no-cert canary on every OS).*

- **1.31** For every seam a DI-registration extension (`AddX`) registers, does a resolution test in THAT extension's OWN test file `GetRequiredService<>()` the seam — rather than relying solely on a cross-module / composed-host test that happens to resolve it transitively?
  - **Scope**: every publicly-injectable seam an `AddX` registers (handler interfaces, ports, keyed resolvers, options-configured services). Sharpens §1.3 by pinning WHERE the resolution test lives: in the registering extension's own test, not borrowed from a downstream consumer. Out of scope: a seam with no standalone registration extension (host-inline only) — usually itself a §9.22 smell.
  - **The rule**: the extension that OWNS the registration owns the resolution proof. `AddX`'s own test builds a `ServiceProvider` from `AddX` (+ minimal real dependencies) and calls `GetRequiredService<ISeam>()` for every seam it registers. A seam proven resolvable ONLY in a downstream composed-host test leaves `AddX`'s OWN contract unverified — the next change to `AddX` that breaks it passes `AddX`'s suite and only fails the unrelated downstream test (if it covers it).
  - **Evidence**: per `AddX` in scope → its own test file contains a `GetRequiredService<ISeam>()` (or singleton-resolution) call for every seam, each listed individually (§1.3). A seam whose only resolution proof is in a different module's integration test = FINDING (the §1.3 gap localized to the owning extension).
  - **Why**: descriptor-presence ≠ resolvability (§1.3), AND resolvability-proven-elsewhere ≠ the owning extension's contract being tested — a regression in `AddX`'s registration surfaces, if at all, as a confusing failure in an unrelated module. (0023 FINAL-REVIEW M-2 — see Provenance.)
  - **How**: when writing/modifying an `AddX`, add (in `AddX`'s own test file) a composition-resolution test that resolves every seam it registers; do not treat a downstream integration test as a substitute. Cross-ref §1.3, §9.21, §9.22.
  - *Provenance: deliverable 0023 FINAL-REVIEW M-2.*

- **1.32** When a validation suite uses a test double to stand in for a collaborator that does not yet exist (an unbuilt host, an unregistered consumer, a not-yet-wired DI integration), does the double CAPTURE and ASSERT the inputs the component passes across the seam, AND verify the outputs it processes in return — rather than vacuously returning a canned value with no structural assertion?
  - **Scope**: any test using a mock / stub / fake / spy to substitute for a real collaborator that is (a) not yet built, (b) not yet wired into the target hosting surface, or (c) a real shared lib isolated for independent generator validation. Governs the BEHAVIORAL FIDELITY of those doubles, not merely their presence.
  - **The rule**: a seam-contract double must:
    - Capture the INPUTS the component passes to it (method arguments, wire bytes, emitted string content) and assert they match the expected contract values at that seam.
    - Return a REALISTIC RESPONSE that exercises the component's handling of the collaborator's wire format — not a trivially-truthy sentinel that would pass even if the component sent garbage.
    - Document IN THE LEDGER (§26.16) what real collaborator the double stands in for and its replace-trigger.
  - **Hollow double = FINDING-HIGH**: a double returning `"ok"` / `true` / an empty struct without asserting any input is not a seam-contract test — it is a vacuous pass indistinguishable from a test never written; it will not catch the component sending malformed, missing, or wrong data.
  - **Evidence**: per double standing in for an unbuilt collaborator → (a) setup code asserting specific input values (`Verify(m => m.Emit(It.Is<Spec>(s => s.Field == expectedValue)))` or equivalent); (b) a realistic response exercising downstream handling; (c) a §26.16 ledger entry naming the double + real collaborator + replace-trigger. A spy/mock with ZERO input assertions or `It.IsAny<T>()` across the board = FINDING-HIGH.
  - **Why**: a hollow double gives the impression of coverage while providing none — the seam is the only place the proof can live when the real collaborator is absent, and a double asserting nothing lets a completely wrong emitter output pass green; the regression surfaces only when the real collaborator is wired, at orders-of-magnitude higher fix cost.
  - **How**: (1) use a framework that lets you assert specific argument values; (2) name the specific wire-value / structural property the component must pass (the emitted error-code string, the TK constant path, the exact JSON field-name); (3) return a response that makes the component do something non-trivial downstream (not `null` / `true` / `string.Empty`). Record the double in the §26.16 validation ledger + the retire event.
  - **Cross-refs**: §26.15 (generators validated independently — this governs the QUALITY of the doubles); §26.16 (the ledger); §1.5 (snapshot tests — complementary); §1.2 (the realistic response exercises error/empty/malformed paths).

- **1.33** Does every test wait for an asynchronous condition via a SIGNAL-DRIVEN or ATTEMPT / POLL-BUDGET mechanism — never via an elapsed-wall-clock deadline in the success path? A `DateTime.UtcNow + timeout` / `Stopwatch`-horizon / fixed-`Task.Delay`-then-assert wait that can EXPIRE while the awaited work is still making progress is forbidden; any bounding budget (poll attempts, nudge count) exists ONLY as a genuine-stuck guard, sized so a passing run never reaches it.
  - **Evidence**: `grep -rEn 'DateTime\.(UtcNow|Now)|Stopwatch|Task\.Delay\(' <integration/test scope>` → per hit in a wait / settle path, confirm termination is signal-driven (semaphore / `TaskCompletionSource` / event) or attempt-budgeted, not elapsed-time-gated. Negative-check settle delays and drain assertions of a DIFFERENT class are cited as deliberately-retained.
  - **Why**: under full-suite thread-pool saturation a wall-clock horizon expires while the starved SUT continuation has not yet run — a load-only failure, invisible when the test runs solo, that re-flakes the gate suite every merge. Signal-driven / attempt-budgeted waits stretch with the slowdown instead of expiring, so the same code is deterministic under load. Three distinct flake classes in 0026 traced to this exact pattern (a refresh-test count budget that burned before the starved `Task.Delay` continuation ran a single tick; broker-wait helpers using `DateTime.UtcNow + timeout` deadlines; a 30s wall-clock CTS — each replaced with a signal or a poll-attempt budget, no assertion weakened, no sleeps added).
  - **How**: replace the wall-clock CTS with a signal (a counting semaphore fired per timer registration / a `TaskCompletionSource` completed by the awaited event) or an attempt budget (`_POLL_ATTEMPT_BUDGET`, unreachable on a passing run); remove dead timeout parameters at all call sites; sister-sweep the identical latent helper across sibling integration files and document what is deliberately left. Never weaken an assertion or add a bare sleep to "fix" a flake. Cross-ref §1.2, §1.16, §4.5.
  - *Provenance: 0026 post-cycle de-flake commits (park-driven clock advance + poll-budget broker waits); "load-only failure, invisible solo" is the diagnostic fingerprint.*
