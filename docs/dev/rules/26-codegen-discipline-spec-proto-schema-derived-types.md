## 26. Codegen Discipline (spec / proto / schema-derived types)
<a name="top"></a>
_[← rules index](../rules.md) · §26 of the D2-WORX rules catalog._

When a `.proto`, `.spec.json` + `.schema.json`, OpenAPI spec, GraphQL schema, or any multi-language type contract exists for a type, hand-written spec-mirror types in any DESTINATION assembly (one that ships to consumers) are FORBIDDEN — they create a third source of truth (schema + spec + DTO) where every drift is a silent-bug surface schema validation cannot catch (a DTO field absent from the schema gets silently dropped on parse; a schema-required field missing from the DTO gets silently un-required). Empirical: `SubdivisionSpec.cs` carried an `EndonymOfficialName` field NOT in the schema AND omitted `parentISO31662Code` from the schema's required-set — exactly this drift.

Hand-coded spec-mirror DTOs INSIDE the source-gen project (deserialization shims that never ship) are PERMITTED under two structural conditions: (a) the source-gen csproj is a Roslyn analyzer (`netstandard2.0` + `IsRoslynComponent=true`) so the DTOs cannot leak to consumers — only the emitted `.g.cs` ships; AND (b) where a TypeScript counterpart emitter exists, cross-language parity tests verify the same JSON spec produces equivalent output on both sides. Without parity tests an internal DTO becomes the same anti-pattern as a destination-leaked one — silently divergent emitter behavior from the same spec.

This category is its own conceptual surface because codegen discipline cuts across architecture, conventions, and shared-lib hygiene. The predicates apply at PLAN time (Plan-Audit per §24.16 verifies them as a primary Cluster E check) AND at code-audit time (any new source-gen producing DTOs is a §26 audit row).

### Predicates — §26 codegen discipline

- **26.1 (No hand-coded spec-mirror types in DESTINATION assemblies)** When a multi-language type contract exists (`.proto`, `.spec.json` + `.schema.json`, OpenAPI, GraphQL, JSON Schema, or any declarative type spec), are hand-coded `record` / `class` / `interface` / `type alias` declarations whose field set + types + nullability mirror that spec's entry structure FORBIDDEN in any DESTINATION assembly (any assembly shipping to consumers — anything NOT a Roslyn analyzer `*-source-gen` csproj scoped per §26.2)?
  - **Boundary vs §11.30**: §11.30 governs cross-language CONSTANT CATALOGS (values crossing the network); §26.1 governs DESTINATION-ASSEMBLY DTO SHAPES (records / interfaces mirroring a spec entry). On an enum-like DTO catalog both co-apply — classify §26.1 when the violation is the type's FIELD STRUCTURE, §11.30 when it's the CATALOG VALUES crossing the wire. When both apply, classify §26.1 (narrower / more-architectural) noting §11.30 also flags it.
  - **Scope**: any type whose shape is defined by a checked-in spec AND whose declaration lives in a destination assembly (a `.csproj` / `package.json` compiling to a consumer-facing DLL / package). The scope is the LEAK SURFACE — types consumers can `using` / `import`. Source-gen internals (§26.2) are out of scope here.
  - **Allowed (NOT violations — complementary, not spec-mirror)**: behavioral interfaces / extension methods (`IGeoReference` — API surface, not data shape); typed primitives / catalog instances the codegen catalogs are INSTANCES of (`TKMessage` whose `TK.g.cs` emits instances; `Scope` primitive whose `AuthScopes.g.cs` emits constants — the hand-coded type DEFINES one catalog entry's shape, the source-gen emits POPULATED INSTANCES); meta-records surfaced via public API (`SpecMetadata`, `EmitResult`) — explicit carve-out, cited by name + reason.
  - **Forbidden in destination assemblies**: `public record FooSpec(...)` mirroring a JSON spec entry that ships to consumers; `public interface IFoo { ... }` mirroring a spec entry's field structure; TS `export interface FooSpec { ... }` / `export type FooSpec = { ... }` in a published package mirroring a spec; any hand-coded destination type whose field set + types + nullability duplicates a schema's property declarations.
  - **Evidence**: enumerate destination assemblies FIRST (every `.csproj` NOT `<IsRoslynComponent>true</IsRoslynComponent>` + every published TS package that is NOT a source-gen internal); ONLY THEN grep them for `record [A-Z][A-Za-z]+Spec\b`, `interface I[A-Z][A-Za-z]+Entry\b`, `record [A-Z][A-Za-z]+Entry\b`, `type [A-Z][A-Za-z]+Spec\s*=`, `interface [A-Z][A-Za-z]+Spec\s*\{` (the whole-repo naive grep surfaces §26.2-permitted internal DTOs as false positives). Per hit → read the declaration + cross-reference the spec. Behavioral interface / typed primitive / catalog-instance → PASS with reason cited (e.g. `PASS — TKMessage is a typed primitive; TK.g.cs emits instances; cited at TKMessage.cs:12`). Spec-entry mirror in a destination assembly → FINDING-HIGH. A hit in a Roslyn analyzer csproj → the §26.2 carve-out — evaluate under §26.2 instead.
  - **Why**: destination types are public API — every consumer can deserialize / construct / serialize them, so hand-coded mirrors create the silent-drop / silent-un-required drift documented above. The 0008 destination-leak audit found ZERO destination duplicates — that baseline is what this predicate locks in.
  - **How**: at PLAN (§24.16 Cluster E) + code-audit time, a new spec-derived destination type MUST either be autogenerated (destination receives only `.g.cs`) OR be a complementary typed primitive / behavioral interface (cited explicitly). Existing destination spec-mirror types = tech debt; on next-touch migrate the whole DTO to autogen OR into source-gen internals — do NOT add a new field to the hand-coded destination DTO.

- **26.2 (Source-gen INTERNAL DTOs allowed under no-leak + parity-test conditions)** When a source-gen needs a deserialization shim to read its JSON spec (an `internal sealed record FooSpec(...)` consumed only by the source-gen's JSON parser, never emitted to consumers), is the source-gen structured so the DTO cannot leak to consumer assemblies, AND — where a TypeScript counterpart emitter exists — do cross-language parity tests verify the .NET and TS emitters produce equivalent output from the same spec?
  - **Boundary vs §16.4 (Polyfills/ pattern)**: §16.4 mandates that string / Guid / collection helpers INSIDE a `netstandard2.0` source-gen use `Polyfills/StringExt.cs` instead of the forbidden BCL helpers — universally, INCLUDING inside the §26.2-permitted internal DTOs. The §26.2 carve-out covers the DTO's SHAPE (hand-coded mirror OK if no-leak + parity); it does NOT exempt the DTO's INTERNAL USE of helpers from §16.4 (a `FooSpec` calling `string.IsNullOrEmpty` violates §16.4 even though §26.2 permits the record).
  - **Scope**: any `internal sealed record` / `class` / `interface` inside a `*-source-gen/*.csproj` that mirrors a JSON spec entry to deserialize the spec at codegen time; the DTO never appears in emitted `.g.cs` and never references a consumer-facing type.
  - **Conditions BOTH required for the carve-out to apply**:
    - **(a) No leak — structural csproj guarantee**: `<TargetFramework>netstandard2.0</TargetFramework>` AND `<IsRoslynComponent>true</IsRoslynComponent>` (the analyzer runs in the compiler process; its types are NEVER added to consumer assemblies), + the DTO declared `internal`. Only the `.g.cs` files emitted via `context.AddSource(...)` reach consumers.
    - **(b) Parity tests (where a TS counterpart exists)**: per §26.3, a cross-language parity test loads the SAME `contracts/` JSON spec, runs / compares both emitters, and asserts equivalent output. If no TS counterpart exists (and none is planned), this sub-condition is N/A.
  - **Evidence**: per source-gen with internal spec-mirror DTOs → (1) verify `netstandard2.0` + `IsRoslynComponent=true` both present, cite both lines; (2) grep the referenced project assemblies' bin output for the DTO type name → ZERO hits (proves no-leak); (3) per §26.2(b), cite the parity test. Both hold → PASS with both citations. (a) fails → FINDING-HIGH (leak surface). (b) fails (TS counterpart exists, no parity test) → FINDING-HIGH (drift surface); see §26.3.
  - **Why**: deserialization shims are pragmatic and are NOT the leak surface §26.1 prevents (Roslyn analyzers structurally cannot ship their internal types — the 0008 audit confirmed ZERO consumer-side duplicates). The remaining risk is cross-LANGUAGE drift, which §26.3 parity tests detect; with both conditions in place the pattern is safe.
  - **How**: migrating a hand-coded DTO OUT of a destination assembly (§26.1) INTO source-gen internals satisfies §26.2 as long as both conditions hold. At PLAN time confirm both; the audit row cites the csproj structure (file:line) + the parity test reference (or N/A).

- **26.3 (Cross-language parity tests required for source-gens with TS counterparts)** For any source-gen with a TypeScript counterpart emitter (e.g. `auth-scopes-source-gen` ↔ `tools/ts-codegen/src/auth-scopes-emit.ts`), does a cross-language parity test load the same JSON spec, run / compare both emitters' output, and assert equivalent output — same keys / constant names / wire-format values / semantic coverage — failing on drift?
  - **Boundary vs §1.19 (runtime composition / wire-up integration tests)**: §1.19 covers RUNTIME WIRE-UP (logging pipelines, telemetry SDK setup, middleware order, message-bus subscribers). §26.3 covers EMITTER-OUTPUT EQUIVALENCE between two languages from the same spec — a different failure class. A source-gen WITH a TS counterpart triggers BOTH; PASS on §26.3 does NOT transitively PASS §1.19. Auditors walk them as independent rows.
  - **Scope**: every pairing of a .NET source-gen + TS emitter consuming the same checked-in JSON spec (walk `*-source-gen/*.csproj` + match each to its counterpart under `tools/ts-codegen/src/` or `server/shared/typescript/*/`). Pairings with no TS counterpart (.NET-only) are out of scope per the carve-out below.
  - **Required test properties**: **same spec input** (loads the SAME `contracts/` JSON, not a per-language fork); **equivalence assertion** (same constant names, wire-format string values, `enum` member coverage, semantic key ordering — trivial formatting differences OK); **drift detection** (adding / removing / renaming a key MUST fail the test until BOTH emitters reflect it — the structural guard against one emitter being updated without the other).
  - **Canonical pattern reference**: 0009 Step 1 (`D2.Shared.Time`) shipped `contracts/temporal/temporal-adversarial.fixture.json` consumed by both `CrossLanguageTemporalParityTests.cs` (.NET) and `cross-language.test.ts` (TS) — one fixture drives both; adding a case fails both until both cover it. Use as the reference for adding parity tests where missing.
  - **Carve-out**: .NET-only source-gens (no TS counterpart exists AND none is planned per the active project tracking doc) are exempt — cite the carve-out reason in the audit row (e.g. `N/A — geo-context-source-gen is .NET-only; no TS counterpart planned per docs/v2/V2.md`).
  - **Evidence**: per `*-source-gen/*.csproj` → search `tools/ts-codegen/src/` + `server/shared/typescript/**/` for a counterpart (`{name}-emit.ts` / `{name}.ts` consuming the same spec); per pairing → search the test trees for a file that loads the shared JSON spec AND asserts on both emitters' outputs — cite the test files + the spec. TS counterpart with no parity test → FINDING-HIGH (drift surface). Parity test checking only one side (no cross-language assertion) → FINDING-MEDIUM (name implies parity but doesn't enforce it).
  - **Why**: without parity tests the §26.2 "internal DTOs allowed" carve-out is structurally unsafe — the .NET and TS interpretations can drift silently (a field added to the spec lands in one emitter's output but not the other). Schema validation catches spec-vs-emitter drift WITHIN one language; only cross-language parity catches DIVERGENT interpretations BETWEEN languages from the same spec.
  - **How**: at PLAN time enumerate every source-gen the deliverable touches + verify (or schedule) parity coverage for each with a TS counterpart. The §26.3 row cites the parity test + shared spec, OR the carve-out reason for .NET-only source-gens; new source-gens with TS counterparts land their parity tests in the same deliverable.

- **26.3.1 (Fixture-reflection patterns are permitted for cross-language parity tests)** When a cross-language parity test (§26.3) consumes a shared cross-language ground-truth fixture (e.g. `contracts/geo/fixtures/confusables.fixture.json`, `contracts/temporal/temporal-adversarial.fixture.json`), MAY the test walk the fixture rows via reflection / iteration — asserting field-set / shape / outcome equivalence per row — instead of per-case `[Theory] [InlineData]` / `it.each`? Yes, when all three carve-out criteria are met.
  - **Scope**: parity tests covered by §26.3 (cross-language emitter-output OR cross-runtime outcome equivalence from a shared spec / fixture). This carves fixture-reflection OUT of the broader "each case should be `[Theory] [InlineData]`" presumption that applies to single-runtime behavioral tests; it does NOT carve out single-runtime behavioral testing (see "Boundary vs traditional InlineData" below).
  - **Carve-out criteria (all three must hold)**:
    - **(a) Shared fixture is the cross-language ground truth**: the test loads a fixture checked into `contracts/` (or equivalent shared location) that BOTH runtimes consume — not a per-language fork. The fixture IS the canonical case enumeration.
    - **(b) Field-set / shape / outcome equivalence asserted via walking the fixture**: the test iterates fixture rows (`for (const row of fixture.cases)` / `[Theory] [MemberData(nameof(FixtureCases))]`) and asserts per-row equivalence on §26.3's dimensions. Reflection is permitted when the assertion is over types' SHAPES (field-set membership) rather than per-field hard-coded literals.
    - **(c) Both runtimes consume the same fixture as ground truth**: a sister-test on the OTHER runtime walks the SAME fixture with structurally-equivalent assertions. Adding a row pressures BOTH runtimes' tests identically; the pair of fixture-walkers IS the parity proof — neither alone suffices.
  - **Boundary vs traditional `[Theory] [InlineData]` / `it.each`**: per-case enumeration is STILL REQUIRED for (1) single-runtime behavioral tests (no cross-language ground truth to walk); (2) tests pinning specific input → output expectations NOT in a cross-language fixture (a one-off regression test); (3) tests where the cases ARE the spec (parser edge cases with no shared fixture). Fixture-reflection is NOT a shortcut to avoid writing test cases — it is correct ONLY when the cross-language fixture IS the case enumeration.
  - **Evidence**: per fixture-reflection parity test → cite (1) the `contracts/` fixture both runtimes load; (2) the .NET sister test walking it; (3) the TS sister test walking it; (4) the reflection / iteration mechanism (`for (const row of fixture.cases)` / `[MemberData]` / `Object.keys(...)`). If any of the three carve-out criteria fails — fixture not shared, no sister test on the other runtime, or the pattern used to AVOID tests for a non-fixture surface — the carve-out does NOT apply and the test is re-shaped to per-case enumeration. PASS rows cite §26.3.1 alongside the standard §26.3 evidence.
  - **Why**: cross-language parity is structurally a fixture-walker problem — the ground truth IS a row-wise table, and repeating each row as `[InlineData]` DUPLICATES the fixture (a second source of truth; drift between them passes silently). Reflection preserves single source of truth: a row added to the fixture runs through BOTH runtimes with no test-code edits, failing the moment fixture and implementation disagree. Canonical codebase examples walk `records.json` / `confusables.fixture.json` from both runtimes.
  - **How to apply**: at PLAN time name the chosen pattern — **fixture-reflection per §26.3.1** (shared cross-language fixture + sister test on the other runtime) OR **traditional enumerated cases** (test-code-local / single-runtime). Auditors do NOT flag fixture-reflection as missing-`InlineData` coverage when the three carve-out criteria are met — this carve-out exists specifically to stop that recurring miscategorization.
  - **When**: applies at every cross-language parity test added / modified + at PLAN time when the Plan proposes parity coverage (the Plan names the chosen pattern).

- **26.3.2 (cross-runtime API + diagnostic parity — a capability or a hard-fail diagnostic on one runtime gains its twin)** When a cross-runtime pair (.NET source-gen ↔ TS emitter, .NET codec ↔ TS codec) gains a CAPABILITY (a new parameter, a codec helper, an exposed option) OR a hard-fail DIAGNOSTIC (a build-error on malformed input, a closed-set cross-check, a collision guard), does the twin runtime gain the equivalent — so neither side is silently more permissive or less capable?
  - **Boundary vs §26.3**: §26.3 pins emitter-OUTPUT equivalence (same keys / values / member coverage from a shared spec). §26.3.2 pins API + FAIL-behavior parity (the capabilities each side EXPOSES + the malformed inputs each side REJECTS). Orthogonal: a TS emitter that `continue`s past a malformed spec entry while the .NET source-gen fires a diagnostic is an output-parity non-event but a §26.3.2 violation.
  - **Evidence**: per cross-runtime pair → enumerate (a) the public capabilities / parameters each side exposes and (b) the hard-fail diagnostics each side fires; assert each has a twin. A capability or diagnostic with no equivalent = FINDING (capability gap / fail-behavior asymmetry). PARITY.md's wire-format / codec rows enumerate the capability + diagnostic surface per pair.
  - **Why**: output parity (§26.3) passes when both emitters produce the same constants from a valid spec — but does NOT catch a capability one runtime exposes and the other doesn't, nor a malformed-input case one rejects and the other swallows. Empirical: 0017 final review found a TS gRPC wrapper lacking a `traceId` param the .NET twin threaded, a TS catalog-discovery path silently skipping a malformed spec the .NET source-gen diagnoses, and a missing collision-guard diagnostic on one runtime — output parity passed in each case.
  - **How**: add the twin in the SAME deliverable. At PLAN time enumerate the capability + diagnostic surface per pair; PARITY.md tracks it so a future addition has an explicit twin to mirror. Applies whenever a cross-runtime generator / codec pair is added or modified.
  - *Provenance: deliverable 0017 final review (cross-runtime gRPC-codec capability gap + catalog-discovery + collision-guard diagnostic asymmetries).*

- **26.4 (If you autogen DTOs, use established tools — not one-off generators)** If a source-gen autogenerates DTOs from JSON Schema (rather than hand-code internal spec-mirror DTOs per the §26.2 carve-out), does it use either (a) a custom Roslyn `IIncrementalGenerator` project-consistent with existing infrastructure (e.g. `D2.Shared.Context.SourceGen`) OR (b) `NJsonSchema`? For TS autogen from JSON Schema, `json-schema-to-typescript`? For proto-derived types, the established `@bufbuild/buf` + `ts-proto` (TS) or `Grpc.Tools` + `Google.Protobuf` (.NET) pipeline?
  - **Boundary vs §16.1 / §8.6**: §16.1 says "reach for shared libs before hand-rolling"; §8.6 says "new deps need justification." §26.4 narrows the choice SET for codegen specifically — the established schema-to-DTO tools take precedence over a hand-rolled internal generator. §16.1's "shared lib first" remains true for everything ELSE the source-gen needs; "established codegen tool over hand-roll" IS the §8.6 justification.
  - **Scope**: any source-gen that opts to autogenerate DTOs from a spec (as opposed to the §26.2 hand-coded internal-DTO carve-out). OPTIONAL in the sense that hand-coded internal DTOs are permitted under §26.2 — but IF autogen is chosen, the tool choice is constrained.
  - **PASS / N/A boundary when §26.2 was chosen**: when the source-gen takes the §26.2 hand-coded internal-DTO route (NO autogen output), §26.4 is N/A — cite `N/A — source-gen uses §26.2 hand-coded internal DTOs at <file:line>; no autogen output`. §26.4 only fires PASS / FINDING when autogen output exists.
  - **Evidence**: per source-gen that autogenerates → its `csproj` (`NJsonSchema` ref) / `package.json` (`json-schema-to-typescript`) shows the tool dependency. Custom Roslyn `IIncrementalGenerator`: follows the established structure in `server/shared/dotnet/context/abstractions/` (`[Generator]` attribute, `Initialize(...)` method, schema reader + emitter separation). Proto pipelines: `buf.gen.yaml` + `pnpm-workspace.yaml` (TS); `<ProjectReference>` to a `*.proto` project + `Grpc.Tools` (.NET). Source-gens using the §26.2 carve-out are N/A — cite the §26.2 evidence instead.
  - **Why**: consistent tool choice means one mental model for contributors, shared escape hatches when autogen produces wrong output, and ecosystem schema-feature coverage (one-off implementations lag). `D2.Shared.Context.SourceGen` is the canonical .NET reference; the proto pipeline is canonical per project memory.
  - **How**: at PLAN time (§24.16 Cluster B + E), the Plan names the approach: hand-coded internal DTOs per §26.2 (conditions verified) OR autogen via the listed tools. For .NET, choose Roslyn (incremental-build awareness) vs `NJsonSchema` (one-shot pre-build). Plan-Audit Cluster E rejects a one-off generator when an established tool fits.

- **26.5 (Hand-edits of GENERATED output are FORBIDDEN — fix the generator, the input, or extend the pipeline)** Is every generated artifact free of hand-edits — the only path that mutates a generated file is the generator / emitter / pipeline (or, transitively, the spec / overlay / third-party-source input)? Direct edits are a process-integrity failure: the next pipeline run silently overwrites the "fix," so reproducibility is gone and the fix rots without warning.
  - **Scope**: "Generated" includes (when in doubt, treat as generated): any `*.g.<ext>` file (`*.g.cs`, `*.g.ts`, `*.g.json` — the `.g.` segment is the canonical marker); any file under `Generated/` / `generated/` / `obj/Generated/` / `src/generated/`; any file produced by a documented build / codegen / data pipeline (Roslyn source-gen, `tools/ts-codegen`, `@bufbuild/buf` + `ts-proto`, `Grpc.Tools` + `Google.Protobuf`, Drizzle migration artifacts, Paraglide-compiled locales, and **Tier-2 spec files** like `contracts/geo/*.spec.json` built by the 0008 geo pipeline from Tier-1 Wikidata + CLDR + IPinfo); any file whose header banner carries `GENERATED` / `auto-generated` / `do not edit` / `DO NOT MODIFY` / `<auto-generated>`.
  - **Forbidden**: editing a `*.g.cs` / `*.g.ts` to tweak output (fix the emitter); editing a checked-in `contracts/**/*.spec.json` (or Tier-2 artifact) to correct data quality (fix the Tier-1 source, add an overlay, or extend the transform / validation step); hand-editing a Drizzle SQL / journal / snapshot (edit the schema source + re-run `drizzle-kit generate`); editing Paraglide-compiled output (edit `messages/<locale>.json`); editing proto-derived `*.pb.cs` / `*_pb.ts` (fix the `.proto` + re-run codegen); any commit touching a generated file with no corresponding generator / input / pipeline-config diff in the same commit.
  - **Allowed (NOT violations — fixes through the right layer)**: editing the GENERATOR / emitter / pipeline code; editing the INPUT (spec source, third-party data, schema, overlay, transform-rule file); EXTENDING the pipeline (new overlay, transform step, validation predicate, codegen-time diagnostic); deleting an obsolete generated file when its generator / spec entry is deleted in the same change; re-running the generator after a generator / input change (the commit's PROVENANCE is the generator / input change).
  - **Evidence**: walk the changed-file set; classify each generated vs hand-coded via the scope criteria; for every generated file in the diff → verify the SAME commit / deliverable contains the generator / input / pipeline change that PRODUCES the diff (cite both paths). A generated file touched WITHOUT a corresponding generator-side change in the same commit → FINDING-HIGH (silent-overwrite class). A new generator + its first emitted output BOTH count as Allowed (regeneration is mechanical follow-through).
  - **Why**: reproducibility (`re-run the pipeline → same output`) IS the contract that makes generated code trustworthy; a hand-edit breaks it silently (the next run clobbers it, or produces an eternal merge conflict, or the hand-fix is re-applied on every regen). Empirical: the 0008 geo pipeline — an Implementer hand-edited `contracts/geo/countries.spec.json` to fix a data-quality issue in a Tier-2 file built from Tier-1 sources; the fix worked AT REST but vanished on the next pipeline run. The right surface was the pipeline (overlay / transform / source correction), not the output.
  - **How**: ask "what produced this file?" and fix at one of three layers: (a) the GENERATOR (emitter logic wrong), (b) the INPUT (spec / source / overlay data wrong), (c) the PIPELINE STRUCTURE (add an overlay / transform / validation predicate). Re-run the pipeline; the regenerated file's diff is the mechanical follow-through in the same commit. The FIX never happens at the output.
  - **When**: at every code-audit walk (a diff touching a generated file is a §26.5 row) AND at PLAN time (§24.16 Cluster E2 — a Plan proposing "edit the generated file to fix X" is a Plan-level FINDING forcing relocation to the generator / input / pipeline layer).
  - **Boundary vs §24.17**: §24.17 governs Plan-artifact currency across dispatch; §26.5 governs the LAYER at which generated-output fixes land. Co-apply when a mid-deliverable amendment relocates a generated-file fix — §24.17 requires the amendment in the Plan before re-dispatch; §26.5 requires the fix at the generator / input / pipeline layer.
  - **Boundary vs §26.1**: §26.1 governs WHERE DTO types live (no hand-coded spec-mirrors in destination assemblies); §26.5 governs generated output's reproducibility once it exists (no hand-edits). A `*.g.cs` from a §26.1-compliant source-gen still triggers §26.5 if hand-edited.
  - **Boundary vs §26.3**: §26.3 detects DRIFT between two emitters consuming the same spec (emitter-to-emitter); §26.5 prevents DRIFT between a generated file and its generator (emitter-to-output — hand-edits are the most aggressive form). Parity tests pin emitter-to-emitter agreement; §26.5 pins emitter-to-output agreement.

- **26.5.1 (standing byte-parity gate TEST per committed generated file — drift FAILS a test, not a human's `git diff`)** For every generated artifact committed to the repo (`.g.cs`, `.g.ts`, generated `.g.json`, the committed fixture / manifest outputs of a documented pipeline — the §26.5 scope), does a standing test assert the committed output is BYTE-IDENTICAL to a fresh regeneration from the current spec / generator — so a stale-commit / un-regenerated-output drift FAILS a test rather than relying on a human noticing a diff?
  - **Boundary vs §26.5**: §26.5 forbids hand-EDITING the output (the prohibited ACT); §26.5.1 requires a standing TEST that detects when committed output diverges from a fresh regeneration (the permanent GUARD — fails the moment someone edits a spec / emitter without re-committing the output, OR hand-edits the output). Both apply.
  - **Boundary vs §1.18 / §1.21**: §1.18 pins per-public-VALUE constants; §1.21 pins the per-RECORD wire-key SET against the spec catalog. §26.5.1 pins the WHOLE FILE byte-for-byte — catching dimensions the per-value / per-key-set tests do NOT enumerate (member reordering, banner drift, whitespace / formatting drift, helper members). Complementary, not substitutes.
  - **Non-vacuous-gate requirement**: the byte-parity gate ASSERTS a contract per §1.20 — it MUST be proven non-tautological (a deliberate-drift case fails the gate with a useful diagnostic naming the drifted file / field, then is reverted). A gate that regenerates into the SAME buffer it compares against (can never fail) is the §1.20 tautology.
  - **Evidence**: per committed generated file in scope → the byte-parity gate test (file:line) that regenerates the artifact in-process (or re-runs the emitter against the committed spec) and asserts byte-equality with the committed bytes. A committed generated file with NO standing gate = FINDING-HIGH (drift guarded by human discipline, not a test). Cite the §1.20 negative-validation entry proving the gate fails on deliberate drift.
  - **Why**: a generated file's value is reproducibility; without a standing test that contract is enforced only by a human remembering to run `git diff` after every spec / emitter change. Empirical: 0017 final review surfaced 8 committed `.g.*` files with no byte-parity gate; the fix landed 9 standing gates so a future un-recommitted emitter change FAILS a test instead of silently shipping stale.
  - **How**: ship a `*OutputParityTests` (.NET) / byte-parity case (TS) alongside every committed generated artifact; prove the fail-path per §1.20 (deliberate-drift → gate fails naming the file → revert → passes) and cite the negative-validation entry. New committed generated artifacts land their gate in the SAME deliverable. Applies at every code-audit walk touching a committed generated file AND at PLAN time (the Plan names the gate + the deliberate-drift case).

- **26.6 (Error codes are SPEC-DECLARED — code + httpStatus + category + userMessageKey originate in one spec entry; constants, typed factories, and merged registry are GENERATED)** Is every error code declared in a `*-error-codes.spec.json` catalog (generic `contracts/error-codes/` OR per-domain `contracts/<domain>-error-codes/`), each carrying its `httpStatus`, semantic `category`, and a `userMessageKey`? Are the .NET + TS constants, the typed `D2Result` failure factories, and the merged cross-service registry GENERATED from that spec — never hand-written, never a free-text code string, never a hand-mapped `Fail(statusCode, "message")` where a spec entry could declare it?
  - **Boundary vs §11.30 / §5.3**: §11.30 governs the wire-VALUE of any cross-network identifier; §5.3 governs USING the generated factory at the call site. §26.6 is the upstream STRUCTURAL predicate — code, status, category, message-key all ORIGINATE in one spec entry, and the constants + factories + registry are codegen-emitted.   - **Why**: the `.g.*` extension + generated-banner conventions ARE the §26.5 detection mechanism — the only way the sweep distinguishes "fix the generator, not the file" from "hand-authored, fix it here." A hand-authored file adopting those markers produces false positives and may cause the file to be passed over for manual correction. Cross-ref §26.5, §26.16, §7.7.

- **26.19 (Consumable shared packages are versioned PER-PACKAGE — semver + CHANGELOG derived from the build-free artifact diff; commit footers are escalation overrides; wire/contract breaks are auto-gated, library-API breaks are author-declared; registry publishing is never automatic)** Does every consumable shared package (each `D2.Shared.*` .NET library, the KeyCustodian client, each `@d2/*` TypeScript package) carry its own `MAJOR.MINOR.PATCH` version + its own `CHANGELOG.md`, bumped by the `tools/release-runner` from the build-free artifact diff — not by hand-bumping every commit, and not as one monolithic all-packages release? Are deployable services excluded (they version as deployables on the product cadence)?
  - **The mechanism (default — `runDiffRelease`)**: the runner derives per-package bumps from a build-free artifact diff (`diff-runner.ts:runDiffRelease`): (a) a source-based output fingerprint (SHA-256 over committed source + `PublicAPI.Shipped.txt` / `etc/<pkg>.api.md` API report + resolved dep versions + toolchain pin, committed as `.release-fingerprint`) and (b) a public-API-surface text diff. The diff sets the floor: any fingerprint change → PATCH; any API-surface change → MINOR; a breaking-footer → MAJOR (`≥1.0.0`) / MINOR (`0.x`). **Commit footers (`WIRE-BREAKING:` / `BREAKING CHANGE:`) are escalation overrides only** — they raise the diff-derived floor but never lower it, and are the ONE conscious force-valve for wire/API breaks. The gate + runner share the footer parser (`bump-engine.ts` `parseBreakingFooters`) so the valve and bump signals cannot diverge. The legacy commit-type model (`runner.ts:runRelease`, `--legacy-commit-type`) is a one-cycle escape hatch, not the default.
  - **Dependent propagation**: after direct bumps, the runner PATCH-bumps every consumable dependent of a bumped package (`dependency-graph.ts` — BFS closure over the reverse dep graph, cycle-guarded); the dependent's CHANGELOG gets a `### Changed — Dependency update: <upstream>` entry. Default-ON; `--no-propagate` suppresses it. A dependent re-exposing an upstream break declares it via its own footer.
  - **Commit-format enforcement**: `.husky/commit-msg` machine-enforces conventional-commit format; allowed types `feat | fix | perf | chore | refactor | docs | test | ci | build | style`. Non-conforming subjects are rejected. Merge/revert/fixup/squash/amend commits are exempt. The hook + runner share the type set.
  - **Pre-stable carve-out**: all packages start at `0.1.0`. Breaking changes on `0.x` bump MINOR with no force valve — the gate does not block a pre-stable break. The strict valve + MAJOR bump + gate block activate only at `≥ 1.0.0`. Graduation is a deliberate `--graduate <pkg>`.
  - **Detection scope (the honest boundary)**: the always-on `tools/contract-gate` (`cli.ts`) AUTO-DETECTS WIRE/CONTRACT breaks only — proto (`buf breaking`), `*.spec.json` + i18n keys (JSON-diff), OpenAPI `*.openapi.g.json` (dormant until a stable REST surface ships). It does NOT detect .NET / TS library PUBLIC-API breaks; those are AUTHOR-DECLARED via footer. Automated library-API break detection is a tracked follow-on, not a silent gap.
  - **Deprecate-not-delete**: a going-away spec entry gets a `deprecated` marker (`[Obsolete]` / `@deprecated`), not removal; deletion of even a deprecated entry is a gate break.
  - **Releases / publishing**: each consumable is independently buildable / versionable / packable; a manual `release-libs.yml` `workflow_dispatch` cuts a GitHub Release. Registry publishing (npm / NuGet) is NEVER automatic.
  - **Evidence**: a consumable added / modified → confirm it carries a version slot (`<Version>` / `version`), a `CHANGELOG.md`, and a committed `.release-fingerprint`; a wire/API break lands a `WIRE-BREAKING:` / `BREAKING CHANGE:` footer (NOT a hand-edited version / CHANGELOG — the runner writes both). No version slot / CHANGELOG / fingerprint → FINDING-HIGH. A break by hand-editing version / changelog → FINDING-MEDIUM (bypasses one-signal discipline). A deployable given an independent per-package semver → FINDING-MEDIUM. Missing `--no-propagate` in a scoped dry-run when propagation is unwanted → FINDING-LOW. Verify against `diff-runner.ts` (`runDiffRelease`), `diff-bump.ts` (`deriveBump`), `bump-engine.ts` (`findPackageForFile`, `parseBreakingFooters`, `--legacy-commit-type`), `dependency-graph.ts`, `.husky/commit-msg`, `tools/contract-gate/src/cli.ts`, the per-package `<Version>` / `version` / `CHANGELOG.md` / `.release-fingerprint`, `.github/workflows/release-libs.yml`.
  - **Why**: per-package semver lets a consumer pin one library without coupling to the framework's cadence; the artifact-diff engine makes the bump a function of the committed output, so version metadata can't drift from the code; the auto-gate / author-declare split is stated honestly so no one assumes a library-API break is caught automatically.
  - **How**: at PLAN time confirm `runDiffRelease` is the bump mechanism (no hand-bumping; footers escalation-only); at audit time cite the version slot, `CHANGELOG.md`, `.release-fingerprint`, and (for a break) the footer. Canonical docs: `CONTRIBUTING.md` + `docs/COMMANDS.md`.

- **26.20 (After touching any consumable shared package's source, the `.release-fingerprint` (and `.NET` `PublicAPI.Shipped.txt` / `Unshipped.txt`) must be re-seeded before committing — the pre-commit gate blocks a stale baseline)** After any change to a consumable's source (`.cs`/`.ts`, the API report, `package.json`/`.csproj` dep versions, or the toolchain pin), did the contributor re-run the seed scripts to update `.release-fingerprint` and (for `.NET`) promote `PublicAPI.Unshipped.txt` to `Shipped.txt` before committing?
  - **Mechanism**: `.husky/pre-commit` runs `pnpm --filter release-runner check-baselines` (`fingerprint-currency-cli.ts`), calling `checkFingerprintCurrency` per package: recomputes the source-based fingerprint over the WORKING TREE vs the on-disk `.release-fingerprint`; for `.NET` also asserts `PublicAPI.Unshipped.txt` is header-only. Any mismatch → exit 1 + stale-package table. Distinct polarity from the §26.19 drift check (which compares recomputed vs `git HEAD` and fires when source changed without a version bump — a CI/PR gate); this gate compares recomputed vs the on-disk file and fires when source changed without re-seeding (pre-commit).
  - **Remediation**: run the printed seed scripts (`node tools/scripts/seed-publicapi-baselines.mjs` for `.NET`; `pnpm --filter './server/shared/typescript/**' -r build && node tools/scripts/seed-apiextractor-baselines.mjs` for TS), re-stage, commit again. Seed scripts are the ONLY correct update path — never hand-edit `.release-fingerprint`, `PublicAPI.Shipped.txt`, or `etc/<pkg>.api.md` (§26.5).
  - **Evidence**: the pre-commit hook enforces this on every commit — a clean commit is proof the gate passed. At audit time verify `.husky/pre-commit` invokes `fingerprint-currency-cli.ts` and that the `.release-fingerprint` beside every modified consumable matches the working-tree recompute (`check-baselines` → exit 0). A consumable's source modified but its `.release-fingerprint` NOT updated in the same change → FINDING-HIGH. `PublicAPI.Unshipped.txt` carrying API entries after the deliverable (not header-only) → FINDING-HIGH (seed not run).
  - **Why**: the `.release-fingerprint` is the authoritative proof the drift check's baseline is stable; if it drifts from the working tree, the next PR's drift check fires spuriously. Catching this at pre-commit (full working-tree context, single-script remediation) is cheaper than at CI. The `Unshipped` check enforces that every committer reviewed + promoted new public API before the commit lands.
  - **How**: at PLAN time include a "re-seed baselines before committing" gate-check note; at EXECUTE time, after source changes run `check-baselines` before committing; the Implementer report includes baseline-currency gate state. Entry point: `fingerprint-currency-cli.ts`; testable core: `fingerprint-currency.ts` (`checkFingerprintCurrency`, `formatCurrencyReport`, `isUnshippedHeaderOnly`); docs: `docs/COMMANDS.md`.

- **26.21 (Compare / switch against the EMITTED CONSTANT — never a raw string-literal of a spec/codegen-emitted symbol when a generated constant exists)** When hand-written code branches on a value that has a generated constant — an error code (`KeyCustodianErrorCodes.KEYCUSTODIAN_*`, the generic `ErrorCodes.*`), a generated wire-identifier, any spec-emitted `const` — does every `switch` case label, `==` / `!=` operand, `is`-pattern, and dictionary-key reference use the emitted CONSTANT, never a hand-typed string-literal of that symbol's value?
  - **Boundary vs §26.7 / §12.5**: §26.7 is the EMITTER-OUTPUT analog (the GENERATOR must emit the constant reference, fix at the emitter). §12.5 governs hand-written TK-key references via constants. §26.21 is the CONSUMER-COMPARISON analog: a hand-authored branch / switch / lookup references the generated constant rather than re-typing its literal value.
  - **Forbidden**: `case "KEYCUSTODIAN_KEY_NOT_FOUND":` / `errorCode == "KEYCUSTODIAN_KEY_NOT_FOUND"` / `errorCode is "KEYCUSTODIAN_…"` in hand-written production code where `KeyCustodianErrorCodes.KEYCUSTODIAN_KEY_NOT_FOUND` exists; a dictionary / set built from raw code literals where the generated `<Domain>ErrorCodes.AllCodes` is the source.
  - **Allowed (NOT violations)**: test assertions pinning the WIRE VALUE (`result.ErrorCode.Should().Be("KEYCUSTODIAN_…")`, registry-membership tests, the `[InlineData(<Const>, "<literal>")]` value-pin which REQUIRES both forms); generated output emitting a literal (that is §26.7 / §26.5); a literal with NO generated constant (but surface it — usually reference the cross-service registry).
  - **Evidence**: grep hand-written (non-test, non-`.g.*`) source for code-shaped literals as comparison / case / lookup operands — `case\s+"[A-Z]{2,}_`, `==\s*"[A-Z]{2,}_[A-Z0-9_]+"`, `"[A-Z]{2,}_[A-Z0-9_]+"\s*==`, `is\s+"[A-Z]{2,}_`. Per hit in production code where a generated constant exists = FINDING.
  - **Why**: a hand-typed code literal in a `switch` / `==` is a second source of truth. When the spec renames / removes a code, the generated-constant change is a COMPILE error at every reference (caught immediately) — but a raw literal silently keeps comparing against the dead value (the branch goes dead, no diagnostic).
  - **How**: reference the generated constant — `case KeyCustodianErrorCodes.KEYCUSTODIAN_X:` (C# permits `const string` case labels). Cross-ref §26.6, §26.7, §1.18.
  - *Provenance: deliverable 0026 sub-step 4a — codified alongside the handler-alias retrofit; the sweep found zero existing production violations, so the rule gates the new sign-handler deny-telemetry switch + future consumers.*
