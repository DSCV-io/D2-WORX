# PARITY.md — Cross-Language Parity Tracking

> **Audience**: engineers introducing a new shared abstraction, wire-format type, or constant catalog that must exist in multiple language runtimes — and engineers auditing cross-language consistency.
>
> Template + justification framework for any cross-language additions in D²-WORX.
>
> Backend is **.NET only** (the SvelteKit BFF is the only non-.NET surface). This doc is the cross-language parity template — populated as cross-language components ship.

---

## When Cross-Language Parity Matters

Parity tracking applies when the SAME concept must exist in MULTIPLE languages. Examples:

- A shared abstraction (D2Result, BaseHandler) implemented in both C# and TypeScript
- A wire-format type generated in multiple languages from the same proto
- A test matcher pattern duplicated in xUnit + Vitest
- A naming convention enforced consistently across languages

When a concept lives in ONE language only, parity isn't a concern — it's exclusive.

---

## "Why Exclusive?" Framework

Before adding a cross-language component, justify why it must be cross-language. Single-language exclusivity is the default; parity is the exception.

For each entry in the parity table, the **Why exclusive?** column documents the reason if a counterpart in another language is intentionally absent. Acceptable reasons:

| Reason                                 | Example                                                                                                                                                                 |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Language has built-in equivalent**   | `Microsoft.Extensions.DependencyInjection` is built into .NET — no D2-specific DI container needed                                                                      |
| **Single-language consumer surface**   | If only the SvelteKit BFF needs a primitive, it lives in TS only                                                                                                        |
| **Different ergonomic ceiling**        | Some patterns (e.g., reflection-driven `[RedactData]`) work better in one language than the other; the other can use a different approach (per-handler `RedactionSpec`) |
| **Single-language runtime constraint** | Python-only ML library, JVM-only compliance toolkit                                                                                                                     |
| **Frozen — out of parity scope**       | Component is OUT OF SCOPE for cross-language parity (no porting expected)                                                                                               |

Unacceptable "exclusive" reasons (= force parity instead):

- "Nobody asked for the other one yet" — if both languages have the same problem, both should have the same solution
- "Implementation cost" — parity reduces long-term cost; exclusivity adds it
- "We already have one, adding another would be inconsistent" — circular reasoning; the inconsistency IS the parity gap

## Utility helper naming divergence — TS `*Undef*` vs .NET `*Null*`

The `@d2/utilities` TS package and `D2.Shared.Utilities.Extensions` .NET package provide
identical boundary-helper behavior but use different absent-value tokens and function-name
suffixes per language convention:

| TS (`@d2/utilities`)              | .NET (`D2.Shared.Utilities.Extensions`) | Return on absent               |
| --------------------------------- | --------------------------------------- | ------------------------------ |
| `toUndefIfEmpty(s)`               | `ToNullIfEmpty()` on string             | TS: `undefined` / .NET: `null` |
| `tryParseTruthyUndefUuid(s)`      | `TryParseTruthyNull(out Guid? r)`       | TS: `undefined` / .NET: `null` |
| `tryParseTruthyUndefInt(s)`       | `TryParseTruthyNull(out int? r)`        | TS: `undefined` / .NET: `null` |
| `tryParseTruthyUndefEnum(obj, s)` | `TryParseTruthyNull<TEnum>(out var r)`  | TS: `undefined` / .NET: `null` |

**Rationale**: TypeScript's native absent-value is `undefined` (rules.md §6.15 — prefer
`undefined` for absent semantics everywhere in TS, never `null`). C# convention uses `null`
for nullable reference/value types. The divergence is intentional and permanent — behavior
is functionally equivalent on the helpers' input domain (same input → same absent/present
semantic), only the absent sentinel and function-name suffix differ.

Cross-language reviewers reading both sides should expect `*Undef*` names in TS returning
`undefined`, and `*Null*` names in the corresponding .NET methods returning `null` — same
semantics, different sentinel per language convention. Per-language adversarial test
coverage lives in `server/shared/typescript/utilities/tests/{parse,strings,clean,falsey}.test.ts`
and `server/shared/dotnet/utilities/Tests/D2.Shared.Tests.Unit.Utilities.*`. No drift — this
is the designed API surface.

## Process

When adding a cross-language component:

1. **Identify the concept** — what abstraction is being shared?
2. **Identify the consumers** — which languages have the same problem?
3. **Justify exclusivity** for any language NOT in the implementation set (using the framework above)
4. **Add a row** to the parity table above (or create a new table for the component category)
5. **Document the API contract** in shared docs — both implementations must match
6. **Verify drift** during audit rounds (per [`docs/dev/rules.md §9`](dev/rules/09-architectural-layer-hygiene.md#9-architectural-layer-hygiene) cross-language drift predicate)

---

## Anti-Patterns

- **Implementing in language A, "porting later"** — if the other language needs it, port now or document why not
- **Diverging APIs across languages** — if D2Result has a `BubbleFail` method in .NET, it has the same method in TS (with adjusted naming convention)
- **Implementing twice with subtle differences** — one of them WILL drift. Either share via codegen or document divergences explicitly.
- **Not tracking parity at all** — over time, drift accumulates silently. The table is the source of truth.

## Parity test infrastructure

Cross-language parity for spec-driven catalogs is enforced by a fixture-driven test pair: the .NET test suite emits canonical JSON fixtures to disk; a TS-side Vitest workspace reads those fixtures and asserts that the spec-emitted TypeScript decoders / encoders / catalogs agree byte-for-byte (after canonicalization).

**Architectural shape**

```
.NET test                                    TS Vitest test
[Trait("Category","ContractFixtures")]       (in @d2/contract-tests)
       |                                              ^
       v                                              |
  Emit fixture JSON                              Read fixture JSON
  to disk                                        from disk
       |                                              |
       └────────────► same path ◄────────────────────┘
            server/shared/typescript/contract-tests/
            fixtures/<catalog>/<scenario>.json
```

The fixture file is the meeting point. Fixtures are committed to git so PR diffs surface accidental drift. There is no subprocess, no JSON-RPC bridge, no live spawn-and-roundtrip — comparison is deterministic across two independent test runs (one per language). The one exception is the non-deterministic crypto fixtures (see **Non-deterministic crypto fixtures** under the CI hook below): the TS read-and-assert comparison stays deterministic (it reads the committed frame and decrypts it), but re-EMITTING those fixtures produces different bytes, so they are exempt from the emit-then-assert-no-drift check.

**Direction**: forward-only (`.NET → fixture → TS read+assert`). Bidirectional cross-language assertion (TS-emit → .NET-read) is intentionally OUT OF SCOPE for this test surface.

**Invocation**

```bash
# 1. Regenerate fixtures from the .NET side:
dotnet test server/D2.slnx -- --filter-trait "Category=ContractFixtures"

# 2. Run the TS parity assertions:
pnpm test:contracts        # from repo root
```

**CI hook**

`.github/workflows/test.yml` runs an active `contract-fixtures-emit` job that regenerates fixtures via `dotnet test … --filter-trait "Category=ContractFixtures"` and asserts no drift with an untracked-aware `git status --porcelain` emptiness check over `server/shared/typescript/contract-tests/fixtures/` (tracked modifications, untracked new files, and deletions all fail the lane). TS parity assertions run inside the `ts-shared-unit-tests` lane via `@d2/contract-tests` against the same committed fixtures. Locally, `pnpm test:contracts` is the composite of emit + TS assert.

**Non-deterministic crypto fixtures — drift-check carve-out (per scenario).** Three committed fixtures are non-deterministic by cryptographic design (a fresh recipient keypair / ephemeral / GCM nonce per emit): the `mq-messages-golden/sealed-audit-message` scenario (`MqGoldenMessageFixtureEmitter`) and the two `TsCryptoInterop` manifests (`sealed-frames.manifest.fixture.json` / `symmetric-frames.manifest.fixture.json`, emitted by the `@d2/encryption` `scripts/emit-*-frames.fixture.ts` scripts). Re-emitting them yields a different `bodyBase64` / `frameHex` even with no code change. Correctness is proven functionally (the consumer opens / decrypts the committed frame and compares plaintext); the byte-exact gate is delegated to the deterministic `symmetric-crypto-kat` / `sealed-crypto-kat` known-answer fixtures (pinned key + nonce + ephemeral, byte-reproduced). The CI drift check stays green for distinct per-scenario reasons: the `sealed-audit-message` golden is emit-only-when-absent (see next paragraph); the TsCryptoInterop manifests are produced by separate pnpm emit scripts that the CI job does **not** invoke — so those files are not rewritten during the lane.

**`mq-messages-golden/sealed-audit-message` — emit-only-when-absent gate.** Unlike the two `TsCryptoInterop` manifests (which are emitted by an explicit `pnpm` script), the `sealed-audit-message` golden is written by `MqGoldenMessageFixtureEmitter.Emit_SealedAuditMessage`, which runs as part of `dotnet test … --filter-trait "Category=ContractFixtures"`. Because re-emitting yields a different `bodyBase64` (fresh ECDH ephemeral per seal), the file would churn on every test run. The emitter therefore writes the file ONLY when it does not already exist, or when the environment variable `D2_REGEN_GOLDENS` is set (any non-empty value, e.g. `D2_REGEN_GOLDENS=1`). Normal test runs skip the write and leave the committed bytes unchanged. To deliberately refresh the golden (after a wire-format or payload change), delete the file or set `D2_REGEN_GOLDENS=1` and re-run the `ContractFixtures` category; then verify the TS parity suite still passes (`pnpm test:contracts`) before committing the new bytes.

**Adding a catalog**

1. Pick a synthetic-data scenario set (every fixture uses synthetic IDs / RFC 5737 IPs / `*.invalid` emails — no real PII).
2. Add a `<catalog>FixtureEmitter.cs` under `server/shared/dotnet/tests/Integration/ContractFixtures/` with one `[Fact, Trait("Category","ContractFixtures")]` per scenario; write via `FixturePathHelpers.WriteFixture`.
3. Add a `<catalog>.parity.test.ts` under `server/shared/typescript/contract-tests/tests/` that loads each scenario via `loadFixture` and asserts per-VALUE / per-PROPERTY equality.
4. Update the parent `server/shared/typescript/README.md` Mermaid graph + this doc's catalog list.
