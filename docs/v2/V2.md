## 1. Context & Scope

D2-WORX v1 was a polyglot system: .NET (Geo, Gateway, SignalR) + Node.js (Auth, Comms, Files) + SvelteKit (web). It accumulated ~5 ingress points, 3 layers of cross-cutting middleware duplicated per service, parity-driven shared abstractions on both sides, and an architecture that made adding new services costly.

**v2 (`nova` branch) is a structural rewrite**, not a refactor:

- **Backend collapses to .NET only.** Every Node.js service is rewritten in .NET. SvelteKit is the only remaining Node footprint (it's the trusted web client).
- **A unified Edge service** absorbs today's Gateway + SignalR + Auth + WhoIs + cross-cutting middleware into one process.
- **Geo decomposes** into shared libraries (no Geo service exists in v2).
- **Comms splits** into D2.Courier (outbound delivery) + D2.Notifications (in-app feed). D2.Threads is a future deferred concern.
- **D2.Audit** is added as a separate service for tamper-evident audit logging.
- **Files port** from Node.js to .NET, with SeaweedFS replacing MinIO for object storage.

**Scope of this document:** the architectural target, all settled decisions, the project structure, the patterns that govern new code, the versioning policy, the testing strategy, and the implementation sequence.

**What this document is NOT:** an active progress tracker, a sprint plan, or a feature roadmap. Those concerns are out of scope.

### Key structural decisions

- **`server/` (singular)** — only one trusted-code language now (.NET); SvelteKit goes here because it has a backend half. Plural `backends/` was honest when we had .NET + Node.js services; singular is honest now.
- **`server/services/{service}/{layer}/`** — drop the redundant `{Service}.{Layer}/` folder name. Folder is `app/`, csproj is `D2.{Service}.App.csproj`. Saves 1 folder level.
- **`server/services/{service}/clients/{language}/`** — forward-proofs polyglot consumers. Edge has no `clients/` (entry point); Files / Courier / Notifications / Audit have `clients/dotnet/` for their .NET client libs. Adding a future `clients/typescript/` is just dropping a folder in.
- **`server/shared/dotnet/{lib}/`** — drop the `Implementations/Caching/Distributed/` nesting. Was: `shared/Implementations/Caching/Distributed/DistributedCache.Redis/`. Now: `shared/dotnet/caching-distributed-redis/`. **Saves 3 folder levels.**
- **`server/shared/typescript/`** — exists with just a README initially. When the first cross-language pattern (e.g., a Result type or Handler shape mirror) needs to be shared with future TS web clients, packages land here. No pnpm workspace until then.
- **`infra/`** — consolidates `/docker/`, `/docker-compose*.yml`, `/observability/` from v1. Repo root no longer has compose files.
- **`docs/`** — non-essential `.md` files move out of root. Only README, CLAUDE, CHANGELOG, CONTRIBUTING, LICENSE, V2 stay at root.
- **All .NET configs in `server/`** — `Directory.Build.props`, `Directory.Packages.props`, `global.json`, `NuGet.config`, `stylecop.json`, `D2.slnx` all live under `server/` (they cascade downward to all `.csproj`). Repo root stays clean.
- **No more pnpm workspace at root** — SvelteKit is the only Node project; it's standalone with its own `package.json` at `server/web/`. Workspace returns when there's a real second TS package.

### Folder casing convention (lowercase outer + PascalCase inner)

Apply consistently across the whole repo:

- **Folders OUTSIDE a project** (csproj-grouping, organizational) → **lowercase**, kebab-case for multi-word
  - Examples: `server/`, `services/`, `edge/`, `app/`, `clients/`, `dotnet/`, `caching-distributed-redis/`, `geo-reference/`, `service-defaults/`, `infra/`, `tools/`, `docs/`
- **Folders INSIDE a project** (namespace-mapping, where Rider auto-creates folders from namespace operations) → **PascalCase**
  - Examples (inside `server/services/edge/app/`): `Application/`, `Handlers/`, `Commands/`, `Queries/`, `Observability/`, `Infrastructure/`, `Persistence/`, `Vault/`, `Configuration/`
- **`.cs` file names** → **PascalCase** (matches the type they contain — one-class-per-file convention)
- **`.csproj` file names** → **PascalCase**, dot-separated (`D2.Shared.Handler.csproj`) — the csproj filename IS the assembly name; appears in error messages, logs, telemetry
- **Namespaces and type names** → **PascalCase** (C# language convention)

The rule: **if Rider auto-generates a folder from a namespace operation, that folder must be PascalCase. Anything else is lowercase.**

Why this works:

- The C# compiler doesn't read folder names; namespaces are declared at the top of files independently
- Cross-platform safety (Linux/macOS are case-sensitive; lowercase removes a class of "works on my machine" bugs)
- Visual consistency at the top level with non-.NET parts (`contracts/`, `infra/`, `tools/`)
- Inner project folders that DO map to namespaces stay PascalCase, so Rider's "Add Class" / "Move to namespace" operations work without friction

Minor friction: `dotnet new` defaults to PascalCase folders. Workaround: `mkdir handler && cd handler && dotnet new classlib -n D2.Shared.Handler` (folder name and csproj name decoupled). Could codify in the Makefile (`make new-lib name=Handler` does the right thing).

### What's gone vs v1

- ❌ `d2-gateway` (.NET REST facade) — endpoints absorbed into Edge
- ❌ `d2-signalr` (.NET SignalR gateway) — hubs absorbed into Edge
- ❌ `d2-auth` (Node.js + BetterAuth) — replaced by Auth module inside Edge, self-rolled .NET
- ❌ `d2-geo` (.NET Geo service) — reference data → embedded library, WhoIs → Edge module, Contacts → folded owned-component library (see ADR-0001)
- ❌ `d2-comms` (Node.js) — replaced by D2.Courier + D2.Notifications
- ❌ Per-service rate-limit / fingerprint / JWT / idempotency / CORS middleware (5× duplication today)
- ❌ "Contacts service" as originally envisioned — replaced by contacts folded into each consuming service's own entities via `D2.Shared.Contacts` (see §5.6 Revised / ADR-0001; the earlier per-consuming-service-DB plan is superseded)

**Net container count change**: today's `gateway + signalr + auth + geo + files + comms + sveltekit + dkron-mgr` → tomorrow's `edge + files + courier + notifications + audit + sveltekit + dkron-mgr`. Net **−1** application container, but with a vastly cleaner boundary set.

## 4. Phasing

Build order is bottom-up: foundational shared libraries first, then domain-specific shared libraries, then services in dependency order (Edge before its consumers; Audit before Comms because Comms publishes audit events; Comms before Files because Files publishes notification events; SvelteKit last because it consumes everything).

Everything in v2 is built fresh from scratch (using `/old/v1/` as reference) — no extracting, no porting, no in-place modifying. The wipe deletes v1 entirely; phases below build the v2 implementation from a clean slate.

## 5. Stack Decisions

### 5.1 Backend Language & Orchestration

- **Language**: .NET 10 (C# 14) for all backend services. SvelteKit is the only Node footprint.
- **Orchestration**: Docker Swarm + Portainer in production until the business is making the kind of money that warrants scaling past ~3 machines. K8s is explicit overkill at this scale.
- **HTTP/REST**: ASP.NET Core 10 minimal APIs.
- **gRPC**: Built-in `Grpc.AspNetCore` for inter-service communication.
- **EF Core 10** with `Npgsql.EntityFrameworkCore.PostgreSQL` for persistence.
- **Async**: RabbitMQ via `RabbitMQ.Client` 7.x (low-level, no MassTransit).
- **Sync inter-service**: gRPC (HTTP/2) — default for everything internal.

#### gRPC contract documentation (parallel to OpenAPI on the HTTP side)

Internal gRPC services get the SAME first-class contract documentation that Edge endpoints get via OpenAPI. The proto file is the spec; runtime enforcement reads from the same spec.

**Layer 1: Structured comments on every service / RPC / message** (zero tooling cost, immediate value for code review)

```proto
service FilesService {
  // Uploads a new file to the user's account.
  //
  // Authorization: caller must have scope `files.upload.write`.
  // Risk tier: Standard (see §5.3).
  // Idempotency: not idempotent (each call creates a new file).
  // Side effects:
  //   - Writes object to SeaweedFS
  //   - Publishes file.uploaded event on `files.events` exchange
  //   - Updates user storage quota
  // Errors:
  //   - PermissionDenied: caller lacks required scope
  //   - ResourceExhausted: storage quota exceeded
  //   - InvalidArgument: file metadata fails validation
  rpc UploadFile(UploadFileRequest) returns (UploadFileResponse);
}
```

**Layer 2: Custom proto options for machine-readable contract metadata**

`contracts/protos/d2/options.proto`:

```proto
syntax = "proto3";
package d2.options;

import "google/protobuf/descriptor.proto";

option csharp_namespace = "D2.Protos.Options";

extend google.protobuf.MethodOptions {
  // OAuth-style scope(s) required to call this RPC. Multiple = AND.
  repeated string required_scope = 50000;

  // Operation Risk Tier — drives auth requirements, rate limit caps, risk thresholds,
  // impersonation default, audit verbosity, fail-open vs fail-closed.
  // Values: "Public", "Standard", "Elevated", "Critical". See §5.3.
  string risk_tier = 50001;

  // Whether this RPC is safe to retry without side effects.
  bool idempotent = 50002;

  // Override impersonation default for this RPC.
  // Per §5.3, Elevated tier defaults to blocking impersonation but can opt-in to allow;
  // Critical tier always blocks (no opt-in). Standard tier defaults to allow.
  // Set this only when the tier's default doesn't fit.
  optional bool impersonation_allowed = 50003;
}
```

Used in service definitions:

```proto
import "d2/options.proto";

service FilesService {
  rpc UploadFile(UploadFileRequest) returns (UploadFileResponse) {
    option (d2.options.required_scope) = "files.upload.write";
    option (d2.options.risk_tier) = "Standard";
    option (d2.options.idempotent) = false;
  }

  rpc DeleteFile(DeleteFileRequest) returns (DeleteFileResponse) {
    option (d2.options.required_scope) = "files.upload.delete";
    option (d2.options.risk_tier) = "Elevated";  // destructive — defaults to blocking impersonation
    option (d2.options.idempotent) = true;
  }
}
```

**Layer 3: Runtime enforcement via gRPC interceptor**

A startup-time scan reads the options from generated method descriptors; a server interceptor enforces them at request time:

```csharp
public sealed class GrpcContractMetadataProvider
{
    // At startup, walks all registered services, reads (d2.options.*) per method,
    // caches a methodFullName → ContractMetadata lookup.
}

public sealed class GrpcContractEnforcementInterceptor(GrpcContractMetadataProvider metadata) : Interceptor
{
    public override async Task<TResponse> UnaryServerHandler<TRequest, TResponse>(
        TRequest request, ServerCallContext context, UnaryServerMethod<TRequest, TResponse> continuation)
    {
        var contract = metadata.Get(context.Method);
        if (contract is null) return await continuation(request, context);

        var userScopes = context.GetHttpContext().User.GetScopes();
        foreach (var required in contract.RequiredScopes)
            if (!userScopes.Contains(required))
                throw new RpcException(new Status(StatusCode.PermissionDenied, $"Required scope: {required}"));

        if (!contract.ImpersonationAllowed && context.GetHttpContext().User.HasClaim(c => c.Type == "act"))
            throw new RpcException(new Status(StatusCode.PermissionDenied, "Not callable during impersonation."));

        return await continuation(request, context);
    }
}
```

**Same proto option drives both the doc AND the auth check.** Drift is impossible because they read from the same source.

**Layer 4: Generated documentation via `protoc-gen-doc`**

[`protoc-gen-doc`](https://github.com/pseudomuto/protoc-gen-doc) (works with Buf — already in our toolchain) emits Markdown/HTML from proto files. Both the structured comments AND the custom options render. Output committed to `docs/api/grpc/` (or served as a static site).

**Layer 5: gRPC reflection in non-prod environments**

```csharp
if (env.IsDevelopment() || env.IsStaging())
{
    builder.Services.AddGrpcReflection();
    // ...
    app.MapGrpcReflectionService();
}
```

Lets devs use `grpcurl`, Postman, BloomRPC for ad-hoc service introspection. Trivial to add.

**One-time setup cost**: ~1-2 days to scaffold (define `options.proto`, wire `protoc-gen-doc`, build the metadata provider + interceptor, document the convention). Per-RPC cost after: just add the option lines inline. Pays for itself the first time a code review uses the proto contract to verify the implementation.

#### Request enrichment for gRPC paths

Identity (JWT validation) and request context propagation work the same way for gRPC as for HTTP because gRPC runs over HTTP/2 in ASP.NET Core — same auth pipeline, same `HttpContext`. Specifically:

- **JWT validation**: ASP.NET Core's standard JWT bearer middleware (`AddAuthentication().AddJwtBearer(...)`) runs before the gRPC handler dispatch and populates `HttpContext.User`. The gRPC contract enforcement interceptor reads it via `context.GetHttpContext().User`.
- **Cross-cutting context** (request id, fingerprints, WhoIs hash, etc.): propagated via gRPC metadata key-value pairs (the gRPC equivalent of HTTP headers). Edge injects `traceparent` / `tracestate` / `x-d2-context` on outbound gRPC calls; backend services read them via a server interceptor that decodes the propagated envelope into the request-scoped `IRequestContext`. Same wire names as the HTTP headers — the `D2.Shared.Headers.Common` / `D2.Shared.Headers.Grpc` catalogs are spec-driven from `contracts/headers/headers.spec.json` so cross-transport entries appear at identical wire values.
- **Request enrichment middleware**: HTTP middleware runs in the standard ASP.NET pipeline before gRPC handler dispatch. For services that are gRPC-only (no HTTP endpoints), the gRPC server interceptor is the entry point that runs the equivalent enrichment logic.

In short: the same identity + enrichment plumbing works for both transports. Backend service handlers (HTTP or gRPC) see the same `IRequestContext` API regardless of how the request arrived.

### 5.2 Edge — Unified Gateway

The Edge is one .NET process bundling:

- **Reverse proxy**: `Yarp.ReverseProxy` 2.3+ for HTTP routing to backend services. YARP IS the load balancer for backends.
- **Self-rolled Auth** — no framework wrapper. `Microsoft.IdentityModel.Tokens` + `IDataProtectionProvider` + `AuthorizationPolicyBuilder` + `Microsoft.AspNetCore.RateLimiting` + `Antiforgery` + `IHostedService` are framework primitives, not framework flow control. We compose. **No** IdentityServer, OpenIddict-as-framework, or ASP.NET Identity-as-framework.
- **SignalR hubs** for real-time push.
- **In-process WhoIs lookup** via existing IPinfo HTTP client.
- **All cross-cutting middleware** (rate limit, request enrichment, JWT validation, idempotency, fingerprint, CSRF, CORS) in one place.

**Production topology**:

- **Early**: single Edge instance behind Cloudflare (DNS, TLS, WAF).
- **HA**: multiple Edge instances behind a Layer 7 LB (Cloudflare candidate). L7 because Edge is stateful via WS connections. Backplane for cross-instance push via Redis.

**Why bundle vs split**: Edge is the only place that needs to know about both HTTP request handling AND WebSocket connection state for the same user session. Splitting them duplicates session lookup. Bundling them means session state lookup happens once per request.

#### OpenAPI documentation (per-version, transformer-extensible)

Edge uses **`Microsoft.AspNetCore.OpenApi`** (the built-in MS library introduced in .NET 9, hardened in .NET 10 — replaces Swashbuckle) combined with **`Asp.Versioning.OpenApi`** to produce **one OpenAPI document per API version**: `/openapi/v1.json`, `/openapi/v2.json`, etc.

Auto-discovers every minimal API endpoint, extracts request/response shapes from C# types, infers HTTP methods + paths, reads XML doc comments + attributes (`[Authorize]`, `[Tags]`, `[EndpointSummary]`, `[ProducesResponseType]`, etc.).

**Custom Operation Transformers** surface our domain-specific metadata into the OpenAPI document — same pattern as the gRPC custom proto options:

```csharp
[AttributeUsage(AttributeTargets.Method)]
public sealed class RequireScopeAttribute(params string[] scopes) : Attribute
{
    public string[] Scopes { get; } = scopes;
}

// Endpoint usage:
app.MapPost("/api/v1/files/upload", UploadHandler)
   .RequireAuthorization()
   .WithMetadata(new RequireScopeAttribute("files.upload.write"));

// Operation transformer (registered once at startup):
public class RequireScopeOperationTransformer : IOpenApiOperationTransformer
{
    public Task TransformAsync(
        OpenApiOperation operation,
        OpenApiOperationTransformerContext context,
        CancellationToken ct)
    {
        var scopes = context.Description.ActionDescriptor.EndpointMetadata
            .OfType<RequireScopeAttribute>()
            .SelectMany(a => a.Scopes)
            .Distinct()
            .ToArray();

        if (scopes.Length > 0)
        {
            operation.Extensions["x-required-scopes"] = new OpenApiArray
            {
                Items = scopes.Select(s => (IOpenApiAny)new OpenApiString(s)).ToList(),
            };
            operation.Description = $"**Required scopes**: `{string.Join("`, `", scopes)}`\n\n{operation.Description}";
        }

        return Task.CompletedTask;
    }
}

// Register at startup:
builder.Services.AddOpenApi(options =>
{
    options.AddOperationTransformer<RequireScopeOperationTransformer>();
});
```

**Same pattern applies to** `[OperationRiskTier]` (see §5.3), `[Deprecated]`, and any future cross-cutting attribute — one attribute + one transformer per concern.

**Doc UI**: [Scalar](https://github.com/scalar/scalar) (`Scalar.AspNetCore` package) — modern Swagger UI replacement. Mounts at `/docs/v1`, `/docs/v2`, etc. Renders `x-*` extensions natively. Looks good out of the box.

**Same conceptual pattern as gRPC contracts** — single source of truth (attribute on endpoint = proto option on RPC), runtime enforcement reads the same metadata, generated docs always accurate. Drift impossible.

### 5.3 Operation Risk Tier (cross-cutting)

A single attribute on every endpoint or RPC drives multiple subsystems: auth requirement, rate-limit cap, risk-score thresholds, impersonation default, audit verbosity, fail-open vs fail-closed behavior. Pick a tier per endpoint, everything else follows.

**The single question** the developer answers when choosing a tier: _"What's the blast radius if this endpoint is abused?"_ No other axis. Auth-required is captured by the tier (Public = no auth; everything else = auth required); op type (read vs write) is captured by HTTP method or RPC name.

#### Four tiers, one axis

| Tier         | Meaning — answer to "what's the blast radius if abused?"                                                                  | Example endpoints                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Public**   | None or negligible. Reading public data, health checks. **Auth not required.**                                            | `GET /health`, `GET /api/v1/public/*`                                                                                                                          |
| **Standard** | Low. Standard authenticated read/write of user's own data.                                                                | `GET /api/v1/users/me`, `GET /api/v1/files/{id}`, `POST /api/v1/files` (regular upload)                                                                        |
| **Elevated** | Medium. Affects user account integrity, modifies auth-relevant state, or exposes PII beyond the user's own basic profile. | `POST /api/v1/account/email`, `POST /api/v1/account/password`, `GET /api/v1/billing/history`, `GET /api/v1/account/sessions`, `POST /api/v1/account/mfa/setup` |
| **Critical** | Maximum. Irreversible, financial, or admin-org-only actions.                                                              | `POST /api/v1/billing/charge`, `DELETE /api/v1/orgs/{id}`, `POST /api/v1/admin/users/{id}/ban`, force-impersonation initiation                                 |

#### Per-tier defaults

| Tier         | Auth required? | Rate-limit per-FP cap                                       | Risk thresholds (step-up / block) | Impersonation default                                                                  | Audit verbosity                          | Fail behavior on Redis outage |
| ------------ | -------------- | ----------------------------------------------------------- | --------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------- | ----------------------------- |
| **Public**   | No             | None (relies on per-IP / per-city / per-country dimensions) | n/a (no session)                  | n/a                                                                                    | Low (sample 1%)                          | Fail open                     |
| **Standard** | Yes            | 100/min                                                     | 50 / 80                           | Allow                                                                                  | Medium (every write)                     | Fail open                     |
| **Elevated** | Yes            | 30/min                                                      | 30 / 60                           | **Block by default** (must explicitly opt in via `[ImpersonationAllowed]` to override) | High (every event)                       | **Fail closed**               |
| **Critical** | Yes            | 10/min                                                      | 20 / 40                           | **Always blocked** (no opt-in)                                                         | Maximum (every event + payload metadata) | **Fail closed**               |

**HTTP (Edge minimal API endpoints)**:

   .WithMetadata(new RequireScopeAttribute("auth.user.email.change"));

**gRPC (proto file)**:

#### Per-endpoint overrides

The tier sets sensible defaults; specific endpoints can override individual dimensions when warranted. Dominant case: **brute-force-targeted Public endpoints** (sign-in, password reset, OTP verification) are `Public` tier (must be callable without auth) but need a tighter per-IP rate limit than the default.

```csharp
app.MapPost("/api/v1/auth/sign-in", SignInHandler)
   .WithMetadata(new OperationRiskTierAttribute(OperationRiskTier.Public))
   .WithMetadata(new RateLimitOverrideAttribute(maxPerMinute: 5, dimension: RateLimitDimension.IP));  // tighter than Public default
```

The TIER says "no auth needed, low blast radius." The OVERRIDE says "but cap brute-force attempts at 5/min/IP." Two orthogonal concepts, two attributes.

#### How user/org Security Policy interacts with tiers

The user/org `Security Policy` framework (see §5.4) **monotonically tightens** the per-tier defaults. A user on a "Strict" personal policy might have step-up at 30 instead of 50 for `Standard` endpoints. The tier sets the baseline; the policy adjusts it for the specific user — same monotonic-stricter rule we already have.

**Policies can never loosen** the per-tier defaults. A `Critical` endpoint always blocks impersonation; no policy can change that.

#### Where this is referenced

- **§5.2 Edge — OpenAPI subsection**: surfaces `risk_tier` per endpoint via Operation Transformer
- **§5.1 gRPC contract documentation**: surfaces `risk_tier` proto option in generated docs and runtime interceptor
- **§5.4 Auth & Security**: tier drives auth requirements, impersonation defaults, OTP step-up thresholds
- **§5.5 Real-Time / Rate Limiting**: tier drives per-FP rate limit caps, fail-open vs fail-closed behavior

The single declaration on each endpoint becomes the source of truth — every middleware reads from it; documentation auto-surfaces it; PR review verifies the implementation matches the declared tier.

### 5.4 Auth & Security

#### Auth as a module within Edge (with its own DB)

Edge is a service; **Auth is a module within Edge**. Despite living in the same process, the Auth module owns a complete, isolated database — `auth_db` — for clean separation of concerns. Other Edge modules (SignalR push, WhoIs, YARP routing, cross-cutting middleware) do not access `auth_db` directly; they go through the Auth module's internal interfaces.

**`auth_db` schema (owned tables)**:

- `user`, `org`, `member`, `invitation` — identity model (replaces v1 BetterAuth tables)
- `account` — linked external auth providers (Google, etc.)
- `session` — durable session storage (also dual-written to Redis cache; see Sessions below)
- `oauth_client` — OAuth client registry for service-identity grants (per "Service Identity" below)
- `impersonation_consent` — per-(user, granting-org) consent grants for support impersonation
- `sign_in_event` — every sign-in attempt with risk score, IP, fingerprint, country, etc. **Lives in `auth_db`** (not `audit_db`) because it's queried at sign-in time for risk scoring ("does this user usually sign in from this country / IP / fingerprint?"). Audit events for sign-ins are ALSO published to `d2.audit.events` for the central audit trail; both stores have the data, with different access patterns.
- `security_policy_org`, `security_policy_user` — per-org and per-user policy framework (see "Security Policy framework" below)
- `verification` — short-lived email/OTP verification tokens
<!-- ADR-0016 supersedes: KC tables removed from auth_db. KeyCustodian owns `keycustodian_db` (see §5.4 "Key Custodian" below). -->

#### Sessions (3-tier)

- **Cookie cache** (5min compact session info, signed via `IDataProtectionProvider`) for fast happy-path
- **Redis** for session lookup
- **`auth_db`'s `session` table** for durable storage (dual-write pattern: write Redis first for happy-path latency, then async-write to PG for durability; on cache miss, read PG and re-populate Redis)

Cookie is opaque (HttpOnly, Secure, SameSite=Lax) for browser. Mobile / CLI / B2B use bearer tokens.

> §3.8 + Q23. Implementation is Phase 3 Edge work — not in `D2.Shared.Auth` (the inbound runtime
> already supports the contract via the trinary `IRequestContext.IsAuthenticated`,
> `Scopes.AllAnonymousScopes`, and `Scopes.IsAnonymous`).

Edge mints a short-lived anon-session JWT for every unauthenticated visitor — every request
reaching a backend service carries a validated JWT (anon or user). The anon JWT carries
`d2_kind: "anonymous"`, an `anon:<uuid>` `sub` mapped 1:1 to a 3-tier session via the cookie,
and tamper-evident enrichment claims (`d2_whois_id`, optional `d2_fingerprint_score`).
Sign-in elevates the same session to a user JWT (same cookie, same `d2_session_id`); sign-out
mints a fresh anon-session for continuity (cookie-presence stops being a frontend-side auth
signal — `IRequestContext.IsAuthenticated` is the discriminator).

Implications for downstream design (full list in PHASE_0_AUTH.md §3.8):

- **Rate-limiting** keys collapse to JWT claims — see
  [`docs/v2/PHASE_3_RATE_LIMITING.md`](PHASE_3_RATE_LIMITING.md) §11 for the post-Pattern A bucket-keying.
- **CSRF gates** branch on `d2_kind: "anonymous"`, not cookie presence.
- **Audit propagation** distinguishes anon vs authed via `IsAuthenticated`.
- **Risk engine** keys historical-pattern signals on `d2_session_id` (longer-lived than the
  per-JWT `sub`).

#### Key Custodian (module within Edge, peer to Auth)

> **Design updated by ADR-0016 (2026-06-06).** KeyCustodian is a **peer module** to Auth inside Edge — not a sub-component of Auth. It owns its own database (`keycustodian_db`), independent of `auth_db`. The earlier framing ("runs inside Auth, reuses `auth_db`, no new DB") is superseded.

KeyCustodian owns the lifecycle of every long-lived secret in the system: JWKS signing keys, message payload encryption keys (per §5.7), cookie signing secrets, and service-identity OAuth `client_secret`s. **Not a separate service** — runs inside Edge as a peer module (same process, independent DB). Owns `keycustodian_db`; does not access `auth_db`.

**Key types under custody**:

| Key type                                                  | Owner             | Cadence      | Coordination required                                                                                |
| --------------------------------------------------------- | ----------------- | ------------ | ---------------------------------------------------------------------------------------------------- |
| Auth JWKS (RS256)                                         | KeyCustodian      | 90 days      | None — public key in JWKS endpoint, JWTs naturally expire 15min                                      |
| Message payload keys (AES-256-GCM, per encryption-domain) | KeyCustodian      | Quarterly    | High — N publishers + N consumers all need the keyring                                               |
| Cookie signing secret                                     | KeyCustodian      | 90 days      | Low — dual-secret window, sessions naturally expire                                                  |
| Service-identity OAuth `client_secret`                    | KeyCustodian      | 180 days     | Per-client, requires service restart                                                                 |
| Root key (encrypts all keys at rest in `keycustodian_db`) | Operator (manual) | 1-2 years    | Highest — full break-glass procedure documented in [`docs/v2/PHASE_0_AUTH.md`](PHASE_0_AUTH.md) §14a |
| Third-party API keys (Twilio, Resend, IPinfo)             | Operator (manual) | Per provider | Out of band — third party owns rotation                                                              |

**State machine** (per `kid` in `keycustodian_db.key_record`):

```
              ┌─────────┐
custodian ──→ │ pending │   (generated, not yet activated)
              └────┬────┘
                   ↓ activate (after T+1h smoke check)
              ┌─────────┐
              │ active  │   (encrypts new traffic; one per domain at a time)
              └────┬────┘
                   ↓ rotate (next active comes online)
              ┌─────────┐
              │retiring │   (still in keyring; decrypts in-flight; no new encrypts)
              └────┬────┘
                   ↓ retire (after grace window, default 7 days)
              ┌─────────┐
              │ retired │   (not in production keyring; only ops CLI loads on demand)
              └─────────┘

emergency  ──→ ┌────────────┐
               │compromised │  (terminal; cannot be promoted; production keyring excludes)
               └────────────┘
```

`compromised` is terminal: once marked, the kid cannot re-enter the active set. Production keyring excludes it. DB record kept indefinitely for forensic decryption.

**Distribution — pull-based, cached** (consumers use `D2.Shared.Auth`'s `KeyringClient`):

- On startup: fetch full keyring for relevant domains from Edge `internal/keys/{domain}` (gRPC, service-identity JWT required)
- Cache in memory; refresh hourly via TTL
- Subscribe to `d2.security.key-rotated` event on RabbitMQ → force refresh on receipt
- TTL fallback covers missed events
- No shared volumes, no file watching — works identically in Compose-dev, Compose-prod, and (future) Swarm

**Schedule**: daily cron (in Phase 8 dkron-mgr replacement; `IHostedService` cron in Edge before then) calls Edge's `internal/keys/check-rotations`. KeyCustodian inspects every domain's active kid age and:

- Age > rotation_cadence → generate new key (status: `pending`) → activate after T+1h smoke check → mark old as `retiring`
- Age in `retiring` > grace_window → mark old as `retired`
- Emit `d2.security.key-rotated` event for each transition (with `urgent=true` for emergency rotations)
- Audit-log every action to `d2.audit.events`

**Storage** (in `keycustodian_db` — per ADR-0016 §3 + §7):

- `key_record { kid PK, key_domain, key_type, key_material_encrypted, public_key_material, created_at, status, activated_at, retiring_at, retired_at, compromised_at, compromise_reason }` — flat non-polymorphic EF entity; `status` is a settable value column (NOT a TPH discriminator); pure mapper rehydrates sealed domain states
- `key_audit_record { id, kid FK, action, resulting_status, occurred_at }` — append-only operational log; written in the same transaction as the state change; no material, no free-text reason (per ADR-0016 §6)
- `key_material_encrypted` is the actual key material wrapped with the **root key** (via `D2.Shared.Encryption`)
- Retired and compromised keys stay in DB indefinitely; the production `KeyringClient` filters them out by status

**Bootstrap — root key**:

- KeyCustodian needs to decrypt `key_material_encrypted` on startup → needs the root key
- Root key lives at `secrets/keycustodian/root.key` (mounted into Edge container; read at startup; never logged; deny-ruled for Claude per §12)
- Pre-launch / Compose: bind-mounted file, gitignored, generated by `tools/scripts/gen-dev-keys.sh` for local dev
- Future Swarm: same library, same logical path — entrypoint script symlinks `/run/secrets/d2_root_key` → `secrets/keycustodian/root.key`
- Root-key rotation = decrypt all `key_record.key_material_encrypted` rows with old root, re-encrypt with new root, atomic transaction. Documented in [`docs/v2/PHASE_0_AUTH.md`](PHASE_0_AUTH.md) §14a. Rare (every 1-2 years), high-ceremony, manual.

**Compromise response — emergency rotation CLI**:

```bash
d2 keys rotate --domain audit --reason "leaked-via-jenkins-logs" --emergency
```

Flow:

1. Mark current active kid as `compromised` (terminal, immediate, audit-logged)
2. Generate + activate new kid (no smoke-test delay)
3. Force-emit `d2.security.key-rotated` with `urgent=true`
4. Consumers reload immediately on receipt; old key drops from active keyring
5. Background job scans last N days of audit events for messages encrypted with the compromised kid; flags for forensic review
6. Auto-generate incident report row in `audit_db.incident` with full timeline

For **JWT signing key compromise** (worst case): same flow + invalidate all active sessions (clear Redis session cache) + force global re-auth + emit `d2.security.signing-key-compromised`.

**Testing — required CI gate**: flagship integration test in `D2.Edge.Tests` (against Testcontainers PG + RMQ):

```
Given: 3 publishers + 3 consumers using audit domain, kid v1
When : KeyCustodian triggers rotation to v2
Then : new messages use v2 (verified by inspecting frame kid)
       in-flight v1 messages still decrypt (publish 100 pre-rotation, assert all consumed post-rotation)
       no message loss (counter check)
       audit trail records rotation event

Then : grace window expires
       v1 marked retired, removed from production keyring
       publishing with v1 fails with explicit error (no silent fallback)
       consuming a stale v1 message → DLQ + alert

Then : ops CLI fetches v1 from archive, decrypts stale message successfully
```

Plus emergency-rotation test, compromise-marking-is-terminal test, race-condition test (rotation while N replicas publishing). **No rotation tests = no merge** — see §8.

#### Internal token issuance — RFC 8693 OAuth Token Exchange

Edge implements [RFC 8693](https://datatracker.ietf.org/doc/html/rfc8693) as the single mechanism for producing every internal JWT. One `POST /oauth/token` endpoint covers boundary exchanges (cookie/external bearer → user JWT), downstream re-mints (narrowed scope/audience for backend → backend hops), impersonation (actor + subject), and service-identity tokens.

Wire shape:

```
POST /oauth/token HTTP/1.1
Host: edge.internal
Content-Type: application/x-www-form-urlencoded
Authorization: <caller authenticates here — see Service Identity below>

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<inbound token / session id / previous-hop JWT>
&subject_token_type=urn:ietf:params:oauth:token-type:<jwt | access_token | …>
&requested_token_type=urn:ietf:params:oauth:token-type:jwt
&audience=https://files.internal
&scope=files.upload.read
&actor_token=<optional — present for impersonation>
&actor_token_type=urn:ietf:params:oauth:token-type:jwt
```

**JWT shape**: RS256, ~5min TTL. JWKS served at the **OIDC-spec-canonical** `/.well-known/jwks.json`, with a discovery doc at `/.well-known/openid-configuration` pointing at it (off-the-shelf JWT libraries auto-discover via this path). Standard OAuth/OIDC claims (`sub`, `aud`, `iat`, `exp`, `azp`, `scope`, `act`) keep their canonical names; D²-specific claims are namespaced with the `d2_` prefix per CLAUDE.md §5 to avoid future spec collisions. Claims include `sub`, `aud`, `d2_org_id`, `d2_org_name`, `d2_org_type`, `d2_org_role`, `d2_session_id`, `d2_username`, `d2_fp`, `scope` (OAuth-canonical, space-separated string — see "Scope vs permission terminology" below), optional `act` (impersonation chain — see Impersonation). The full custom-claim catalog is the `JwtClaimTypes` static class in `D2.Shared.Auth.Abstractions`.

**Custom-claim namespacing**: any D2-specific claim (not defined by RFC 7519, OIDC, or RFC 8693) is prefixed with `d2_` to avoid future spec collisions. Example: `act["d2_kind"] = "consent"` instead of `act.kind`. The full custom-claim catalog is documented in `docs/JWT-CLAIMS.md` (created at Phase 3).

#### Scope vs permission terminology

**These are the same thing in our model.** JWT carries them as the OAuth-canonical `scope` claim (space-separated string). Code references them as constants in `D2.Shared.Auth.Scopes` (a static class with `const string` members). The string values match exactly.

We use **"scope"** as the primary term throughout V2 because:

- It's universal in OAuth/OIDC specs and tooling
- It's the name of the JWT claim
- Every off-the-shelf library and policy attribute speaks "scope"

"Permission" survives only in informal/conversational usage; in code and docs the term is "scope."

#### Service identity — Edge-issued via `client_credentials` (RFC 6749 §4.4)

Replace static `X-Api-Key` with the canonical OAuth 2.0 service-to-service pattern. Each backend service registered at Edge as an OAuth client with `client_id` + `client_secret`. On startup, exchange bootstrap credential at `/oauth/token` for a service identity JWT. Receivers validate against Edge's JWKS (same path as user JWTs).

Why: industry-standard pattern (Auth0 M2M, Okta Service Apps, Azure Service Principals, Google Service Accounts, AWS Cognito App Clients, Keycloak Service Accounts all do exactly this). Not patchwork — the textbook answer. Composes naturally with RFC 8693 (service uses its own identity token as the `Authorization` header on `/oauth/token` requests).

**Maturity ladder note**: this lands us at "rung 2" — central AS + `client_credentials`. Future upgrades (SPIFFE for bootstrap credentials, mTLS for transport) layer on top without rewriting.

#### Scope registry — code constants only

No DB catalog table, no admin UI for scope management. Scopes are static `const string` members in `D2.Shared.Auth.Scopes`. Naming convention: `service.resource.action` (three-part, lowercase, dot-separated):

```csharp
public static class Scopes
{
    public const string FilesUploadRead = "files.upload.read";
    public const string FilesUploadWrite = "files.upload.write";
    public const string OrgMemberInvite = "org.member.invite";
    public const string AuthUserImpersonate = "auth.user.impersonate";
    public const string AuthUserImpersonateForce = "auth.user.impersonate.force";
    // …
}
```

**Wildcards** supported only in role definitions (never in JWT scope claims): `files.*`, `files.upload.*`, `*`. Wildcard expansion happens at JWT mint time; backends only ever see exact strings.

**Roles**: hardcoded. Each `(role, org_type)` tuple resolves to an effective scope set computed at JWT mint time. Example: `Owner` in `customer` org type is scoped to own org; `Owner` in `admin` org type is `*`.

**JWT claim**: `scope` (space-separated, OAuth-canonical), not a `permissions` array.

Future: per-tenant custom roles in DB (deferred).

#### Impersonation only (no emulation)

Org emulation killed entirely. Replaced by purpose-built admin/staff dashboards. Only mechanism for staff/admin to access another user's data is **impersonation** — agent becomes the user via the RFC 8693 `act` chain.

**Two flavors**:
| Flavor | Who | Consent | Use case |
|---|---|---|---|
| **Consent-based** | Staff + Admin orgs (`auth.user.impersonate`) | Yes — OTP to user's email | Standard customer support |
| **Force** | Admin orgs only (`auth.user.impersonate.force`, granted only to mgmt + dev) | No — silent | Dev work, supporting users who can't complete the OTP flow |

**Critical actions blocked during impersonation** via scope narrowing at JWT mint time. Permissions marked with `[ImpersonationBlocked]` attribute are stripped from impersonation tokens:

```csharp
[ImpersonationBlocked]
public const string AuthUserPasswordChange = "auth.user.password.change";
[ImpersonationBlocked]
public const string AuthUserEmailChange = "auth.user.email.change";
[ImpersonationBlocked]
public const string AuthUserPhoneChange = "auth.user.phone.change";
[ImpersonationBlocked]
public const string BillingPaymentInitiate = "billing.payment.initiate";
```

Defense-in-depth: even a backend that forgot to add an extra check is safe because the scope literally doesn't include the permission.

**Time limits**: slider 15m / 30m / 1h / 2h, default 30m. For consent-based, the OTP authorizes a specific duration. For force, the JWT's `exp` is set directly.

**Concurrency**: no locks. Browser holds one opaque cookie → one active JWT, so an agent can only impersonate one user from a given browser session anyway. Multiple agents impersonating the same target user concurrently has no functional issue (audit records every action with the actor's identity).

**What the impersonated user experiences**:

- **Force**: silent at the time. Audit log visible later in their account activity.
- **Consent-based**: OTP request IS the notification.
- **No kick**: user's own session stays valid throughout.

**JWT shape for active impersonation**:

```json
{
  "sub": "user_bob_01HXYZ", // target user (impersonated)
  "d2_org_id": "org_acme", // Bob's org
  "d2_org_type": "customer",
  "d2_org_role": "owner",
  "scope": "files.upload.read …", // Bob's scope MINUS [ImpersonationBlocked] perms
  "act": {
    "sub": "agent_alice_01PQRS", // the impersonator (agent)
    "d2_kind": "consent", // or "force" — d2_ prefix per custom-claim namespacing
    "d2_session_id": "imp_01J…", // impersonation session id (distinct from user's session)
    "d2_org_id": "org_support_01ABC", // agent's own org (for audit + agent-keyed authz)
    "d2_org_name": "Customer Support",
    "d2_org_type": "support",
    "d2_org_role": "agent"
  },
  "exp": 1730001800
}
```

The `act` object carries the agent's own org context (`d2_org_id` / `d2_org_name` / `d2_org_type` / `d2_org_role`) so audit and authz logic can reason about the impersonator's home org without a separate DB lookup. Top-level `d2_org_*` claims represent the IMPERSONATED user's org (the "operating org"); `act.d2_org_*` represents the AGENT's own org.

#### Adaptive authentication (risk-based auth)

Two distinct concerns, designed independently:

##### Fingerprint binding — what identifies "same client"

Composite fingerprint with **10 sub-components** — 5 client-side (extended FingerprintJS-OSS), 5 server-side (computed at Edge from request itself). All device-stable signals; **no network-volatile signals (IP, ASN, geo) in binding** — those drive behavioral scoring separately.

**Wire format** (JWT `d2_fp` claim and `IRequestContext.SessionFingerprint`):

```
v{N}.c1.c2.c3.c4.c5.s1.s2.s3.s4.s5
```

Leading `v{N}` version token (currently `v1`) for forward-compat; followed by 10 dot-separated component hashes in fixed slot order. Each component hash is the first 16 hex chars of SHA-256 (64 bits — sufficient given each component's underlying signal entropy is far below 64 bits anyway; truncation isn't the bottleneck, signal entropy is).

**Slot order** (locked at v1):

| Slot | Layer  | Component                                                                       | Stability | Spoof resistance |
| ---- | ------ | ------------------------------------------------------------------------------- | --------- | ---------------- |
| `c1` | Client | FingerprintJS-OSS hash (canvas + WebGL + audio + base font + screen + timezone) | High      | Medium           |
| `c2` | Client | WebGL renderer hash (`WEBGL_debug_renderer_info`)                               | Very high | Medium           |
| `c3` | Client | Speech synthesis voices hash                                                    | Very high | Medium           |
| `c4` | Client | Media device kinds + counts                                                     | High      | Medium           |
| `c5` | Client | Extended font enumeration hash (~500 fonts)                                     | High      | Medium           |
| `s1` | Server | HTTP/2 SETTINGS frame hash                                                      | Very high | **Strong**       |
| `s2` | Server | Header order hash                                                               | Very high | **Strong**       |
| `s3` | Server | Sec-CH-UA Client Hints hash                                                     | Very high | Strong           |
| `s4` | Server | Accept-Encoding ordered list hash                                               | High      | Strong           |
| `s5` | Server | Accept-Language quality hash                                                    | High      | Strong           |

Adding a component (or changing slot meaning) requires bumping `v1` → `v2`; consumers that don't recognize the version skip component-level diff and treat the whole string as opaque (string equality only). Forward-compat without breaking changes.

**Estimated uniqueness**: ~97-98% (vs ~60-70% for bare FingerprintJS-OSS). Approaches commercial FingerprintJS Pro (~99.5%) without licensing cost.

**Server-side signals are unspoofable from a malicious JS environment** — even with stolen cookie + harvested client headers, an attacker can't replicate the actual TLS/HTTP library signatures of a real browser.

**Two fingerprints handlers see** (per request):

- **`IRequestContext.SessionFingerprint`** — the composite bound at JWT mint time (the `d2_fp` claim). Stable across all requests in a session. Propagated through AMQP for forensic continuity.
- **`IRequestContext.CurrentFingerprint`** — the same composite recomputed for THIS request by Edge fingerprint middleware. Per-request — does not propagate through AMQP.

**Risk scoring — component-by-component fingerprint diff feeds Edge's broader risk engine**:

Edge splits both fingerprints on `.`, compares each slot independently, and feeds the per-slot mismatch count into its risk engine. The fingerprint contribution is just one input — geo-velocity drift from sign-in baseline, ASN / Tor / proxy flags, country allowlist hits, and per-org / per-user policy contributions all stack into the same composite `IRequestContext.RiskScore` (0-100; **higher = more risky**). Action thresholds come from the resolved security policy (Lenient / Standard / Strict tiers per §5.4): risk < step-up = allow; ≥ step-up = OTP step-up; ≥ block = block + invalidate session.

Per-component diff lets the risk engine distinguish "WebGL renderer changed (driver update — low risk)" from "HTTP/2 SETTINGS frame + header order changed (different HTTP client — high risk)" — not possible with a single opaque score. The per-component breakdown stays Edge-internal (telemetry / forensic-audit data feeding the composite score); consumer-side handlers see only the composite `RiskScore` on `IRequestContext`.

**Rate-limit bucket key** — internal to the rate-limit middleware. Computed as `sha256(SessionFingerprint)` (compact hash of the dot-separated form, suitable as a Redis key without the per-component verbosity). Not exposed on `IRequestContext` — handlers don't need it.

##### Behavioral risk scoring

Independent of binding. Per-session activity tracker (Redis sorted set, TTL = session lifetime, capped at last ~50 events). Inputs: IP, ASN, country, lat/lon (from IPinfo via `X-D2-WhoIs`).

```
risk_score = 0

// Impossible travel
if (lastEvent exists AND policy.impossibleTravelLimit != Off):
    distance_km = greatCircleDistance(lastEvent.latLon, current.latLon)
    time_hours = (current.ts - lastEvent.ts) / 3600
    implied_speed = distance_km / time_hours
    if (implied_speed > policy.impossibleTravelLimit) → risk_score += 50
    elif (implied_speed > 300) → risk_score += 10

// Country / ASN signals
if (country != lastEvent.country AND time < 30min) → risk_score += 20
if (>5 different ASNs in last 2min) → risk_score += 15
if (asnType == datacenter AND policy.datacenterPolicy == Flag) → risk_score += 30
if (asnType == tor AND policy.torPolicy == Block) → block immediately
if (country NOT IN policy.countryAllowlist) → block immediately

// Burst rate
if (recent rate > 10× normal baseline) → risk_score += 20

// Fingerprint binding mismatch contribution
risk_score += fingerprintMismatchScore
```

**Risk score interpretation**:
| Score | Action |
|---|---|
| 0 to (step-up - 1) | Allow |
| step-up to (block - 1) | **OTP step-up required** — interrupt request, send OTP to verified email |
| ≥ block | **Block + invalidate session** + notify via Courier |

**Step-up via OTP** (not password re-entry) — more enterprise-shaped, doesn't train users that "anything that asks for my password is normal."

**Risk score persistence**:

- Per-session ephemeral score in Redis (cumulative)
- Per-request risk score on `audit_event` rows for blocked / step-up'd / elevated requests
- Per-sign-in risk score on `sign_in_event` rows (forensic analysis)

##### Security Policy framework

Three hierarchy levels, monotonically restrictive going up:

```
platform_minimum  ← code/env, applies to all
       ↓
org_policy        ← org admins, must be ≥ platform_minimum
       ↓
user_policy       ← users, must be ≥ org_policy(s) they belong to
```

**Effective requirement** = `max(user_policy, max(org_policy across the user's orgs), platform_minimum)`.

**Tunable dimensions**:

| Dimension                        | Tiers                                                                    | Default             |
| -------------------------------- | ------------------------------------------------------------------------ | ------------------- |
| **Risk scoring**                 |                                                                          |                     |
| Step-up threshold                | Lenient (70) / **Standard (50)** / Strict (30)                           | Standard            |
| Block threshold                  | Lenient (95) / **Standard (80)** / Strict (60)                           | Standard            |
| Impossible-travel speed limit    | **Off** (VPN) / Lenient (1500 km/h) / **Standard (1000)** / Strict (500) | Standard            |
| Country allowlist                | Off / On (configured set)                                                | Off                 |
| Datacenter ASN policy            | Allow / **Flag (+30 risk)** / Block                                      | Flag                |
| Tor exit node policy             | Allow / Flag / **Block**                                                 | Block               |
| Anonymous proxy policy           | Allow / **Flag** / Block                                                 | Flag                |
| **Authentication**               |                                                                          |                     |
| MFA requirement                  | None / **OTP on step-up only** / OTP every sign-in / TOTP / WebAuthn     | OTP on step-up only |
| Password complexity              | Basic / **Standard** / Strict                                            | Standard            |
| **Session**                      |                                                                          |                     |
| Max session lifetime             | **30 days** / 7 days / 24 hours / 8 hours                                | 30 days             |
| Idle timeout                     | None / **24 hours** / 1 hour / 15 min                                    | 24 hours            |
| Allow persistent sessions        | **Yes** / No                                                             | Yes                 |
| Max concurrent sessions per user | 1 / 2 / 3 / **4** (FIFO eviction always)                                 | 4                   |

**Platform-fixed (NOT configurable)**:

- Password minimum length: **always 12** characters
- Email verification: **always required** for sign-up
- Phone verification: **required for specific flows** (sensitive ops, MFA setup), API-determined
- Re-auth frequency for sensitive ops: **per-flow, API-determined**
- Max concurrent sessions: always **FIFO eviction**; cap is 1-4; never unlimited

##### Sign-in flow + per-org policy enforcement

**Sign-in is into the user's account only**, not into a specific org. Then user picks an org context.

1. User authenticates (email/password + any MFA from user's _personal_ policy + platform minimum)
2. If `redirectUrl` query param present, MUST also include `orgId` query param
3. User selects an org from their list
4. **At org-selection time** (NOT sign-in time), system evaluates whether user's effective policy meets the org's policy
   - Compliant → enter org context, mint org-scoped JWT, navigate
   - Non-compliant → upgrade interstitial. User can update settings to comply, or back out

A user belonging to 10 orgs with mixed policies does NOT have to upgrade their settings to the strictest org's level just to sign in. **Compliance is on-demand, per-org-selection.**

##### Joining an org with stricter requirements

Invitation arrives. Modal shows specifics: "Joining {Org B} requires: TOTP MFA, max session lifetime 7 days, datacenter ASNs blocked. Your current settings meet 2 of 3. **[Auto-upgrade & accept]** / **[Decline]** / **[Decide later]**."

Decide-later (or just closing the modal) keeps the invitation pending in the dashboard until expiry (default 30 days). No silent decline.

##### Org admin raising policy

Grace period with prompts (admin picks 24h / **7 days** / 30 days). When member with non-compliant settings selects this org OR is mid-session and tries an org-scoped action: upgrade interstitial. Other orgs the user belongs to unaffected. **Per-org enforcement only when actively using that org.**

##### Audit visibility

- **Self**: each user can see their own sign-in events, blocked attempts, step-up events, policy changes
- **Org agents/owners**: audit for their org's members, scoped to org-related actions only
- **Staff (support org)**: relevant to support tickets, with consent / impersonation framework, read-only
- **Admin (admin org)**: full visibility

##### WhoIs pass-down (no service-level cache)

Edge does the IPinfo lookup **once per request** (with a small in-memory cache to suppress duplicate hits within a short window for high-traffic IPs). The result is **encoded and passed downstream via the `X-D2-WhoIs` HTTP header** (and equivalent gRPC metadata key for service-to-service calls). Backend services **never call IPinfo themselves** — they decode the header and use the data directly.

**Encoding**: WhoIs object JSON-serialized, base64url-encoded for header transport. Same approach as JWT (compact, deterministic, easy to decode in any language). Optionally compressed (gzip + base64) if payloads grow.

**What this gives us**:

- Zero per-service IPinfo cost — Edge is the only consumer of the IPinfo API
- No multi-tier cache infrastructure needed (no Redis layer, no DB layer, no service-level memory cache)
- Sensitive services (e.g., a future Payments service) can do **additional risk scoring** using the WhoIs data without depending on Edge's risk-scoring decision
- Service-to-service calls preserve the original WhoIs context (the metadata propagates per the standard Request Enrichment pattern — see §5.5)

**The only caching that exists**: a short-lived in-process cache inside Edge to deduplicate IPinfo hits within a single request burst from the same IP (typically 5-30 second TTL). No Redis, no DB.

##### Guest sensitive operations (magic-link / signed-token pattern)

Some operations are simultaneously **sensitive** (financial, account-affecting) AND **callable by users without a Worx account** — e.g., a customer of one of our Worx customers paying an invoice via a link emailed to them.

**Pattern**: these endpoints stay at their natural risk tier (`Elevated` or `Critical` per §5.3) and require auth like any other sensitive endpoint. The "anonymous" caller is granted **temporary, scoped auth via a magic-link token**:

- Worx customer triggers "send invoice to client" → Edge mints a signed, short-lived token (15-30 min default, configurable) scoped narrowly to "pay invoice X" only
- Email/SMS to client contains a URL with the token embedded as a query param
- Client clicks link → SvelteKit page renders, calls Edge to exchange the magic-link token for a temporary session JWT with the narrow scope baked in
- Client completes payment → temporary session expires after action OR after TTL, whichever first

**No new tier needed.** The endpoint is `Critical`. The token IS the auth. This pattern also applies to: email verification links, password reset links, OTP verification, "review and approve" workflows for non-account-holders.

**Why not a tier**: a "PublicSensitive" tier would invite developers to design endpoints that are publicly callable AND modify state, which is exactly the wrong instinct. Magic-link tokens force the right architecture: sensitive operations require auth, auth can be temporary and narrowly scoped.

##### ClamAV deployment

Single ClamAV container on the Swarm `internal` network. Files service uses `nClam` to communicate over TCP. **Failure mode: if ClamAV is down, file uploads return 503.** No exceptions; uploading unscanned files is too risky regardless of file type or user tier.

### 5.5 Real-Time (SignalR)

#### Auth lifetime — handshake-only + targeted revocation

SignalR connections authenticated **only at the handshake**. JWT presented at WebSocket upgrade is validated; once open, no recurring re-check. Connections survive their handshake JWT's expiry. **Targeted revocation** delivered out-of-band via `session.revoked` SignalR message + server-side force-close.

**Why**: industry standard (Slack, Discord, Teams, GitHub live updates, AppSync, Firebase, SignalR's own `[Authorize]` default). Periodic re-auth or kick-on-exp breaks UX (every user disconnected every 15min, reconnect storms, missed pushes during reconnect) for negligible security gain.

**WS protocol-level liveness**:

- `KeepAliveInterval` = 15s (server pings client) — SignalR default
- `ClientTimeoutInterval` = 30s — SignalR default
- SignalR JS client auto-reconnects with exponential backoff on drop

**Connection cap**: **10 per user, FIFO eviction**.

**"Reconnecting…" indicator**: show after 5s of disconnected state.

#### Three categories of client-facing events

| Category                         | Trigger                                    | Transport                                                 | Toast              | Persist | Examples                                                                                             |
| -------------------------------- | ------------------------------------------ | --------------------------------------------------------- | ------------------ | ------- | ---------------------------------------------------------------------------------------------------- |
| **Sync UI feedback**             | REST request returns success               | None — SvelteKit reacts to its own `await fetch()` result | Yes                | No      | "Profile updated", "Copied to clipboard", form errors                                                |
| **Async work-completion signal** | Server-side work the user started finishes | **WS push (fire-and-forget)**                             | Yes                | **No**  | Avatar processed, file scan complete, image variants generated                                       |
| **Entity notification**          | Domain event the user may not have started | **WS push as optimization + persistent store**            | Yes (foregrounded) | **Yes** | "Alice signed in from a new device", "Your monthly report is ready", "@-mention", "Payment received" |

**The deciding question** for which category an event falls into: **"if the user misses the WS push entirely, is the state still discoverable in-place?"** Yes → category 2. No → category 3.

#### SignalR push layering

The WS push API is owned by **Edge's SignalR gateway**, not by Notifications. Notifications is one consumer among many.

```
Edge SignalR gateway (the WS connection holder)
  • PushToUser(userId, eventType, payload)         ← anyone with auth can call
  • PushToOrg(orgId, eventType, payload)
  • PushToConnection(connectionId, eventType, payload)
        ▲                       ▲                        ▲
   ┌────┴────┐            ┌─────┴─────┐            ┌─────┴─────┐
   │ Notifs  │            │ Files     │            │ Auth      │
   │ Cat 3:  │            │ Cat 2:    │            │ Session   │
   │ Persist │            │ Push only │            │ events    │
   │ + Push  │            │           │            │           │
   └─────────┘            └───────────┘            └───────────┘
```

**Mobile backgrounded delivery** (future): WS poor fit for backgrounded mobile. APNs (iOS) / FCM (Android) push notifications fed from same notifications pipeline that fires WS pushes when foregrounded.

#### Targeted revocation flow (load-bearing)

- Edge maintains `session_id → [connection_ids]` mapping (Redis-backed)
- On revocation (sign-out, ban, password reset, impersonation exit, role change requiring fresh token):
  1. Emit `session.revoked` SignalR message to all matching connection ids
  2. Force-close those connections server-side
  3. Invalidate session in 3-tier store
- Browser drops WS, clears in-memory state, redirects to sign-in (or re-auths transparently)

#### Rate limiting

> **Authoritative design lives in [`docs/v2/PHASE_3_RATE_LIMITING.md`](PHASE_3_RATE_LIMITING.md).** This subsection is a 3-paragraph summary; the dedicated doc covers the full design, bucket math, kill-switch hierarchy, FP-too-common detection, and Edge implementation guidance.

**Two orthogonal axes — kept distinct.** `RateLimitTier` (`Standard` / `Elevated` / `Restricted`) is an Edge endpoint attribute that captures "how costly / abusable is this endpoint?" and lives ONLY at the Edge. `ActionSensitivity` (`Routine` / `Sensitive` / `Critical`) is per-scope claim metadata that captures "how dangerous is this action if it succeeds?" and drives audit verbosity / step-up / impersonation defaults. A sign-in endpoint is `Routine` × `Restricted`; an admin destructive endpoint is `Critical` × `Standard`. The two never get cross-wired (distinct enums, distinct vocab).

**18-bucket model with cookie-shortcut bypass.** Three dimensions (FP-or-UserId / City+Region+Country / Country) × three `RateLimitTier` values × two auth states = 18 conceptual buckets system-wide. Each request only touches 3. Anonymous requests with a known-good session cookie (found in L1 in-memory cache or Redis) **bypass the anonymous gates entirely** and proceed straight to auth → authed-side rate limits — protects authenticated users behind shared NATs from being penalized by co-located bad actors. Authenticated requests bucket by UserId (not FP), eliminating FP-collision unfairness for the auth'd population. Per-FP detection includes a "too common?" guard: FPs seen across many distinct non-VPN/proxy/Tor IPs (over a sliding window) get bypassed for per-FP and rely on geographic dimensions instead — handles the "many identical iPhones" case without one bad actor rate-limiting the whole population.

**Robustness hooks.** Pub/sub session-invalidation backplane keeps the cookie shortcut consistent across Edge replicas (revocation events evict from L1 immediately; 5-min TTL as belt-and-suspenders). Runtime kill-switch hierarchy via Redis keys (per-FP / per-IP / per-user / per-dimension / global) with 10s per-replica caching for emergency bypass without redeploy. Failure mode is `RateLimitTier`-keyed: `Standard` and `Elevated` fail-open on Redis outage; `Restricted` (brute-force surfaces — sign-in, password reset, OTP) **fails closed** because better to 503 than allow uncapped brute force.

**The handler-facing fingerprint surface** (consumed by audit / risk scoring, not by rate limit middleware itself):

|                                                                                                                     | `SessionFingerprint` (JWT `d2_fp` claim)                                                                     | `CurrentFingerprint` (per-request recomputed) |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| Purpose                                                                                                             | "What was bound to this session?"                                                                            | "What is THIS request's device fingerprint?"  |
| Format                                                                                                              | `v1.c1.c2.c3.c4.c5.s1.s2.s3.s4.s5` (10 component hashes per V2.md §5.4 fingerprint binding)                  | Same                                          |
| Includes IP?                                                                                                        | **No** — IP changes constantly on mobile                                                                     | **No**                                        |
| Match style                                                                                                         | (compared component-by-component against CurrentFingerprint; mismatch count feeds the composite `RiskScore`) |                                               |
| Propagated via the cross-hop `x-d2-context` header (`PropagatedContext`) to async consumers / sync gRPC + HTTP hops | Yes                                                                                                          | Yes (per-publish / per-call snapshot)         |

**Spoof detection** ramp:

1. **Reject missing fingerprint on cookie-auth endpoints** (browser auth = JS always runs = absence is anomaly = 400)
2. **Server-recomputable cross-checks** (UA major version vs HTTP/2 fingerprint, timezone vs IP geo, screen DPR vs device family)
3. **Known-bot signal databases** (FingerprintJS OSS botDetection module + headless Chrome / Selenium / Puppeteer / Tor signatures)
4. _Defer_: honeypot probes, statistical anomaly detection

**Cross-effects with risk scoring**: rate-limit hits feed back into risk score (each 429 adds +5); risk score modulates rate limits (high-risk session gets tighter caps until OTP step-up resets). Full integration documented in [`docs/v2/PHASE_3_RATE_LIMITING.md`](PHASE_3_RATE_LIMITING.md).

### 5.6 Storage

#### Object storage — SeaweedFS with Postgres Filer backend

Replace MinIO with [SeaweedFS](https://github.com/seaweedfs/seaweedfs) as part of Phase 1 Files port. Filer uses **existing Postgres** as metadata backend — no net-new infrastructure.

**Why SeaweedFS**:

- MinIO's OSS posture has been degrading (Console removed from OSS in 2025, features gated). Liability for self-hosted-OSS-first project.
- **Workload fit**: Haystack-inspired design optimized for many small files (avatars, documents, image variants — our exact pattern). Small objects packed into volume files internally; reading 100 thumbnails is closer to "one disk seek + sequential read" than "100 individual seeks."
- **Horizontal scale**: designed for billions of files, petabyte scale. Higher ceiling than Garage (~100 nodes) or RustFS (unproven).
- **Apache 2.0 license** — more permissive than MinIO's AGPLv3.
- **Pluggable metadata backend**: uses our existing Postgres (no new dep).

**Architecture (production)**:

- **Master servers** (Raft for cluster topology). Start with 1; scale to 3 for HA. Operationally similar to Redis Sentinel.
- **Volume servers** (data plane). Each volume = ~30GB file holding many objects. Add nodes for capacity; data redistributes automatically.
- **Filer servers** (stateless S3 gateway + metadata). Backed by our existing Postgres.

**Architecture (local dev)**: single container, all-in-one mode (`server -s3`).

**Encryption at rest**: disk-level (LUKS / dm-crypt). Dominant enterprise pattern (matches AWS EBS); accepted by SOC 2 / HIPAA / PCI for "data at rest is encrypted" requirements. Per-object SSE-C / customer-managed keys deferred (addressable later via app-level encryption layer in Files if needed).

**Known losses vs MinIO** (accepted):

- **Object Lock / WORM**: limited support. Audit storage uses Postgres + revoked-permissions + DB triggers for tamper-evidence; "tiny separate MinIO for audit bucket only" is a fallback if true Object Lock ever required for compliance.
- **SSE-C / SSE-KMS per-object encryption**: not native. Addressable later.
- **IAM-style JSON bucket policies**: SeaweedFS uses simpler access-key + role model. Fine for our use case (per-tenant prefix, presigned URLs minted by Files).
- **Lifecycle policies**: basic expiry; anything sophisticated handled in Files cleanup job.
- **Tooling polish**: `weed shell` competent but less polished than `mc`; built-in admin UI is basic.
- **AWS SDK behavioral fidelity**: MinIO has years of investment matching every SDK quirk. SeaweedFS gateway is "S3-compatible enough" for our operations (PutObject, GetObject, presigned URLs, multipart, basic listing).

#### Database topology — one server, many DBs (initial), eventual replicas

Initial deployment: **one Postgres server** hosting many databases. Move to a primary + 2 read replicas (HA configuration) when needed at launch time. Same Postgres server hosts the SeaweedFS Filer DB.

**Database catalog (each as a separate DB on the shared server)**:

#### Database — greenfield, no migration

App is pre-alpha with no real users and no production data to preserve. The new .NET architecture starts with a **fresh schema** designed for the new domain model. EF Core generates initial migrations from scratch. Old Drizzle migration files live in `/old/v1/` as historical reference only — never run, never adapted.

**Implications**:

- No data migration scripts.
- No EF Core "baseline" migration.
- New schema can re-shape freely.
- Local dev: dev databases dropped + re-created on first run.
- `d2-node-init` migration runner container retired as part of the Node → .NET cleanup.

**Migration discipline** (per CLAUDE.md, carried forward):

- **Never hand-write migrations** (.NET = `dotnet ef migrations add <Name>`; that's it)
- Generator output committed as-is

#### Migration runner — multi-replica safety via PG advisory locks

With 2-3 replicas of a service starting concurrently, all attempt EF Core migrations on startup. To prevent races, each migration acquires a named PostgreSQL advisory lock before running:

```csharp
// Pseudocode in the startup IHostedService that runs migrations
var lockName = $"d2-migration-{serviceName}";
var lockId = (long)XxHash64.Compute(lockName);

await using var conn = new NpgsqlConnection(connectionString);
await conn.OpenAsync();
await conn.ExecuteAsync("SELECT pg_advisory_lock(@lockId)", new { lockId });
try
{
    await dbContext.Database.MigrateAsync();
}
finally
{
    await conn.ExecuteAsync("SELECT pg_advisory_unlock(@lockId)", new { lockId });
}
```

Built-in PG, no infra dependency. Only one replica runs the migration at a time; others wait then proceed (EF Core's "is this migration already applied?" check no-ops). Contact data folds into each service's own `DbContext` — there is no separate contacts DB or contacts-specific migration lock.

#### 5.6 (Revised 2026-05-30) — Contacts as a folded owned-component library

> **Supersedes** the struck-through per-consuming-service-DB design above. Full rationale + v1 ↔ prior-plan ↔ today lineage: [ADR-0001](../adrs/0001-contacts-folded-owned-component.md).

> **Built (2026-06-04).** The core decision — folded owned-component, no service, no DB — shipped on `n/contacts`. The implementation mechanism was refined during build: the initial wrapper-selector EF API (`EmbedContact` / `OwnContactInTable`) was replaced by a pure **VO-as-property + infra `IEntityTypeConfiguration<T>`** model using EF complex types for multi-field VOs and value converters for single-value VOs. `OwnsOne` / `OwnsMany` are not used (the anonymization engine's bulk erasure cannot reach owned child rows — principled boundary). **ADR-0001 is the canonical built record.** The planning prose below is preserved for tracking context.

`D2.Shared.Contacts` is a **.NET-only library of value-object building blocks + reusable EF Core mapping** — **NOT a service, NOT its own database**. Contacts are **folded into each consuming service's own aggregates, tables, and `DbContext`**. There is no contacts DB, no contacts service, and no cross-service contact lookup / external-key triple.

**Why the flip** (full reasoning in ADR-0001):

- A contact is almost always a **subset of a host entity** (an invoice's billing/shipping contact, a user's or org's 1:1 contact, an org's address-book entry) — not an independent aggregate with its own lifecycle.
- "Folded **like Location**" means **embedded into a host entity** (Location's structural trait) — **not content-addressed**. Contact fields are PII, so Location's hash-dedup model deliberately does not extend to them (dedup of PII doesn't belong).

**What the library ships** (zero migrations, zero `DbContext`, zero DB):

- **Six composable PII value objects** (`Personal`, `NameAffixes`, `Demographics`, `Professional`, `EmailAddress`, `PhoneNumber`) with `Create(...) → D2Result<T>` smart constructors. `Personal` carries a correlation `HashId` (SHA-256 over First/Middle/Last — excludes PreferredName for display-name-change stability).
- **Per-VO EF mapping helpers** (`D2.Shared.Contacts.EntityFrameworkCore`): multi-field VOs → EF complex types (`MapPersonal` / `MapNameAffixes` / `MapDemographics` / `MapProfessional`); single-value VOs → value converters (`MapEmailAddress` / `MapPhoneNumber`) with compile-time `.Unique(template)` coupling. All anonymize defaults written via the `D2.Shared.DataGovernance.EntityFrameworkCore` fluent API.
- Address fields reuse `D2.Shared.Location` VOs directly — mapped via `D2.Shared.Location.EntityFrameworkCore`.

**Subject-id axes (kept):** every contact-bearing host entity carries optional **`Guid? UserId`** and **`Guid? OrgId`** — the correlation and erasure keys. Erasure fans out per subject via `D2.Shared.DataGovernance`. Guests/externals fall back to the channel address (email/phone). Legal-hold rows are field-overwritten with tombstone values in place.

**Live vs snapshot ownership:** exactly one service owns a person's **live** canonical contact (Auth owns the user's); everyone else snapshots at capture-time. Never replicate a live contact.

**Versioning discipline (migration-cascade mitigation):** because the host owns the migration, a contact-shape change can require a migration in every adopting service. Mitigated by **semver + additive-only-within-a-major**. The library stays pure (types + mapping + validation, no business behavior).

**Delivery preferences / consent — separated out, DEFERRED:** delivery preferences + consent stay central in Courier, keyed by channel address (suppression) and subject id (routing prefs). The detailed prefs/category-lane schema is deferred.

**Day-one consumers:** Edge/Auth (user + org contacts). Invoice/billing snapshots arrive when those services exist.

#### GeoReference + Location libraries

`D2.Shared.GeoReference` — embedded library for countries, IANA timezones, currencies, locales, regions via MSBuild `EmbeddedResource`. No service, no DB, no Redis cache, no gRPC round-trip. Loaded into memory at service boot (a few hundred KB total).

`D2.Shared.Location` — three value objects:

- **`AdminLocation`** (CountryCode + Region + City + computed hash)
- **`Coordinates`** (Lat + Lon + Geohash)
- **`StreetAddress`** (Line1 + Line2 + Line3 + computed hash of normalized lines)

`WhoIsRecord` composes `AdminLocation + Coordinates` (no street ever — type system prevents it).
Host entities with contact fields embed any combination of the three Location VOs alongside the Contacts VOs — reused independently, mapped via `D2.Shared.Location.EntityFrameworkCore` (see [§5.6 Revised](#56-revised-2026-05-30--contacts-as-a-folded-owned-component-library) + [ADR-0001](../adrs/0001-contacts-folded-owned-component.md)).

### 5.7 Messaging & Notifications

#### Event naming — service-namespaced to avoid clashes

All RabbitMQ exchanges, routing keys, and event message types are namespaced by **producing service** to prevent name collisions and make ownership explicit:

| Concern                           | Pattern                                                 | Examples                                                                                                         |
| --------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Exchange names                    | `d2.{producer}.{purpose}`                               | `d2.audit.events`, `d2.notifications.requests`, `d2.files.events`, `d2.courier.delivery-status`                  |
| Routing keys (within an exchange) | `{event-type}` (lowercase, dot-separated for hierarchy) | `sign-in.success`, `sign-in.failed`, `payment.charged`, `file.uploaded`, `file.processed`                        |
| Event proto packages              | `d2.events.{producer}.v{N}`                             | `d2.events.audit.v1`, `d2.events.files.v1`, `d2.events.notifications.v1`                                         |
| Event proto messages              | `{Producer}{EventType}Event`                            | `AuditEventEvent` (yes, awkward — see naming exception below), `FileUploadedEvent`, `NotificationRequestedEvent` |

**Naming exception**: when the producer's name matches the event type (e.g., D2.Audit's only event IS an audit event), drop the redundant suffix — just `AuditEvent`. Same for any future case where producer + event-type would create the awkward double-naming.

**Schema location**: all event message schemas live in `contracts/protos/events/v{N}/{producer}.proto`. Each `.proto` documents (in comments): "Published by: X. Consumed by: Y, Z." So readers can trace producers and consumers without grep.

**Proto versioning**: same rules as RPC contracts (per §7). Breaking changes require a new `vN+1/` package; never modify a `vN` schema in place. Old version stays in service until explicitly decommissioned.

#### Naming — Comms splits into three

| Service              | Concern                                                                    | Verb                 | Status      |
| -------------------- | -------------------------------------------------------------------------- | -------------------- | ----------- |
| **D2.Courier**       | Outbound delivery via email / SMS / future webhooks / Slack / Teams / push | `deliver()`          | **Phase 2** |

#### D2.Courier (pure outbound delivery + prefs gate)

After redesign + rename, Courier shrinks dramatically:

- ❌ No contact storage, no contact resolution
- ❌ No template entity, no template management
- ❌ No conversational messaging (that's Threads)
- ❌ No in-app feed (that's Notifications)
- ✅ Receives delivery request: subject (markdown w/ placeholders), body (markdown w/ placeholders), variables map, channel hints, recipient delivery info, prefs scoping context
- ✅ Substitutes variables into subject + body (HTML-escaped on insertion; no escape hatch)
- ✅ For email: renders markdown → HTML via `Markdig` (`UseAdvancedExtensions().DisableHtml()`), runs through `Ganss.Xss` HTML sanitizer, wraps in brand chrome (Razor template, branding vars only — color, logo image)
- ✅ For SMS: substitutes variables into plain-text body, no rendering, forward via Twilio
- ✅ Plain-text fallback for email derived automatically via Markdig's `PlainTextRenderer`
- ✅ Looks up delivery preferences scoped by `(UserId/OrgId) × (RelatedServiceName/Key/Id)`; most-specific match wins
- ✅ Delivers via SMTP / Twilio
- ✅ Retries via tier-queue topology (existing pattern)
- ✅ Tracks delivery status

**Future channels** (deferred): webhooks, Slack, Teams, Discord, mobile push (APNs/FCM). All slot in as additional channel handlers behind the same `deliver()` API.

#### D2.Notifications (Phase 2 — promoted from "future")

In-app activity feed only. Persistent feed entries with read/unread state, pagination, aggregation ("Alice and 3 others liked your post").

**Promoted into Phase 2** alongside Courier because the WS-as-optimization pattern requires a persistent source of truth; without Notifications, entity-notification reliability collapses to "WS-only delivery, lost if offline."

**Schema sketch**:

- `notification_feed_entry` — `id`, `recipient_user_id`, `producer_service`, `event_type`, `subject` (markdown), `body` (markdown), `link` (deep-link URL), `metadata` (JSONB), `urgency`, `aggregation_key` (nullable), `read_at`, `created_at`. Indexed on `(recipient_user_id, read_at, created_at)`.

**Pipeline**:

- Producers publish `NotificationRequestedEvent` to the `d2.notifications.requests` exchange (consistent with the event naming convention above; decouples producers from Notifications availability)
- Notifications consumes, persists feed entry, calls **Edge's SignalR push API** (gRPC) to push a `notification.created` SignalR message to recipient's connections
- REST API: `GET /api/v1/notifications`, `PATCH /api/v1/notifications/{id}/read`, `PATCH /api/v1/notifications/read-all`
- Aggregation rules live in Notifications (it owns the feed shape)
- Notifications does **not** decide whether to also send email/SMS — that's the producer's call (publish to `d2.notifications.requests` AND call Courier explicitly)

#### D2.Audit (Phase 3.5 — separate service)

Append-only audit store for impersonation sessions, sign-in events, security events, cross-service action audit.

**Why a separate service**:

- Different retention policy from operational data
- Different access control (compliance / legal can be granted read-only without touching anything else)
- Append-only easier to enforce in dedicated DB (revoke `UPDATE`/`DELETE` from the service role; only `INSERT` allowed)
- Cross-service audit (Files actions, Auth actions, Courier actions) all flow into one query surface
- Optional later upgrade to tamper-evident immutable bucket (S3 Object Lock) without changing producers

**Schema (rough)**:

- `audit_event` — `id`, `event_type`, `actor_user_id`, `actor_org_id`, `actor_org_type`, `actee_user_id`, `actee_org_id`, `action`, `resource_type`, `resource_id`, `metadata` (JSONB), `source_ip`, `source_fingerprint`, `correlation_id`, `created_at`
- `support_session` — denormalized row per impersonation start/end (duration, kind consent/force, OTP id)

**Write path**: every service publishes `AuditEvent` to the `d2.audit.events` exchange (fanout, fire-and-forget). Audit service consumes, writes to `audit_db`. **Telemetry stays clean** — OTel spans carry only correlation IDs, never the audit payload itself.

**In-transit opacity**: all audit events are encrypted at the publisher via `D2.Shared.Encryption` — see the next subsection.

#### Payload encryption (D2.Shared.Encryption)

All RabbitMQ message bodies in sensitive domains are encrypted at the publisher and decrypted at the consumer. Routing keys and message headers stay in cleartext (RabbitMQ needs them to route). Encryption is per-payload (whole-body), not per-field — simpler, no schema-walking, and nothing in our routing depends on body contents.

**Domains at launch** (separate keys per domain — blast-radius isolation):

| Domain          | Exchanges                                                       | Why encrypted                                                                 |
| --------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `audit`         | `d2.audit.events`                                               | Actor/actee IDs, action, metadata, IP, fingerprint                            |
| `notifications` | `d2.notifications.requests`                                     | Recipient + subject/body markdown (often names, addresses, financial figures) |
| `courier`       | `d2.courier.deliver` (and any future direct-delivery exchanges) | Full email/SMS bodies + recipient addresses                                   |

`d2.files.events` and similar low-PII exchanges start unencrypted; can be added to a domain later by setting `[Encrypted(Domain.X)]` on the message type.

**Algorithm**: AES-256-GCM (.NET native `AesGcm`; authenticated encryption; well-supported across languages).

**Frame format** (self-contained, transport-agnostic — kid travels with the ciphertext to S3 backups, DLQ exports, future bus migrations):

```
[1 byte:  version=1]
[1 byte:  kid_length]
[N bytes: kid (UTF-8, e.g. "audit-2026q3")]
[12 bytes: GCM nonce]
[M bytes: ciphertext + 16-byte GCM auth tag]
```

Overhead: ~14 bytes + kid length. Trivial.

**Kid naming**: `{domain}-{yyyy}q{n}` (e.g., `audit-2026q3`). Domain prefix prevents cross-domain key collisions. Embedded year+quarter makes archive lookup deterministic given any kid.

**Library shape** (`D2.Shared.Encryption`):

```csharp
public sealed class PayloadCryptoKeyring
{
    private readonly Dictionary<string, byte[]> _keys;  // kid → 32-byte key
    private readonly string _activeKid;

    public ReadOnlyMemory<byte> ActiveKey { get; }
    public bool TryGetKey(string kid, out ReadOnlyMemory<byte> key);
    public IReadOnlyCollection<string> AllKids { get; }  // ops/diagnostics
}

public sealed class PayloadCrypto(PayloadCryptoKeyring keyring) : IPayloadCrypto
{
    public byte[] Encrypt(ReadOnlySpan<byte> plaintext);   // uses active kid
    public byte[] Decrypt(ReadOnlySpan<byte> framed);      // reads kid from frame, looks up
}
```

**Bus integration** (`D2.Shared.Messaging`): bus wrapper inspects message type for `[Encrypted(Domain.X)]` attribute. If present, encrypts on publish and decrypts on subscribe. Call sites stay clean — `bus.Publish(myEvent)` / `bus.Subscribe<MyEvent>(handler)` look identical to unencrypted code.

**Multi-key support — JWKS-style overlap (graceful rotation)**: the keyring carries N kids simultaneously, exactly like a JWKS endpoint carries N public keys. Encryption uses the active kid; decryption looks up the frame's kid in the ring. During rotation, both old and new kids are in every consumer's ring for the entire grace window — old in-flight messages decrypt fine while new messages use the new kid. The grace window length is configurable per domain (default 7 days) and can be extended on the fly (e.g., "wait until DLQ drained before retiring v1").

**Two-tier key model** (active vs archive):

| Tier        | Where it lives                                                                                | Loaded by                                     | Removal policy                                     |
| ----------- | --------------------------------------------------------------------------------------------- | --------------------------------------------- | -------------------------------------------------- |
| **Active**  | `keycustodian_db.key_record` (status `active` or `retiring`); fetched by `KeyringClient` per §5.4 | Production publishers/consumers               | Marked `retired` after grace window; never deleted |
| **Archive** | `keycustodian_db.key_record` (status `retired` or `compromised`) — never deleted                  | Privileged ops/inspection CLI only, on-demand | Permanent (forensic record)                        |

Production `KeyringClient` fetches only `active` + `retiring` kids. Archive kids stay in `keycustodian_db` forever; only the ops CLI loads them when an operator runs `d2 msg decrypt --include-archive`. Production services NEVER load archive keys. This bounds production blast radius without losing the ability to decrypt history for old DLQ messages.

**Key distribution**: handled by KeyCustodian (per §5.4). All publishers and consumers consume via `KeyringClient` — no key material in env files, no shared volumes, no file watching. The KeyringClient handles startup fetch, hourly TTL refresh, and live reload on `d2.security.key-rotated` events.

**Inspection CLI** (in privileged ops container):

```bash
# Decrypt 10 recent DLQ messages (active keyring only)
d2 msg decrypt --domain audit --queue audit-events.dlq --count 10

# Decrypt a specific stale message including archived keys
d2 msg decrypt --message-id <id> --include-archive
```

The CLI fetches keys directly from `keycustodian_db` via service-identity JWT with the `auth.keys.archive.read` scope (granted only to admin org owners; `[ImpersonationBlocked]` to prevent impersonation abuse).

**Failure modes** (all explicit, no silent fallback):

- Active kid missing from keyring at publish time → fail fast with `"active kid X not in keyring"` error
- Decrypt sees a kid not in the keyring → explicit `"kid X not in current keyring"` error → DLQ + alert
- Frame version byte ≠ 1 → fail fast (no legacy passthrough — clean break)

See §5.4 for the full key lifecycle, rotation cadences, distribution model, and compromise runbook.

### 5.8 SvelteKit BFF

**Pure SSR, nothing else.** SvelteKit binds to private network; only Edge can reach it. Browser → Edge → SvelteKit. Header spoofing impossible (no external path).

**What's deleted from today's pattern**:

- ❌ All `+server.ts` endpoints (auth proxy, account proxy, etc.)
- ❌ All form actions
- ❌ All proxying — SvelteKit doesn't see auth-state mutations, account mutations, file uploads
- ❌ Most of `@d2/auth-bff-client` (SessionResolver, JwtManager, AuthProxy, route guards)
- ❌ `getAuthContext()` accessor

**What's kept**:

- ✅ SSR rendering of Svelte components
- ✅ `+page.server.ts` `load()` functions for SSR data fetching
- ✅ `superForm + SPA: true` pattern (already in use; no new browser-side AJAX flows; just retargeted at Edge endpoints)

**Outbound from `load()` functions**:

- **gRPC by default** (joining the existing internal mesh; same generated stubs from `contracts/protos/` work in both .NET and Node clients via `@grpc/grpc-js`)
- HTTP allowed per call site only when measurably faster
- Going back through Edge stays HTTP

**Header contract from Edge → SvelteKit (and outbound from BFF → Edge on round-trip)**:

| Header                       | Type              | Source                                           | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------- | ----------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Authorization`              | `Bearer <jwt>`    | Edge mints / re-mints                            | Carries identity (`sub`, `aud`, `scope`, `act` chain, `d2_session_id`, `d2_username`, `d2_org_id`, `d2_org_type`, `d2_org_role`, `d2_fp`). BFF receives identity by VALIDATING this token, not by reading separate spoofable headers. Custom claims are spec-defined in `contracts/jwt-claims/jwt-claims.spec.json`; constants live in the codegen-emitted `D2.Shared.Auth.Abstractions.JwtClaimTypes` (.NET) and `@d2/auth-abstractions` `JwtClaimTypes` (TS) catalogs.                                                                                       |
| `x-d2-context`               | base64url-of-JSON | Edge constructs from the inbound user request    | Carries the small cross-hop subset of `IRequestContext` that downstream consumers can't recompute — `RequestId`, original `RequestPath`, `SessionFingerprint`, `CurrentFingerprint`, `RiskScore`, `WhoIsHashId`. | `traceparent` / `tracestate` | W3C Trace Context | Edge propagates from inbound (or starts new)     | Per the W3C Trace Context spec — distributed tracing context. Same header on HTTP, gRPC, AMQP. | `X-D2-Internal-Token`        | JWT               | BFF receives from Edge or mints via KeyCustodian | Service-identity JWT (audience `d2.edge`, 15-min TTL). Module-singleton cache in BFF; refresh-on-401. Constant lives in `D2.Shared.Headers.Http` (.NET) and `@d2/headers-http` (TS).                                                                                                                                                                                                             |

**Defense in depth for Edge-bypass prevention** — both layers always on (dev + prod):

1. **Network-level**: SvelteKit attached only to `internal` overlay network in Swarm; only Edge can reach it
2. **Application-level**: thin hook validates the inbound `Authorization` JWT signature and the `x-d2-context` envelope shape via the codegen-emitted serializer; rejects malformed / unsigned requests (HTTP 400 / 401 as appropriate)

**The header catalog is spec-driven**: `contracts/headers/headers.spec.json` is the single source of truth for every wire-protocol header D² emits or consumes (across HTTP / gRPC / AMQP). Codegen emits per-transport catalogs (`D2.Shared.Headers.{Common,Http,Amqp,Grpc}` / `@d2/headers-{common,http,amqp,grpc}`) on each language side; cross-transport headers (e.g. `traceparent`, `x-d2-context`) appear in every applicable catalog at identical wire values, codegen-guaranteed. The same model drives the JWT claim names (`contracts/jwt-claims/jwt-claims.spec.json` → `JwtClaimTypes`) and the in-process slot keys (`contracts/in-process-keys/keys.spec.json` → `D2HttpContextItems` + `D2GrpcUserStateKeys`).

**Browser-side `authClient`**: thin typed `fetch()` wrappers around Edge's auth endpoints (`signIn`, `signOut`, `requestPasswordReset`, `verifyOtp`, etc.). Lives in `server/web/src/lib/client/auth/` as plain TypeScript modules — **NOT a separate package** (no pnpm workspace in v2; SvelteKit is standalone).

The browser calls Edge directly for all auth state mutations (no SvelteKit proxy). After a successful sign-in, Edge sets the cookie; browser doesn't manage cookies. After a sign-out, the browser-side helper calls SvelteKit's `invalidateAll()` to refetch all `load()` data so the UI reflects the now-anonymous state.

**Server-side helpers** for SSR auth gates (used inside `+page.server.ts` / `+layout.server.ts` `load()` functions). Lives in `server/web/src/lib/server/auth/` as plain TypeScript modules — **NOT a separate package**. Five synchronous helpers that read from `event.locals` (populated by the thin hook from `X-D2-*` headers Edge sets):

```ts
function requireAuth(event): asserts event has authenticated locals
function requireOrg(event, ...types?: OrgType[]): asserts ...
function requireRole(event, ...roles: string[]): asserts ...
function requireScope(event, ...scopes: string[]): asserts ...
function redirectIfAuthenticated(event, to: string): void
```

Each throws `redirect()` or `error()` on failure. No I/O. Synchronous. Replaces the entire v1 `@d2/auth-bff-client` package — the v1 package's other concerns (SessionResolver, JwtManager, AuthProxy) all become Edge concerns in v2.

**Local dev**: Edge runs alongside SvelteKit. Browser hits Edge on `localhost:5000`, Edge handles `/api/*` in-process and forwards page-render requests to SvelteKit on `localhost:5173`. `make dev` starts everything together. Vite HMR works through Edge's WS upgrade pass-through.

#### BFF Trust & Privilege Boundary (LOCKED)

**LOCKED architectural decision** (foundation for the BFF lib forecast in the next subsection): the BFF holds **ZERO privileged access** to backend infrastructure. The BFF's only backend dependency is **Edge**. ALL backend data fetches go through Edge. **No** direct Redis. **No** direct RabbitMQ. **No** direct backend gRPC clients (Files / Courier / Notifications / Audit / future). The BFF never holds a backend service-identity client_secret, never decrypts a sensitive RMQ payload, never reads/writes a cache key any other instance can see.

**Auth model BFF → Edge**:

- BFF presents an `X-D2-Internal-Token` (internal service-identity JWT, audience `d2.edge`, scope set scoped to "BFF can read on behalf of a propagated user"). Rotated **independently of user sessions** — a user signing in/out doesn't churn the internal token; an internal-token rotation doesn't kick users.
- BFF passes user identity via the `x-d2-context` propagated header (Phase 0 Wave 7's `D2.Shared.Context.Abstractions.PropagatedContextSerializer`) — **not a copy of the user's session cookie**. The BFF never touches the cookie's signed payload; Edge minted the propagated context on the inbound user request and the BFF round-trips it.
- Edge sees BFF as a known internal caller (the `aud=d2.edge`+`act` claim chain plus the source IP attached to its internal overlay network). Edge can distinguish SSR-driven traffic from browser-direct traffic in audit + telemetry tags (`source: bff` vs `source: browser`).

**Cache invalidation lives at Edge**, not at BFF. Edge has the one Redis, shared across all BFF instances behind it. The BFF NEVER caches anything that needs invalidation. **Per-request memoization** within a single SSR render (multiple `+page.server.ts` / `+layout.server.ts` `load()` functions on the same page asking for the same data) is handled by SvelteKit's **native `load()` parent-dedup pattern** (parent layout fetches once; child pages receive via `parent()`) — NOT a Redis L1, NOT an in-process LRU. This is why the `@d2/cache-*` packages are explicitly OUT of scope on the TS side (see drops list below).

**Why the "extra hop" (BFF → Edge → backend) is the deliberate choice**:

- **Uniform observability** — every backend call shows up in Edge's per-route latency / error / rate metrics. There's no shadow path where "the BFF talked to Files directly and we don't have spans for it."
- **Uniform security policy** — single trust boundary, single auth model, single rate-limit + idempotency layer. Edge's middleware stack (per [`docs/v2/PHASE_3_RATE_LIMITING.md`](PHASE_3_RATE_LIMITING.md) + the Edge Auth module) applies whether the originator is a browser or a BFF.
- **Sub-millisecond in-DC hop** — irrelevant for SSR's 50-200ms render budget. The "extra hop" is a microscopic fraction of any SSR render that touches I/O at all.
- **BFF stays stateless** — horizontal scale is trivial (drop another container; no warm-up, no cache prime, no state).
- **Reduced blast radius if BFF is compromised** — there are no privileged credentials to steal. Stealing the internal token gets the attacker only what an authenticated user could already do, gated by Edge.

**SSR-vs-CSR matrix** (typical dashboard surface — defaults; per-page exceptions are explicit at the call site):

| Concern                                        | Default                            | Reasoning                                                                                                                                                             |
| ---------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Page shell + nav                               | SSR                                | Avoid auth flash; identity drives nav rendering off `event.locals.requestContext` populated from the inbound `Authorization` JWT + `x-d2-context` envelope (zero I/O) |
| User identity / org context                    | SSR                                | JWT-driven; zero I/O                                                                                                                                                  |
| Reference data (countries, locales, timezones) | SSR                                | Embedded `D2.Shared.GeoReference` library on the .NET side; SSR receives via Edge or the equivalent embedded TS data — zero remote call                               |
| Route-guard redirects                          | SSR                                | First-byte redirect; no client-side auth-flash redirect                                                                                                               |
| Permission-derived UI structure                | SSR                                | JWT `scope` claim drives what nav items / actions render                                                                                                              |
| Tenant branding / theming                      | SSR (via Edge call)                | Avoid theme-flash for white-labeled enterprise customers                                                                                                              |
| Feature flags affecting nav                    | SSR (via Edge call)                | Avoid nav-item flash when a flag flips; flag value baked into SSR HTML                                                                                                |
| A/B test variants                              | SSR (via Edge call)                | Consistent variant assignment across SSR HTML + CSR continuation                                                                                                      |
| Form scaffolds (Superforms `superValidate`)    | SSR                                | Pure compute; no I/O. Zod schema + initial form state baked into HTML                                                                                                 |
| Dashboard widgets / tables / charts            | CSR with skeleton                  | Sub-second fetch acceptable; avoids first-paint blocking on N concurrent backend calls                                                                                |
| Forms (live submission)                        | CSR                                | `superForm + SPA: true`; user-confirmed direction (no `+page.server.ts` form actions)                                                                                 |
| Real-time indicators                           | CSR via SignalR / SSE through Edge | Subscription model; SSR snapshot is stale by definition                                                                                                               |

**What "BFF needs SSR" data goes through Edge**: when BFF needs tenant config / feature flags / A/B variants for SSR, it's a **single in-DC gRPC call to Edge** carrying the propagated context. Edge handles the cache layer (one shared Redis) and the backing-service fan-out. BFF stays thin — it's a pure render layer with header-driven context plus optional Edge gRPC for non-cookie SSR data.

- **Single source of truth**: both the .NET stack (via `D2.Shared.I18n.SourceGen` → `TK.g.cs`) and Paraglide consume `contracts/messages/{locale}.json`. Adding a key in the JSON ripples to both languages with one edit.
- **TS-side TK constant catalog NOT planned** — Paraglide already emits per-key TS functions (`m.account_errors_emailTaken()` etc.) which IS the TS-side equivalent of the .NET `TK.account_errors_emailTaken` constant. The "shape" parity is functional, not surface-identical.
- The canonical Paraglide outdir is `server/web/src/lib/paraglide/`.

### 5.9 Production Deployment

**Orchestration**: Docker Swarm + Portainer (until ~$50K/month MRR).

- **Cluster shape**: 3 Swarm manager nodes (Raft quorum). All services run on these 3 nodes. Each backend service runs 2-3 replicas distributed across the cluster via Swarm placement constraints.
- **Two overlay networks**:
  - `ingress` — Edge instances attach here; faces L7 LB (Cloudflare)
  - `internal` — everyone else (SvelteKit, Files, Courier, Notifications, Audit, future services, infra). Edge attaches to both.
  - SvelteKit on `internal` only → cannot be reached from outside Edge.
- **Secrets**: `docker secret` mounts OAuth `client_secret` bootstrap creds (and other long-lived secrets) into each service at `/run/secrets/...`. Each service reads on startup. Rotation via dual-secret window.
- **Configs**: `docker config` for non-secret per-environment configuration.
- **Stack deployment**: `docker stack deploy -c stack.yml d2` from CI, or via Portainer UI.
- **Portainer**: ops UI for stack health, container logs, image management, deploy operations.
- **Infrastructure co-location**: Postgres (primary + 2 replicas), Redis (Sentinel/Cluster), RabbitMQ (3-node cluster), SeaweedFS (1 Master initially → 3 for HA; Volume + Filer per node) all on the same 3 Swarm nodes.

**Upgrade path**: when revenue justifies > 3 machines and operational complexity is worth it, K8s migration unlocks SPIFFE workload identity, NetworkPolicy, more sophisticated autoscaling. Until then, Swarm gives 90% of what we need with 20% of the operational surface.

### 6.3 D2Result monadic operations + guard helper

Add `Bind`/`Map`/`Match`/`ThenAsync` for genuine pipelines (sign-in flow, file processing), and `BubbleOnFailure` guard helper for the dominant pattern (multi-value threading).

```csharp
// On D2Result<T>:
public D2Result<TNext> Bind<TNext>(Func<T, D2Result<TNext>> next) =>
    Success ? next(Data!) : D2Result<TNext>.BubbleFail(this);

public D2Result<TNext> Map<TNext>(Func<T, TNext> projection) =>
    Success ? D2Result<TNext>.Ok(projection(Data!)) : D2Result<TNext>.BubbleFail(this);

public R Match<R>(Func<T, R> onSuccess, Func<D2Result<T>, R> onFailure) =>
    Success ? onSuccess(Data!) : onFailure(this);

// Async extension methods on Task<D2Result<T>> and ValueTask<D2Result<T>>:
public static class D2ResultAsyncExtensions
{
    public static async ValueTask<D2Result<TNext>> BindAsync<T, TNext>(
        this ValueTask<D2Result<T>> task,
        Func<T, ValueTask<D2Result<TNext>>> next) { … }

    public static async ValueTask<D2Result<TNext>> MapAsync<T, TNext>(
        this ValueTask<D2Result<T>> task,
        Func<T, TNext> projection) { … }

    // Same-shape chaining (when state flows step-to-step)
    public static async ValueTask<D2Result<T>> ThenAsync<T>(
        this ValueTask<D2Result<T>> task,
        Func<T, ValueTask<D2Result<T>>> next) => await task.BindAsync(next);
}

// Guard helper for the multi-value-threading pattern (the workhorse):
public static class D2ResultGuardExtensions
{
    public static bool BubbleOnFailure<T, U>(
        this D2Result<T> result,
        out D2Result<U?> bubbled,
        out T? data)
    {
        if (!result.Success)
        {
            bubbled = D2Result<U?>.BubbleFail(result);
            data = default;
            return true;
        }
        bubbled = default!;
        data = result.Data;
        return false;
    }
}
```

**When each tool applies**:

- **`BubbleOnFailure` + locals** (workhorse): multi-value threading, dominant pattern. Most command handlers, multi-tier query handlers, anything orchestrating across services.
- **`Bind` / `Map` / `ThenAsync` / `Match`**: genuine linear pipelines where state accumulates (sign-in, file processing, risk scoring).

### 6.6 Auto-validation via `Validator` property

Handlers declare a validator class; BaseHandler runs it before `ExecuteAsync`. Default null = no validation = pass through.

```csharp
public abstract partial class BaseHandler<THandler, TInput, TOutput>
{
    /// Override to declare this handler's input validator.
    /// Returning null (the default) means no validation runs.
    /// When non-null, validator runs BEFORE ExecuteAsync.
    protected virtual IValidator<TInput>? Validator => null;

    public async ValueTask<D2Result<TOutput?>> HandleAsync(...)
    {
        // ... existing OTel + activity setup ...

        // Auto-validation (NEW)
        if (Validator is { } validator)
        {
            var validationResult = await validator.ValidateAsync(input, ct);
            if (!validationResult.IsValid)
            {
                var errors = validationResult.Errors
                    .GroupBy(e => e.PropertyName)
                    .Select(g => new List<string> { g.Key }
                        .Concat(g.Select(e => e.ErrorMessage)).ToList())
                    .ToList();
                return D2Result<TOutput?>.BubbleFail(D2Result.ValidationFailed(inputErrors: errors));
            }
        }

        // ... existing ExecuteAsync invocation + exception handling ...
    }
}
```

## 7. Versioning

### Principles

1. **Version from day one.** Even if there's only ever one version in production, having the infrastructure in place means adding `v2` later is a config change, not a rewrite.
2. **One source of truth per concern.** No drift between where versions are declared.
3. **Conventional commits drive bumps.** No manual version juggling. The git history IS the changelog.
4. **Breaking changes get new versions, never modify in place.** `v1` is forever once shipped — even internally.
5. **Single product version, not per-package.** D2-WORX ships as one product on one cadence. Libraries and assemblies inherit the product version. Per-package independent versioning would be premature optimization for our scale.

### Per-concern rules

| Concern                    | Pattern                                                                                                                                                                                          | Status                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| **Proto packages**         | Directory + package versioning (`auth/v1/`, package `d2.auth.v1`). Buf-style.                                                                                                                    | Already in place, document the rule     |
| **REST URL**               | `Asp.Versioning.Http` v10+ with URL path versioning (`/api/v{version:apiVersion}/...`). One OpenAPI doc per version.                                                                             | Adopt the library                       |
| **NuGet package versions** | Central Package Management via `Directory.Packages.props`. `ManagePackageVersionsCentrally=true`. Single source of truth for every NuGet version across every `.csproj`.                         | Adopt                                   |
| **Internal libraries**     | Single repo-wide version inherited via `Directory.Build.props`. NO per-library versioning.                                                                                                       | Adopt                                   |
| **Node packages**          | All `@d2/*` (only what's left for SvelteKit) at `0.0.1`, `workspace:*` references. Not published externally.                                                                                     | Status quo for the small Node footprint |
| **Database migrations**    | Generator-driven (EF Core timestamps). Never hand-written.                                                                                                                                       | Already CLAUDE.md policy                |
| **Product version**        | Single semver triple in `server/d2-version/D2.Version.csproj`, bumped automatically by `versionize` from conventional commits. Drives assembly versions, CHANGELOG, git tags, Docker image tags. | Adopt                                   |

### Proto evolution rules

Within a `vN/` package, evolve schemas under these rules (per [Microsoft Learn](https://learn.microsoft.com/en-us/aspnet/core/grpc/versioning) and the [Protobuf Evolution guide](https://oneuptime.com/blog/post/2026-01-24-protocol-buffer-evolution/view)):

- **Never renumber field IDs.** Field numbers are wire-format identifiers. Renumbering silently breaks every existing client.
- **Deprecate before removing.** Use the `[deprecated = true]` option on a field that's being phased out. Generators emit warnings on use; the field stays wire-compatible until the next major version removes it.
  ```proto
  string old_email = 4 [deprecated = true];
  ```
- **Old `vN/` packages stay supported until explicit decommission.** Servers can implement multiple versions of the same RPC service simultaneously (e.g., `auth.v1.AuthService` AND `auth.v2.AuthService` in the same process). Decommission only when no client targets `vN`.

**Deferred** (add when value is concrete): the `reserved 5, 6;` / `reserved "old_field";` keyword for removed fields. It exists to prevent multi-team field-number collisions ("Team A removes field 5; Team B independently adds a new field 5 thinking it's free; on-wire payloads collide silently for old clients"). Single-team + pre-prod + greenfield = zero value vs real line noise. Adopt the day a real multi-team scenario makes the case concrete, not before.

### Breaking change policy

A change is **breaking** if any of these is true:

- A field is removed, renamed, or has its type changed
- A field's semantic meaning changes (units, allowed values, nullability rules)
- A field changes from optional to required (or vice versa for some clients)
- An RPC method or HTTP endpoint is removed or renamed
- An RPC method's input/output shape changes incompatibly
- An error code emitted by an existing endpoint changes
- A required HTTP header changes name or format
- A protocol-level behavior changes

**Response**: introduce a new version (`v2`) alongside the old. Old version supported until decommission window agreed.

When in doubt: assume breaking, bump version. Cost of wrong bump is small; cost of breaking a client mid-deploy is large.

### Non-breaking changes (safe to add to the current version)

- New optional fields with NEW field numbers (proto) or new optional properties (REST)
- New RPC methods or HTTP endpoints
- New message types
- Tightening validation that was previously too permissive — only if existing valid clients are unaffected
- Performance improvements with no observable behavior change
- New optional headers

### When to bump

**Pre-alpha (no external customers — current state)**: bump on demand when a meaningful chunk of work lands. Don't bump per commit. Let the conventional-commit log accumulate, then bump when:

- A logical feature is complete and would ship as a unit
- Before any deployment to a shared environment
- Before any tag worth referencing later

**Once we have customers**: bump on every release-worthy commit batch (typically once per sprint, or on-demand for security fixes).

### Deprecation timeline

When marking something deprecated:

1. **Now**: add deprecation marker (`[deprecated = true]` in proto, `[Obsolete]` in C#, `.IsApiVersionDeprecated()` for routes). Document in CHANGELOG under "Deprecations."
2. **Next minor**: emit warning logs / deprecation response headers when the deprecated thing is used.
3. **Next major**: remove. Update CHANGELOG.

**Pre-alpha compression**: this timeline can collapse to "deprecate and remove in the same release" since there are no customers to give notice to. Once we have customers, follow the full cadence.

**Required CI gates** — `integration-key-rotation` is non-skippable. Coverage:

- Graceful rotation under load (publishers + consumers; no message loss; in-flight old-kid messages still decrypt during grace)
- Grace expiry (retired kids removed from production keyring; stale messages → DLQ with explicit error)
- Emergency rotation (compromise marking is terminal; cannot be promoted back)
- Race conditions (rotation while N replicas publishing concurrently)
- Archive decryption (ops CLI fetches retired/compromised kids on demand)

## 9. Dev DX

### Docker Compose Watch + `dotnet watch` inside containers

Per [Docker Compose Watch docs](https://docs.docker.com/compose/how-tos/file-watch/) and Compose 2.25+ (Sept 2025 added `initial_sync`). Built INTO Docker Compose itself.

**Why this over Aspire**:

- **Maximum dev↔prod parity** (Compose syntax = Swarm `stack.yml` syntax — same shape between dev and prod, just different override files)
- No new tool to learn beyond what Compose already gives us
- `sync` action avoids `obj`/`bin` pollution that bind mounts cause
- Compose 2.25+ multi-service watch is now production-ready
- We don't lose anything Aspire would give us — our LGTM stack already provides the dashboard
- Aspire is its OWN orchestration model that doesn't match Swarm; adopting it means dev in one paradigm, prod in another

**Configuration shape** (`infra/compose/compose.dev.yml`):

```yaml
services:
  edge:
    build:
      context: ../..
      dockerfile: infra/docker/Dockerfile.edge
      target: dev # use the SDK image with dotnet watch
    environment:
      - DOTNET_USE_POLLING_FILE_WATCHER=1
      - ASPNETCORE_ENVIRONMENT=Development
    develop:
      watch:
        - action: sync
          path: ../../server/services/edge
          target: /src/server/services/edge
          ignore: [bin/, obj/]
        - action: sync
          path: ../../server/shared
          target: /src/server/shared
          ignore: [bin/, obj/]
        - action: rebuild
          path: ../../server/services/edge/**/*.csproj
        - action: rebuild
          path: ../../server/Directory.Packages.props
```

`dotnet watch` runs inside the container; Compose `sync` action copies file changes into the running container; `dotnet watch` picks them up via polling watcher.

**For SvelteKit**: standard Vite HMR, no special handling needed beyond exposing the HMR port.

### Audit framework anti-cheat tooling (design intent)

**Status: design only — implementation deferred to future deliverable.**

The current audit framework (`docs/dev/process.md` + `docs/dev/rules.md` + the 3-artifact markdown journal model) relies on agent discipline + structural sub-agent separation + adversarial framing to enforce evidence quality. The design intent below describes a JSON-first tooled successor that would mechanize the anti-cheat layer. None of the tooling described here is built; the markdown journal model remains canonical until/unless this lands.

**JSON-first artifact model.** The audit output becomes JSON, not markdown. Markdown views are GENERATED from JSON by a renderer for human readability, but JSON is the source of truth. Schemas live in `tools/audit/schemas/` (JSON Schema, or zod TS definitions). Sub-agents producing malformed JSON get rejected before output enters the journal.

Directory layout per step (design):

```
docs/wip/<deliverable>/<NN>-<step>/
├── README.md                          # plan, decisions, prerequisites (human-authored)
├── audit/
│   ├── round-1/
│   │   ├── implementer-report.json
│   │   ├── auditor-1-of-6.json       # partial big-table chunk
│   │   ├── auditor-2-of-6.json
│   │   ├── ...
│   │   ├── big-table.json             # aggregated canonical
│   │   └── validator-report.json      # output of validator script
│   ├── round-2/
│   │   └── ...
│   ├── findings/
│   │   ├── §1-tests.json              # category-indexed, append-only across rounds
│   │   ├── §3-pii.json
│   │   └── ...
│   ├── fix-log.json                   # chronological, append-only
│   └── README.md                      # rendered human-readable summary (auto-generated)
```

Big table row schema (JSON, design):

```json
{
  "section": "§3.1",
  "predicate": "[LoggerMessage] no Exception parameter",
  "status": "PASS",
  "verification": {
    "type": "recipe",
    "recipeId": "no-exception-in-loggermessage",
    "evidenceLocator": {
      "file": "server/shared/dotnet/auth/Telemetry/AuthLog.cs",
      "lineRange": [30, 92]
    },
    "evidenceContent": "[LoggerMessage(EventId = 1001, Level = LogLevel.Warning, ...)]",
    "evidenceHash": "sha256:abc123..."
  },
  "reason": null,
  "finding": null
}
```

**Three-layer mechanical anti-cheat (design):**

- **Layer 1 — Schema validator**: `tools/audit/validate-schema.js <json-file>` parses + schema-validates. Catches missing required fields, bad status enums, malformed evidenceLocator.
- **Layer 2 — Evidence verifier**: `tools/audit/verify-evidence.js <big-table.json>` walks every row and re-runs recipes / checks evidence claims against disk. If verification fails, the entire audit round is rejected.
- **Layer 3 — Recipe runners (proactive scanning)**: `tools/audit/run-recipes.js --step <NN>` runs every recipe-verifiable predicate against the step's files and produces a draft big table. Auditors START with this auto-generated draft and only need to manually walk the judgment-required predicates. Decimates auditor cognitive load.

**`rules.md` transformation — recipe / judgment / process buckets (design).** Each numbered subsection in `rules.md` gets classified:

- **Recipe-verifiable (~70% expected)** — checkable by a script. Each gets a `recipeId` + recipe definition file.
- **Judgment-required (~25% expected)** — requires agent judgment that no script can check. Stays as agent-walked predicates but FLAGGED as `judgment-required`.
- **Process-discipline (~5% expected)** — about HOW the audit runs, not WHAT the code looks like. Moves OUT of the auditor's checklist and INTO the orchestrator's logic.

Tooling layout (design):

```
tools/audit/
├── README.md                        # how to invoke + dev guide
├── schemas/                          # JSON Schema definitions
├── recipes/                          # one recipe file per recipe-verifiable predicate
├── orchestrate.js                    # state machine; main entry point
├── run-recipes.js                    # produces draft big-table.json
├── validate-schema.js                # JSON schema validation
├── verify-evidence.js                # re-runs recipes, checks evidence claims
├── render.js                         # JSON → markdown for human review
└── tests/                            # jest / vitest
```

**Buildout phases (design):**

| Phase | Task                                                                                         | Estimated effort |
| ----- | -------------------------------------------------------------------------------------------- | ---------------- |
| 1     | Build `validate-schema.js` + `verify-evidence.js` + JSON schemas. Baseline anti-cheat infra. | 1-2 days         |
| 2     | Convert `rules.md` predicates: classify into recipe/judgment/process buckets.                | 2-3 days         |
| 3     | Author recipe files for the recipe-verifiable bucket (~70% of predicates).                   | 3-5 days         |
| 4     | Build `orchestrate.js` state machine + `run-recipes.js` + `render.js`.                       | 1-2 days         |
| 5     | Update `CLAUDE.md` / `process.md` to reference JSON-tooled flow as canonical.                | 1 day            |
| 6     | Live-test on a real step. Iterate.                                                           | ongoing          |
| 7     | Backfill recipes for predicates that prove flaky in live tests.                              | ongoing          |

Recommended approach if work resumes: ship Phase 1 opportunistically — it would catch fabricated PASS rows in the current markdown journals immediately, even before the rest of the JSON-first artifact model lands.

**Open design decisions:**

1. **TypeScript vs vanilla JS** — TS gives schema definitions for free (zod) + better DX, but adds build step. Lean TS given the rest of the Node side is TS.
2. **Tie-breaker mechanism** when 2 Auditors disagree on a row — spawn 3rd Auditor as tie-breaker, OR escalate to user. Lean tie-breaker first, escalate if tie-breaker also conflicts.
3. **Recipe authoring incentive** — should recipe authors get to declare effort scaling? Probably yes for performance.
4. **Backwards compat with current journal markdown** — should the renderer produce markdown identical to current journal layout, or break compat with cleaner format? Lean break compat, optimize for new layout.
5. **What happens if a recipe itself has a bug** — false positive? false negative? Need a recipe-test suite.

### Local secrets & Claude deny rules

The pre-v2 setup has a single `.env.local` mixing config and secrets. Split it for safety against accidental Claude reads of real third-party credentials:

| File                   | Contents                                                                                      | Committed?                                      | Claude can read?    | Claude can edit?    |
| ---------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------- | ------------------- |
| `.env.local`           | Non-secret config — service URLs, ports, log levels, feature flags, CORS origins              | No (gitignored)                                 | **Yes**             | **Yes**             |
| `.env.local.example`   | Template with safe defaults                                                                   | **Yes**                                         | Yes                 | Yes                 |
| `.env.secrets`         | Real third-party creds — Twilio, Resend, IPinfo, OAuth client secrets, prod-like DB passwords | No (gitignored)                                 | **No (deny-ruled)** | **No (deny-ruled)** |
| `.env.secrets.example` | Template with placeholder values like `TWILIO_AUTH_TOKEN=replace_with_real_value`             | **Yes**                                         | Yes                 | Yes                 |
| `secrets/`             | Key material — root key, dev encryption keys, dev TLS certs                                   | No (gitignored, populated by `gen-dev-keys.sh`) | **No (deny-ruled)** | **No (deny-ruled)** |

Compose loads both env files (`.env.local` first, `.env.secrets` second so secrets override placeholders if any collision):

```yaml
services:
  edge:
    env_file:
      - .env.local
      - .env.secrets
```

**Workflow when adding a new secret**:

1. Edit `.env.secrets.example` adding `NEW_THING_API_KEY=replace_with_real_value`
2. Update Compose to load it into the right service
3. Tell the operator: "Added `NEW_THING_API_KEY` — copy into `.env.secrets`, set the real value, restart the service"
4. Operator manually syncs

Same pattern for encryption keys: update `tools/scripts/gen-dev-keys.sh` to generate keys for new domains; operator runs the script; output lands in `secrets/`.

**`.claude/settings.json` (committed at repo root)**:

```json
{
  "permissions": {
    "deny": [
      "Read(**/.env.secrets)",
      "Write(**/.env.secrets)",
      "Edit(**/.env.secrets)",
      "Read(**/secrets/**)",
      "Write(**/secrets/**)",
      "Edit(**/secrets/**)",
      "Read(**/*.pem)",
      "Read(**/*.key)",
      "Read(**/.npmrc)",
      "Read(**/.aws/**)",
      "Read(**/.ssh/**)",
      "Bash(cat **/.env.secrets*)",
      "Bash(cat **/secrets/**)",
      "Bash(less **/.env.secrets*)",
      "Bash(head **/.env.secrets*)",
      "Bash(tail **/.env.secrets*)"
    ]
  }
}
```

The exact-match `**/.env.secrets` deliberately does NOT match `.env.secrets.example` — the template file remains fully editable. Bash entries plug the obvious workaround paths.

**Caveats** (the leak paths the deny rules don't cover):

- **Runtime output** — services that log credentials to stdout will leak. Already mitigated by "don't start services manually" + `[RedactData]` on connection-string types. Reaffirmed in CLAUDE.md.
- **Grep** — Grep is a separate tool; if `Read(...)` deny doesn't transitively block it, CLAUDE.md adds a behavioral rule: never `Grep` the `secrets/` directory or `.env.secrets` file by name.
