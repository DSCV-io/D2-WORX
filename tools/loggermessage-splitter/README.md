# tools/loggermessage-splitter

> Parent: [`../README.md`](../README.md)

A small .NET 10 console tool that splits the single `LoggerMessage.g.cs` file emitted by `Microsoft.Extensions.Logging.Generators` into one **deterministic per-class** file under the same generated-files directory.

## Why this exists

`Microsoft.Extensions.Logging.Generators` (v10.0.14.21808) emits **all** `[LoggerMessage]`-decorated partial-class blocks into a **single** `LoggerMessage.g.cs` file. The emitter's **cross-class ordering is non-deterministic** — same source, three consecutive `dotnet build` invocations produce three different blob hashes.

This is a problem because:

- Every consumer of `Microsoft.Extensions.Logging.Generators` in this repo sets `EmitCompilerGeneratedFiles=true` and tracks the `Generated/` tree in git, so PR reviewers can see codegen diffs without a local build (per the framework convention documented in each consumer csproj).
- Non-deterministic cross-class order means every clean build looks like a diff, even with zero source change — constant churn for nothing.

The simple fix would be to gitignore the combined file, but that defeats the PR-review convention. Instead, this tool parses the combined file into one file per partial class. The filenames + per-file contents are deterministic; the combined file itself is gitignored.

## How it's wired

`server/shared/dotnet/Directory.Build.targets` defines two targets:

1. `EnsureLoggerMessageSplitterBuilt` — invokes `<MSBuild>` on this tool's csproj (incremental, fast on no-op, cached by the `<MSBuild>` task across consumer csprojs within one build session).
2. `SplitLoggerMessageGcs` — `AfterTargets="Compile"`, conditional on `Exists($(_LoggerMessageGcsPath))`. Runs `dotnet exec` against this tool's DLL with `--input` and `--output-dir`.

Result: every csproj under `server/shared/dotnet/` that emits a `LoggerMessage.g.cs` file (currently messaging-rabbitmq, auth, auth-outbound, encryption) automatically gets its combined file split into per-class files on every `dotnet build`.

## CLI

```bash
dotnet run --project tools/loggermessage-splitter -- \
  --input <path-to-combined-LoggerMessage.g.cs> \
  --output-dir <directory-to-write-split-files-to>
```

Both args required. The tool exits 0 on success or when the input file does not exist (the MSBuild target gates on `Exists()`, but the tool also handles the no-input case gracefully). Exit 1 = parser error (malformed input). Exit 2 = bad args.

## Output filename convention

```
LoggerMessage.{NamespaceLastSegment}.{ClassName}.g.cs
```

Examples (from messaging-rabbitmq):

```
LoggerMessage.Channels.ChannelPoolLog.g.cs        D2.Shared.Messaging.RabbitMq.Channels.ChannelPoolLog
LoggerMessage.Connection.RabbitMqConnectionLog.g.cs  D2.Shared.Messaging.RabbitMq.Connection.RabbitMqConnectionLog
LoggerMessage.Subscribing.SubscriberLog.g.cs      D2.Shared.Messaging.RabbitMq.Subscribing.SubscriberLog
LoggerMessage.Telemetry.MessagingLog.g.cs         D2.Shared.Messaging.RabbitMq.Telemetry.MessagingLog
LoggerMessage.Topology.TopologyLog.g.cs           D2.Shared.Messaging.RabbitMq.Topology.TopologyLog
```

Each file carries the same header (`// <auto-generated/>` + `#nullable enable` + blank line) followed by a single `namespace X { partial class Y { ... } }` block.

## Determinism guarantees

- Output filenames are deterministic from `(NamespaceLastSegment, ClassName)`.
- Per-file content carries the single class block — no cross-class ordering inside any file.
- The combined input's block-order does not affect any individual output file's content (each class block is parsed + emitted standalone).
- Stale per-class files in the output dir that don't match a class in the current input are **deleted** on each run, so removing a `*Log` class from source cleans up its split file.
- The tool skips writes when content is byte-identical to what's already on disk, so mtime is preserved across re-runs (no spurious incremental-build re-triggers).

## Design rationale: custom parser over Roslyn

The combined file's format is simple + stable (the emitter is a small Microsoft project, the output shape changes rarely). A line-based brace-depth parser is ~70 lines of clean C# vs. pulling in `Microsoft.CodeAnalysis.CSharp` (multi-megabyte dependency, slow cold-start). The parser handles both extension-method form (`public static partial void X(this ILogger logger, ...)`) and plain-static form (`public static partial void X(ILogger logger, ...)`), as well as nested structs that the emitter generates for log methods with `>6` parameters.

## Maintenance

If a future emitter version changes the output shape (e.g. adds a `using` block, changes the `namespace` brace style, decorates classes with extra modifiers), the parser is the right place to extend. `SplitterEngine.ParseBlocks` is the entry point; `ContainsPartialClass` + `ParseClassBlock` handle the per-class extraction.

If you change the tool's source code, the next `dotnet build server/D2.slnx` will incremental-rebuild the splitter DLL before invoking it — no manual rebuild needed.

## Not in the framework solution

This tool is NOT registered in `server/D2.slnx`. It's a stand-alone build-time tool. The MSBuild target builds it on demand via the `<MSBuild>` task.
