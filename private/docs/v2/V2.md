## 1. Context & Scope

D2-WORX v1 was a polyglot system: .NET (Geo, Gateway, SignalR) + Node.js (Auth, Comms, Files) + SvelteKit (web). It accumulated ~5 ingress points, 3 layers of cross-cutting middleware duplicated per service, parity-driven shared abstractions on both sides, and an architecture that made adding new services costly.

**v2 (`nova` branch) is a structural rewrite**, not a refactor:

- **Backend collapses to .NET only.** Every Node.js service is rewritten in .NET. SvelteKit is the only remaining Node footprint (it's the trusted web client).
- **A unified Edge service** absorbs today's Gateway + SignalR + Auth + WhoIs + cross-cutting middleware into one process.
- **Geo decomposes** into shared libraries (no Geo service exists in v2).
- **Comms splits** into D2.Courier (outbound delivery) + D2.Notifications (in-app feed). D2.Threads is a future deferred concern.
- **DcsvIo.D2.Private.Audit** is added as a separate service for tamper-evident audit logging.
- **Files port** from Node.js to .NET, with SeaweedFS replacing MinIO for object storage.

**Scope of this document:** the architectural target, all settled decisions, the project structure, the patterns that govern new code, the versioning policy, the testing strategy, and the implementation sequence.

**What this document is NOT:** an active progress tracker, a sprint plan, or a feature roadmap. Those concerns are out of scope.

### Key structural decisions

- **`server/` (singular)** — only one trusted-code language now (.NET); SvelteKit goes here because it has a backend half. Plural `backends/` was honest when we had .NET + Node.js services; singular is honest now.
- **`private/services/{service}/{layer}/`** — drop the redundant `{Service}.{Layer}/` folder name. Folder is `app/`, csproj is `D2.{Service}.App.csproj`. Saves 1 folder level.
- **`private/services/{service}/clients/{language}/`** — forward-proofs polyglot consumers. Edge has no `clients/` (entry point); Files / Courier / Notifications / Audit have `clients/dotnet/` for their .NET client libs. Adding a future `clients/typescript/` is just dropping a folder in.
- **`public/packages/dotnet/{lib}/`** — drop the `Implementations/Caching/Distributed/` nesting. Was: `shared/Implementations/Caching/Distributed/DistributedCache.Redis/`. Now: `shared/dotnet/caching-distributed-redis/`. **Saves 3 folder levels.**
- **`public/packages/typescript/`** — exists with just a README initially. When the first cross-language pattern (e.g., a Result type or Handler shape mirror) needs to be shared with future TS web clients, packages land here. No pnpm workspace until then.
- **`infra/`** — consolidates `/docker/`, `/docker-compose*.yml`, `/observability/` from v1. Repo root no longer has compose files.
- **`docs/`** — non-essential `.md` files move out of root. Only README, CLAUDE, CHANGELOG, CONTRIBUTING, LICENSE, V2 stay at root.
- **All .NET configs in `server/`** — `Directory.Build.props`, `Directory.Packages.props`, `global.json`, `NuGet.config`, `stylecop.json`, `D2.slnx` all live under `server/` (they cascade downward to all `.csproj`). Repo root stays clean.
- **No more pnpm workspace at root** — SvelteKit is the only Node project; it's standalone with its own `package.json` at `private/services/web/`. Workspace returns when there's a real second TS package.

### Folder casing convention (lowercase outer + PascalCase inner)

Apply consistently across the whole repo:

- **Folders OUTSIDE a project** (csproj-grouping, organizational) → **lowercase**, kebab-case for multi-word
  - Examples: `server/`, `services/`, `edge/`, `app/`, `clients/`, `dotnet/`, `caching-distributed-redis/`, `geo-reference/`, `service-defaults/`, `infra/`, `tools/`, `docs/`
- **Folders INSIDE a project** (namespace-mapping, where Rider auto-creates folders from namespace operations) → **PascalCase**
  - Examples (inside `private/services/edge/app/`): `Application/`, `Handlers/`, `Commands/`, `Queries/`, `Observability/`, `Infrastructure/`, `Persistence/`, `Vault/`, `Configuration/`
- **`.cs` file names** → **PascalCase** (matches the type they contain — one-class-per-file convention)
- **`.csproj` file names** → **PascalCase**, dot-separated (`DcsvIo.D2.Handler.csproj`) — the csproj filename IS the assembly name; appears in error messages, logs, telemetry
- **Namespaces and type names** → **PascalCase** (C# language convention)

The rule: **if Rider auto-generates a folder from a namespace operation, that folder must be PascalCase. Anything else is lowercase.**

Why this works:

- The C# compiler doesn't read folder names; namespaces are declared at the top of files independently
- Cross-platform safety (Linux/macOS are case-sensitive; lowercase removes a class of "works on my machine" bugs)
- Visual consistency at the top level with non-.NET parts (`contracts/`, `infra/`, `tools/`)
- Inner project folders that DO map to namespaces stay PascalCase, so Rider's "Add Class" / "Move to namespace" operations work without friction

Minor friction: `dotnet new` defaults to PascalCase folders. Workaround: `mkdir handler && cd handler && dotnet new classlib -n DcsvIo.D2.Handler` (folder name and csproj name decoupled). Could codify in the Makefile (`make new-lib name=Handler` does the right thing).

### What's gone vs v1

- ❌ `d2-gateway` (.NET REST facade) — endpoints absorbed into Edge
- ❌ `d2-signalr` (.NET SignalR gateway) — hubs absorbed into Edge
- ❌ `d2-auth` (Node.js + BetterAuth) — replaced by Auth module inside Edge, self-rolled .NET
- ❌ `d2-geo` (.NET Geo service) — reference data → embedded library, WhoIs → Edge module, Contacts → folded owned-component library (see ADR-0001)
- ❌ `d2-comms` (Node.js) — replaced by D2.Courier + D2.Notifications
- ❌ Per-service rate-limit / fingerprint / JWT / idempotency / CORS middleware (5× duplication today)
- ❌ "Contacts service" as originally envisioned — replaced by contacts folded into each consuming service's own entities via `DcsvIo.D2.Contacts` (see §5.6 Revised / ADR-0001; the earlier per-consuming-service-DB plan is superseded)

**Net container count change**: today's `gateway + signalr + auth + geo + files + comms + sveltekit + dkron-mgr` → tomorrow's `edge + files + courier + notifications + audit + sveltekit + dkron-mgr`. Net **−1** application container, but with a vastly cleaner boundary set.

## 4. Phasing

Build order is bottom-up: foundational shared libraries first, then domain-specific shared libraries, then services in dependency order (Edge before its consumers; Audit before Comms because Comms publishes audit events; Comms before Files because Files publishes notification events; SvelteKit last because it consumes everything).

Everything in v2 is built fresh from scratch (using `/old/v1/` as reference) — no extracting, no porting, no in-place modifying. The wipe deletes v1 entirely; phases below build the v2 implementation from a clean slate.

## 5. Stack Decisions

### 5.1 Backend Language & Orchestration

- **Language**: .NET 10 (C# 14) for all backend services. SvelteKit is the only Node footprint.
- **Orchestration**: Docker Swarm + Portainer in production until the business is making the kind of money that warrants scaling past ~3 machines. K8s is explicit overkill at this scale.
- **HTTP/REST**: ASP.NET Core 10 minimal APIs.
- **gRPC**: Built-in `Grpc.AspNetCore` for inter-service communication.
- **EF Core 10** with `Npgsql.EntityFrameworkCore.PostgreSQL` for persistence.
- **Async**: RabbitMQ via `RabbitMQ.Client` 7.x (low-level, no MassTransit).
- **Sync inter-service**: gRPC (HTTP/2) — default for everything internal.

**gRPC contract documentation**: internal gRPC services get first-class contract docs via the C0 unified operation-contract IDL. An operation is authored once in TypeSpec; `.proto`, per-endpoint policy metadata, route registrations, and docs are all generated outputs — proto is a generated artifact, not the hand-authored spec. The `@d2*` decorator vocabulary on each op is the single source of truth; the same declaration drives doc generation and runtime enforcement across all three transport planes (external REST/JSON, internal gRPC, in-process). Identity and request-context propagation work identically for gRPC and HTTP paths because gRPC runs over HTTP/2 inside ASP.NET Core — same auth pipeline, same `IRequestContext`. See [ADR-0021](../adrs/0021-unified-operation-contract-idl.md) for the full design and [PHASE_3.md](PHASE_3.md) for build sequencing.

### 5.2 Edge — Unified Gateway

The Edge is one .NET process bundling:

- **Reverse proxy**: `Yarp.ReverseProxy` 2.3+ for HTTP routing to backend services. YARP IS the load balancer for backends.
- **Self-rolled Auth** — no framework wrapper. `Microsoft.IdentityModel.Tokens` + `IDataProtectionProvider` + `AuthorizationPolicyBuilder` + `Microsoft.AspNetCore.RateLimiting` + `Antiforgery` + `IHostedService` are framework primitives, not framework flow control. We compose. **No** IdentityServer, OpenIddict-as-framework, or ASP.NET Identity-as-framework.
- **SSE hub** for real-time push.
- **In-process WhoIs lookup** via existing IPinfo HTTP client.
- **All cross-cutting middleware** (rate limit, request enrichment, JWT validation, idempotency, fingerprint, CSRF, CORS) in one place.

**Production topology**:

- **Early**: single Edge instance behind Cloudflare (DNS, TLS, WAF).
- **HA**: multiple Edge instances behind a Layer 7 LB (Cloudflare candidate). L7 because Edge is stateful via SSE connections. Backplane for cross-instance push via Redis.

**Why bundle vs split**: Edge is the only place that needs to know about both HTTP request handling AND SSE connection state for the same user session. Splitting them duplicates session lookup. Bundling them means session state lookup happens once per request.

**OpenAPI documentation**: the per-version OpenAPI documents (`/openapi/v1.json`, etc.) and their `x-d2-*` policy extensions are generated from the op contract via ADR-0021's emitter fleet — `@d2*` decorators on each operation produce both the route registration and the OpenAPI binding. `Microsoft.AspNetCore.OpenApi` + `Asp.Versioning.OpenApi` serve one document per API version; Scalar (`Scalar.AspNetCore`) renders the UI. The hand-authored attribute + transformer pattern this subsection described is superseded by the IDL — see [ADR-0021](../adrs/0021-unified-operation-contract-idl.md) for the current design.

### 5.3 Operation Risk Tier (cross-cutting)

**Decision (refined):** do **not** overload one enum for everything. **Two orthogonal axes** (see §5.4 rate-limit paragraph below and [PHASE_3_RATE_LIMITING.md](PHASE_3_RATE_LIMITING.md)): `RateLimitTier` (Standard/Elevated/Restricted — abuse cost / fail-open vs fail-closed) vs `ActionSensitivity` (Routine/Sensitive/Critical — step-up, audit, impersonation). IDL `@d2*` decorators still emit both. Older “one Public/Standard/Elevated/Critical drives all middleware” wording is **superseded** by that split.

**Why two axes (not one):** blast radius splits into **traffic abuse** (`RateLimitTier`) vs **damage if the action succeeds** (`ActionSensitivity`). Auth-required is a separate route/policy concern (unauthenticated + Restricted is normal for sign-in). Platform floors stay hard; individuals may loosen some security prefs down to floor ([PHASE_3_AUTH_CORE.md](PHASE_3_AUTH_CORE.md) §10). Critical-class impersonation blocks remain non-overridable.

Full four-tier table (per-tier defaults, rate-limit caps, risk thresholds, impersonation defaults, brute-force override pattern, Security Policy interaction, and code examples): [PHASE_3_RATE_LIMITING.md §12](PHASE_3_RATE_LIMITING.md#12-operation-risk-tier-cross-cutting).

### 5.4 Auth & Security

#### Auth as a module within Edge (with its own DB)

Edge is a service; **Auth is a module within Edge**. Despite living in the same process, the Auth module owns a complete, isolated database — `d2-auth` — for clean separation of concerns. Other Edge modules (SSE push, WhoIs, YARP routing, cross-cutting middleware) do not access `d2-auth` directly; they go through the Auth module's internal interfaces.

**`d2-auth` schema (owned tables)**:

- `user`, `org`, `member`, `invitation` — identity model (replaces v1 BetterAuth tables)
- `account` — linked external auth providers (Google, etc.)
- `session` — durable session storage (also dual-written to Redis cache; see Sessions below)
- `oauth_client` — OAuth client registry. The internal-workload **token**-based service-identity surface was retired in deliverable 0023 (mTLS supplies backend workload identity per [ADR-0023](../adrs/0023-mtls-workload-identity.md)). The `oauth_client` table survives as the registry for genuinely-external boundary-token clients; the BFF is NOT one (mesh-member workload per the 2026-07-03 ruling — mTLS leaf, direct internal calls, Edge-attached transaction tokens) — **Auth Core (A2)** domain/storage; mint path that *uses* clients is **Minting (A3)** per [PHASE_3.md](PHASE_3.md) spine (**Auth Core → Minting → Auth Extras**).
- `impersonation_consent` — per-(user, granting-org) consent grants for support impersonation
- `sign_in_event` (aka `sign_in_attempt` in [PHASE_3_AUTH_CORE.md](PHASE_3_AUTH_CORE.md)) — every sign-in attempt with risk score, IP, fingerprint, country, etc. **Lives in `d2-auth`** (not `d2-audit`) because it's queried at sign-in time for risk scoring ("does this user usually sign in from this country / IP / fingerprint?"). Audit events for sign-ins are ALSO published to `d2.audit.events` for the central audit trail; both stores have the data, with different access patterns.
- `security_policy_org`, `security_policy_user` — per-org and per-user policy framework (see "Security Policy framework" below)
- `verification` — short-lived email/OTP verification tokens

#### Sessions (3-tier)

- **Cookie cache** (5min compact session info, signed via `IDataProtectionProvider`) for fast happy-path
- **Redis** for session lookup
- **`d2-auth`'s `session` table** for durable storage (dual-write pattern: write Redis first for happy-path latency, then async-write to PG for durability; on cache miss, read PG and re-populate Redis)

Cookie is opaque (HttpOnly, Secure, SameSite=Lax) for browser. Mobile / CLI / B2B use bearer tokens.

#### Anon-visitor authentication — Pattern A (mint short-lived anon JWT at Edge)

> Locked 2026-05-11. Authoritative design lives in
> [`private/docs/v2/PHASE_3_AUTH.md`](PHASE_3_AUTH.md#38-anon-visitor-authentication-pattern--pattern-a-locked-mint-anon-jwt-at-edge)
> §3.8 + Q23. Implementation is Phase 3 Edge work — not in `DcsvIo.D2.Auth` (the inbound runtime
> already supports the contract via the trinary `IRequestContext.IsAuthenticated`,
> `Scopes.AllAnonymousScopes`, and `Scopes.IsAnonymous`).

Edge mints a short-lived anon-session JWT for every unauthenticated visitor — every request
reaching a backend service carries a validated JWT (anon or user). The anon JWT carries
`d2_kind: "anonymous"`, an `anon:<uuid>` `sub` mapped 1:1 to a 3-tier session via the cookie,
and tamper-evident enrichment claims (`d2_whois_id`, optional `d2_fingerprint_score`).
Sign-in elevates the same session to a user JWT (same cookie, same `d2_session_id`); sign-out
mints a fresh anon-session for continuity (cookie-presence stops being a frontend-side auth
signal — `IRequestContext.IsAuthenticated` is the discriminator).

Implications for downstream design (full list in PHASE_3_AUTH.md §3.8):

- **Rate-limiting** keys collapse to JWT claims — see
  [`private/docs/v2/PHASE_3_RATE_LIMITING.md`](PHASE_3_RATE_LIMITING.md) §11 for the post-Pattern A bucket-keying.
- **CSRF gates** branch on `d2_kind: "anonymous"`, not cookie presence.
- **Audit propagation** distinguishes anon vs authed via `IsAuthenticated`.
- **Risk engine** keys historical-pattern signals on `d2_session_id` (longer-lived than the
  per-JWT `sub`).

#### Key Custodian (module within Edge, peer to Auth)

KeyCustodian is a peer module to Auth inside Edge — same process, independent `d2-keycustodian`. It owns the lifecycle of every long-lived secret: JWKS signing keys (RS256, 90-day rotation), message payload encryption keys (AES-256-GCM per domain, quarterly), cookie signing secrets, and OAuth `client_secret`s for the surviving boundary-token clients (genuinely-external clients of Edge only — the BFF is no longer one of these per the 2026-07-03 mesh-member ruling; see "BFF Trust & Privilege Boundary"). The token-based internal-workload service-identity surface was retired in deliverable 0023; migrating the managed-secret set off `client_secret`s onto CA-key + leaf-cert custody remains an Edge-gated follow-up (tracked in [PHASE_3.md](PHASE_3.md) §Deferred-work checklist §A). All keys are root-wrapped at rest (`DcsvIo.D2.Encryption`); the root key is an operator-managed file mounted at `secrets/keycustodian/root.key`. Full key lifecycle, state machine (Pending → Active → Retiring → Retired; Compromised terminal), rotation cadences, distribution model (`KeyringClient` pull + `d2.security.key-rotated` RMQ push), emergency-rotation CLI, and compromise runbook: [ADR-0016](../adrs/0016-keycustodian-lifecycle-store.md) + [PHASE_3_AUTH.md](PHASE_3_AUTH.md) §15a.

> **2026-07-06 (0026 Cycle 3 — sealed messaging auto-wired + one-way ruling):** The `audit` / `notifications` / `courier` encryption domains are now per-service **sealed** (asymmetric P-256 ECDH-ES → HKDF-SHA256 → AES-256-GCM to the consumer service's public key), declared as `mode: sealed` + `consumerService` in `contracts/encryption-domains`. The messaging layer auto-seals on publish / auto-opens on consume with zero per-message hand-code (`EncryptedBodyComposer` + the KC-backed sealer/opener runtime, both .NET and TS). Under this one-way ruling these three domains LEFT the KC **symmetric** payload catalog entirely — they have no symmetric keyring/lifecycle existence (one-way by construction: a service can only open what is sealed to it, never re-encrypt-and-read). The domain-generic symmetric keyring machinery (`getKeyring` + authority + rotation hot-swap) is PRESERVED for any future `mode: symmetric` domain. Because the three domains no longer rehydrate through the symmetric catalog, any existing local dev `d2-keycustodian` must be reset once (drop/recreate the volume) — pre-alpha, no production deployments. See [ADR-0009](../adrs/0009-async-messaging-encrypted-payloads.md) (sealed-mode amendment) + [PHASE_3_AUTH.md](PHASE_3_AUTH.md).

#### Internal token issuance — mint once at the Edge boundary, forward unchanged

**Decision** ([ADR-0022](../adrs/0022-service-auth-mint-once-forward.md) + [ADR-0023](../adrs/0023-mtls-workload-identity.md)): Edge mints **exactly one** internal transaction-token at the trust boundary; every downstream cross-process hop forwards it byte-for-byte and independently re-validates it. No per-hop re-mint. RFC 8693 `grant_type=token-exchange` is the wire shape for the boundary mint and deliberate exceptions (cross-trust-domain calls, targeted narrowing, async scope reduction, impersonation) — not the per-hop default. Internal workload identity (which service made a call) is mTLS — KeyCustodian-issued per-workload certificates — strictly additive to the forwarded token. The `X-D2-Internal-Token` boundary token survives only for genuinely-external clients of Edge; the SvelteKit BFF is NOT one — it is a mesh-member workload that holds a KC-issued mTLS leaf and forwards the Edge-minted transaction token as the first internal hop ([ADR-0023](../adrs/0023-mtls-workload-identity.md) 2026-07-02 amendment; see "BFF Trust & Privilege Boundary").

JWT shape: RS256, ~15min TTL, `aud=d2.internal`, JWKS at OIDC-canonical `/.well-known/jwks.json`. Custom claims prefixed `d2_` (`d2_org_id`, `d2_org_type`, `d2_org_role`, `d2_session_id`, `d2_username`, `d2_fp`; optional `act` for impersonation chain). Full custom-claim catalog: `JwtClaimTypes` in `DcsvIo.D2.Auth.Abstractions` + spec `contracts/jwt-claims/jwt-claims.spec.json`. Scopes (the `scope` claim, OAuth-canonical space-separated string) are static `const string` members in `DcsvIo.D2.Auth.Scopes` with `service.resource.action` naming — no DB catalog, no admin UI. Wildcard expansion happens at JWT mint time; backends see only exact strings. Full auth design: [PHASE_3_AUTH.md](PHASE_3_AUTH.md).

#### Impersonation only (no emulation)

Org emulation removed. Only mechanism for staff/admin to access another user's data is impersonation via the RFC 8693 `act` chain — two flavors: consent-based (OTP to user's email, `auth.user.impersonate` scope) and force (admin-org-only, `auth.user.impersonate.force`, silent). Critical actions stripped via `[ImpersonationBlocked]` scope narrowing at JWT mint time. Time-limited (15m / 30m / 1h / 2h slider). Full impersonation design including JWT shape, `act` chain, and `[ImpersonationBlocked]` list: [PHASE_3_AUTH.md](PHASE_3_AUTH.md).

#### Adaptive authentication (risk-based auth)

**Fingerprint binding**: composite `d2_fp` claim with 10 sub-components in fixed slot order (`v1.c1.c2.c3.c4.c5.s1.s2.s3.s4.s5`) — 5 client-side (FingerprintJS-OSS extended) + 5 server-side (HTTP/2 SETTINGS, header order, Client Hints, Accept-Encoding, Accept-Language). Per-component SHA-256 (first 16 hex chars). Server-side signals are unspoofable from a malicious JS environment. Two fingerprints per request: `SessionFingerprint` (bound at JWT mint, `d2_fp` claim, propagated via AMQP) and `CurrentFingerprint` (recomputed per-request at Edge, not propagated). Per-slot diff drives risk-score contribution; slot-version bump (`v1`→`v2`) required to change any slot's meaning. Estimated uniqueness ~97-98%. Full slot table and forward-compat rules: [PHASE_3_AUTH.md](PHASE_3_AUTH.md).

**Risk scoring**: composite `IRequestContext.RiskScore` (0–100, higher = riskier) from fingerprint diff, impossible-travel geo-velocity, ASN/Tor/proxy/datacenter flags, country allowlist, burst rate, and per-org/per-user security policy thresholds. Risk < step-up → allow; ≥ step-up → OTP step-up; ≥ block → block + invalidate session. Full risk-scoring formula and persistence model: [PHASE_3_AUTH.md](PHASE_3_AUTH.md).

**Security Policy**: three-level monotonically-restrictive hierarchy (platform_minimum ← org_policy ← user_policy). Tunable dimensions: step-up/block thresholds, impossible-travel limit, country allowlist, ASN/Tor policy, MFA requirement, session lifetime, idle timeout. Platform-fixed: 12-char minimum password, email verification always required. Compliance is on-demand per org-selection — not sign-in time. Full dimensions table and enforcement model: [PHASE_3_AUTH.md](PHASE_3_AUTH.md).

**WhoIs pass-down**: Edge does one IPinfo lookup per request (small in-memory dedup cache) and encodes the result as `X-D2-WhoIs` (JSON → base64url) for downstream services. Backend services never call IPinfo. No Redis/DB cache layer — Edge in-process cache only.

**Magic-link / guest sensitive ops**: sensitive operations callable by non-account-holders use Edge-minted short-lived scoped tokens (not a new risk tier — the endpoint stays `Elevated`/`Critical` and the token is the auth). Pattern covers invoice payment links, email verification, password reset, OTP, and "review and approve" workflows.

**ClamAV**: single container on `internal` network; Files service uses `nClam` over TCP. If ClamAV is down, file uploads return 503 — no silent bypass.

### 5.5 Real-Time (SSE)

#### Auth lifetime — handshake-only + targeted revocation

**SSE connections** authenticated **only at the connect request**. The JWT presented on the `GET /realtime` (SSE) request is validated; once the stream is open, no recurring re-check. Connections survive their connect-time JWT's expiry. **Targeted revocation** delivered out-of-band via a `session.revoked` **SSE event** + server-side force-close.

**Why**: industry standard for long-lived push (Slack, Discord, Teams, GitHub live updates, AppSync, Firebase all authenticate the stream at connect, not continuously). Periodic re-auth or kick-on-exp breaks UX (every user disconnected every 15min, reconnect storms, missed pushes during reconnect) for negligible security gain.

**SSE protocol-level liveness**:

- Server emits periodic heartbeat comments (`: ping\n\n`) to keep idle streams from being reaped by intermediaries (interval tuned at E4).
- The browser `EventSource` auto-reconnects natively on drop (server-suggested `retry:` backoff); resume uses the `Last-Event-ID` request header for at-least-once replay of buffered events.
- No SignalR-style `KeepAliveInterval` / `ClientTimeoutInterval` knobs — SSE liveness is the heartbeat-comment + native-reconnect pattern.

**Connection cap**: **10 per user, FIFO eviction**.

**"Reconnecting…" indicator**: show after 5s of disconnected state.

#### Three categories of client-facing events

| Category                         | Trigger                                    | Transport                                                 | Toast              | Persist | Examples                                                                                             |
| -------------------------------- | ------------------------------------------ | --------------------------------------------------------- | ------------------ | ------- | ---------------------------------------------------------------------------------------------------- |
| **Sync UI feedback**             | REST request returns success               | None — SvelteKit reacts to its own `await fetch()` result | Yes                | No      | "Profile updated", "Copied to clipboard", form errors                                                |
| **Async work-completion signal** | Server-side work the user started finishes | **SSE push (fire-and-forget)**                            | Yes                | **No**  | Avatar processed, file scan complete, image variants generated                                       |
| **Entity notification**          | Domain event the user may not have started | **SSE push as optimization + persistent store**           | Yes (foregrounded) | **Yes** | "Alice signed in from a new device", "Your monthly report is ready", "@-mention", "Payment received" |

**The deciding question** for which category an event falls into: **"if the user misses the SSE push entirely, is the state still discoverable in-place?"** Yes → category 2. No → category 3.

**SSE push layering**: the SSE push API is owned by Edge's SSE gateway (`PushToChannel`, `RemoveFromChannel`; channels `user:<id>` / `session:<id>` / `org:<id>`). Notifications is one consumer among many — Files, Auth, and any service with auth can call the push API. Org-wide notifications are a Notifications-service Category-3 roster fan-out, not an `org:` channel broadcast (`org:` is for live presence/collaboration among active members). Mobile backgrounded delivery deferred — APNs/FCM fed from the same pipeline when needed. Targeted revocation: Edge Redis-tracks `session_id → [connection_ids]`; on revocation, emits `session.revoked` SSE event + force-closes connections + invalidates session in 3-tier store; browser redirects to sign-in.

#### Rate limiting

> **Authoritative design lives in [`private/docs/v2/PHASE_3_RATE_LIMITING.md`](PHASE_3_RATE_LIMITING.md).** This subsection is a 3-paragraph summary; the dedicated doc covers the full design, bucket math, kill-switch hierarchy, FP-too-common detection, and Edge implementation guidance.

**Two orthogonal axes — kept distinct.** `RateLimitTier` (`Standard` / `Elevated` / `Restricted`) is an Edge endpoint attribute that captures "how costly / abusable is this endpoint?" and lives ONLY at the Edge. `ActionSensitivity` (`Routine` / `Sensitive` / `Critical`) is per-scope claim metadata that captures "how dangerous is this action if it succeeds?" and drives audit verbosity / step-up / impersonation defaults. A sign-in endpoint is `Routine` × `Restricted`; an admin destructive endpoint is `Critical` × `Standard`. The two never get cross-wired (distinct enums, distinct vocab).

**Rate limiting + fingerprinting (O23/O24 design SoT):** [PHASE_3_RATE_LIMITING.md](PHASE_3_RATE_LIMITING.md) + [PHASE_3_FINGERPRINTING.md](PHASE_3_FINGERPRINTING.md). Token-bucket AND of ceilings; identity by O24 confidence (`deviceKey` / IP / userId); WhoIs dirty flags tighten caps; too-common falls back to IP (not global iPhone bucket); cookie-shortcut **superseded**. Kill switches + Restricted fail-closed retained. Session elevate is visit glue only — not sole Restricted key.

**Risk vs rate limit (separate):** traffic budgets = token buckets ([PHASE_3_RATE_LIMITING.md](PHASE_3_RATE_LIMITING.md)); semantic sketchiness = RiskScore → step-up / block / session revoke ([PHASE_3_FINGERPRINTING.md](PHASE_3_FINGERPRINTING.md)). No mandatory “429 → risk → tighter burst” coupling (optional analytics only).

### 5.6 Storage

#### Object storage — SeaweedFS with Postgres Filer backend

Replace MinIO with [SeaweedFS](https://github.com/seaweedfs/seaweedfs) as part of Phase 1 Files port. Filer uses **existing Postgres** as metadata backend — no net-new infrastructure.

**Why SeaweedFS**:

- MinIO's OSS posture has been degrading (Console removed from OSS in 2025, features gated). Liability for self-hosted-OSS-first project.
- **Workload fit**: Haystack-inspired design optimized for many small files (avatars, documents, image variants — our exact pattern). Small objects packed into volume files internally; reading 100 thumbnails is closer to "one disk seek + sequential read" than "100 individual seeks."
- **Horizontal scale**: designed for billions of files, petabyte scale. Higher ceiling than Garage (~100 nodes) or RustFS (unproven).
- **Apache 2.0 license** — more permissive than MinIO's AGPLv3.
- **Pluggable metadata backend**: uses our existing Postgres (no new dep).

**Architecture (production)**:

- **Master servers** (Raft for cluster topology). Start with 1; scale to 3 for HA. Operationally similar to Redis Sentinel.
- **Volume servers** (data plane). Each volume = ~30GB file holding many objects. Add nodes for capacity; data redistributes automatically.
- **Filer servers** (stateless S3 gateway + metadata). Backed by our existing Postgres.

**Architecture (local dev)**: single container, all-in-one mode (`server -s3`).

**Encryption at rest**: disk-level (LUKS / dm-crypt). Dominant enterprise pattern (matches AWS EBS); accepted by SOC 2 / HIPAA / PCI for "data at rest is encrypted" requirements. Per-object SSE-C / customer-managed keys deferred (addressable later via app-level encryption layer in Files if needed).

**Known losses vs MinIO** (accepted):

- **Object Lock / WORM**: limited support. Audit storage uses Postgres + revoked-permissions + DB triggers for tamper-evidence; "tiny separate MinIO for audit bucket only" is a fallback if true Object Lock ever required for compliance.
- **SSE-C / SSE-KMS per-object encryption**: not native. Addressable later.
- **IAM-style JSON bucket policies**: SeaweedFS uses simpler access-key + role model. Fine for our use case (per-tenant prefix, presigned URLs minted by Files).
- **Lifecycle policies**: basic expiry; anything sophisticated handled in Files cleanup job.
- **Tooling polish**: `weed shell` competent but less polished than `mc`; built-in admin UI is basic.
- **AWS SDK behavioral fidelity**: MinIO has years of investment matching every SDK quirk. SeaweedFS gateway is "S3-compatible enough" for our operations (PutObject, GetObject, presigned URLs, multipart, basic listing).

#### Database topology — one server, many DBs (initial), eventual replicas

Initial deployment: **one Postgres server** hosting many databases. Move to a primary + 2 read replicas (HA configuration) when needed at launch time. Same Postgres server hosts the SeaweedFS Filer DB.

**Database naming (locked 2026-07-10):** every D2-owned Postgres database is **`d2-{domain}`** (hyphenated lowercase), e.g. `d2-keycustodian`, `d2-auth`, `d2-files`. Do not invent bare `foo_db` names. Legacy v1 leftovers may still appear as `d2-services-*` until those services rebuild. Connection strings use that path segment (`…/d2-keycustodian`). Advisory-lock catalog entries use the same string as the PG database name.

**Database catalog (each as a separate DB on the shared server)**:

| DB                      | Owner                                                  | Purpose                                                                                                                                            |
| ----------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `d2-auth`               | Edge / Auth module                                     | user, org, membership (+ history), invitation, session, credential methods, oauth_client, impersonation_consent, sign_in_attempt (aka sign_in_event), security_policy_\*, challenge store — see [PHASE_3_AUTH_CORE.md](PHASE_3_AUTH_CORE.md) |

#### Database — greenfield, no migration

App is pre-alpha with no real users and no production data to preserve. The new .NET architecture starts with a **fresh schema** designed for the new domain model. EF Core generates initial migrations from scratch. Old Drizzle migration files live in `/old/v1/` as historical reference only — never run, never adapted.

**Implications**:

- No data migration scripts.
- No EF Core "baseline" migration.
- New schema can re-shape freely.
- Local dev: dev databases dropped + re-created on first run.
- `d2-node-init` migration runner container retired as part of the Node → .NET cleanup.

**Migration discipline** (present-tense law — [AGENTS.md](../AGENTS.md) Critical Reminders + [rules.md §9.10](../dev/rules/09-architectural-layer-hygiene.md#9-architectural-layer-hygiene)):

- **Never hand-write migrations** (.NET = `dotnet ef migrations add <Name>`; that's it)
- Generator output committed as-is

#### Migration runner — multi-replica safety via PG advisory locks

With 2-3 replicas of a service starting concurrently, all attempt EF Core migrations on startup. To prevent races, each migration acquires a named PostgreSQL advisory lock before running:

```csharp
// Pseudocode in the startup IHostedService that runs migrations
var lockName = $"d2-migration-{serviceName}";
var lockId = (long)XxHash64.Compute(lockName);

await using var conn = new NpgsqlConnection(connectionString);
await conn.OpenAsync();
await conn.ExecuteAsync("SELECT pg_advisory_lock(@lockId)", new { lockId });
try
{
    await dbContext.Database.MigrateAsync();
}
finally
{
    await conn.ExecuteAsync("SELECT pg_advisory_unlock(@lockId)", new { lockId });
}
```

Built-in PG, no infra dependency. Only one replica runs the migration at a time; others wait then proceed (EF Core's "is this migration already applied?" check no-ops). Contact data folds into each service's own `DbContext` — there is no separate contacts DB or contacts-specific migration lock.

#### 5.6 (Revised 2026-05-30) — Contacts as a folded owned-component library

> **Supersedes** the struck-through per-consuming-service-DB design above. Full rationale + v1 ↔ prior-plan ↔ today lineage: [ADR-0001](../adrs/0001-contacts-folded-owned-component.md).

> **Built (2026-06-04).** The core decision — folded owned-component, no service, no DB — shipped on `n/contacts`. The implementation mechanism was refined during build: the initial wrapper-selector EF API (`EmbedContact` / `OwnContactInTable`) was replaced by a pure **VO-as-property + infra `IEntityTypeConfiguration<T>`** model using EF complex types for multi-field VOs and value converters for single-value VOs. `OwnsOne` / `OwnsMany` are not used (the anonymization engine's bulk erasure cannot reach owned child rows — principled boundary). **ADR-0001 is the canonical built record.** The planning prose below is preserved for tracking context.

`DcsvIo.D2.Contacts` is a **.NET-only library of value-object building blocks + reusable EF Core mapping** — **NOT a service, NOT its own database**. Contacts are **folded into each consuming service's own aggregates, tables, and `DbContext`**. There is no contacts DB, no contacts service, and no cross-service contact lookup / external-key triple.

**Why the flip** (full reasoning in ADR-0001):

- A contact is almost always a **subset of a host entity** (an invoice's billing/shipping contact, a user's or org's 1:1 contact, an org's address-book entry) — not an independent aggregate with its own lifecycle.
- "Folded **like Location**" means **embedded into a host entity** (Location's structural trait) — **not content-addressed**. Contact fields are PII, so Location's hash-dedup model deliberately does not extend to them (dedup of PII doesn't belong).

**What the library ships** (zero migrations, zero `DbContext`, zero DB):

- **Six composable PII value objects** (`Personal`, `NameAffixes`, `Demographics`, `Professional`, `EmailAddress`, `PhoneNumber`) with `Create(...) → D2Result<T>` smart constructors. `Personal` carries a correlation `HashId` (SHA-256 over First/Middle/Last — excludes PreferredName for display-name-change stability).
- **Per-VO EF mapping helpers** (`DcsvIo.D2.Contacts.EntityFrameworkCore`): multi-field VOs → EF complex types (`MapPersonal` / `MapNameAffixes` / `MapDemographics` / `MapProfessional`); single-value VOs → value converters (`MapEmailAddress` / `MapPhoneNumber`) with compile-time `.Unique(template)` coupling. All anonymize defaults written via the `DcsvIo.D2.DataGovernance.EntityFrameworkCore` fluent API.
- Address fields reuse `DcsvIo.D2.Location` VOs directly — mapped via `DcsvIo.D2.Location.EntityFrameworkCore`.

**Subject-id axes (kept):** every contact-bearing host entity carries optional **`Guid? UserId`** and **`Guid? OrgId`** — the correlation and erasure keys. Erasure fans out per subject via `DcsvIo.D2.DataGovernance`. Guests/externals fall back to the channel address (email/phone). Legal-hold rows are field-overwritten with tombstone values in place.

**Live vs snapshot ownership:** exactly one service owns a person's **live** canonical contact (Auth owns the user's); everyone else snapshots at capture-time. Never replicate a live contact.

**Versioning discipline (migration-cascade mitigation):** because the host owns the migration, a contact-shape change can require a migration in every adopting service. Mitigated by **semver + additive-only-within-a-major**. The library stays pure (types + mapping + validation, no business behavior).

**Delivery preferences / consent — separated out, DEFERRED:** delivery preferences + consent stay central in Courier, keyed by channel address (suppression) and subject id (routing prefs). The detailed prefs/category-lane schema is deferred.

**Day-one consumers:** Edge/Auth (user + org contacts). Invoice/billing snapshots arrive when those services exist.

#### GeoReference + Location libraries

`DcsvIo.D2.Geo` — embedded library for countries, IANA timezones, currencies, locales, regions via MSBuild `EmbeddedResource`. No service, no DB, no Redis cache, no gRPC round-trip. Loaded into memory at service boot (a few hundred KB total).

`DcsvIo.D2.Location` — three value objects:

- **`AdminLocation`** (CountryCode + Region + City + computed hash)
- **`Coordinates`** (Lat + Lon + Geohash)
- **`StreetAddress`** (Line1 + Line2 + Line3 + computed hash of normalized lines)

`WhoIsRecord` composes `AdminLocation + Coordinates` (no street ever — type system prevents it).
Host entities with contact fields embed any combination of the three Location VOs alongside the Contacts VOs — reused independently, mapped via `DcsvIo.D2.Location.EntityFrameworkCore` (see [§5.6 Revised](#56-revised-2026-05-30--contacts-as-a-folded-owned-component-library) + [ADR-0001](../adrs/0001-contacts-folded-owned-component.md)).

### 5.7 Messaging & Notifications

#### Event naming — service-namespaced to avoid clashes

All RabbitMQ exchanges, routing keys, and event message types are namespaced by **producing service** to prevent name collisions and make ownership explicit:

| Concern                           | Pattern                                                 | Examples                                                                                                         |
| --------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Exchange names                    | `d2.{producer}.{purpose}`                               | `d2.audit.events`, `d2.notifications.requests`, `d2.files.events`, `d2.courier.delivery-status`                  |
| Routing keys (within an exchange) | `{event-type}` (lowercase, dot-separated for hierarchy) | `sign-in.success`, `sign-in.failed`, `payment.charged`, `file.uploaded`, `file.processed`                        |
| Event proto packages              | `d2.events.{producer}.v{N}`                             | `d2.events.audit.v1`, `d2.events.files.v1`, `d2.events.notifications.v1`                                         |
| Event proto messages              | `{Producer}{EventType}Event`                            | `AuditEventEvent` (yes, awkward — see naming exception below), `FileUploadedEvent`, `NotificationRequestedEvent` |

**Naming exception**: when the producer's name matches the event type (e.g., DcsvIo.D2.Private.Audit's only event IS an audit event), drop the redundant suffix — just `AuditEvent`. Same for any future case where producer + event-type would create the awkward double-naming.

**Schema location**: all event message schemas live in `contracts/protos/events/v{N}/{producer}.proto`. Each `.proto` documents (in comments): "Published by: X. Consumed by: Y, Z." So readers can trace producers and consumers without grep.

**Proto versioning**: same rules as RPC contracts (per §7). Breaking changes require a new `vN+1/` package; never modify a `vN` schema in place. Old version stays in service until explicitly decommissioned.

#### Naming — Comms splits into three

| Service              | Concern                                                                    | Verb                 | Status      |
| -------------------- | -------------------------------------------------------------------------- | -------------------- | ----------- |
| **D2.Courier**       | Outbound delivery via email / SMS / future webhooks / Slack / Teams / push | `deliver()`          | **Phase 2** |
| **D2.Notifications** | In-app activity feed (persistent, with read/unread state)                  | `notify()`           | **Phase 2** |
| **D2.Threads**       | Conversational messaging (future)                                          | `post()` / `reply()` | Deferred    |

"Dispatch" was the working name for D2.Courier earlier but conflicts with industry terminology in the time-and-materials / contracting space (where "dispatch" means sending a worker to a job site). **Courier** is unambiguous, evocative, scales naturally to webhooks and future channels.

#### D2.Courier (pure outbound delivery + prefs gate)

After redesign + rename, Courier shrinks dramatically:

- ❌ No contact storage, no contact resolution
- ❌ No template entity, no template management
- ❌ No conversational messaging (that's Threads)
- ❌ No in-app feed (that's Notifications)
- ✅ Receives delivery request: subject (markdown w/ placeholders), body (markdown w/ placeholders), variables map, channel hints, recipient delivery info, prefs scoping context
- ✅ Substitutes variables into subject + body (HTML-escaped on insertion; no escape hatch)
- ✅ For email: renders markdown → HTML via `Markdig` (`UseAdvancedExtensions().DisableHtml()`), runs through `Ganss.Xss` HTML sanitizer, wraps in brand chrome (Razor template, branding vars only — color, logo image)
- ✅ For SMS: substitutes variables into plain-text body, no rendering, forward via Twilio
- ✅ Plain-text fallback for email derived automatically via Markdig's `PlainTextRenderer`
- ✅ Looks up delivery preferences scoped by `(UserId/OrgId) × (RelatedServiceName/Key/Id)`; most-specific match wins
- ✅ Delivers via SMTP / Twilio
- ✅ Retries via tier-queue topology (existing pattern)
- ✅ Tracks delivery status

**Future channels** (deferred): webhooks, Slack, Teams, Discord, mobile push (APNs/FCM). All slot in as additional channel handlers behind the same `deliver()` API.

#### D2.Notifications (Phase 2 — promoted from "future")

In-app activity feed only. Persistent feed entries with read/unread state, pagination, aggregation ("Alice and 3 others liked your post").

**Promoted into Phase 2** alongside Courier because the SSE-as-optimization pattern requires a persistent source of truth; without Notifications, entity-notification reliability collapses to "SSE-only delivery, lost if offline."

**Schema sketch**:

- `notification_feed_entry` — `id`, `recipient_user_id`, `producer_service`, `event_type`, `subject` (markdown), `body` (markdown), `link` (deep-link URL), `metadata` (JSONB), `urgency`, `aggregation_key` (nullable), `read_at`, `created_at`. Indexed on `(recipient_user_id, read_at, created_at)`.

**Pipeline**:

- Producers publish `NotificationRequestedEvent` to the `d2.notifications.requests` exchange (consistent with the event naming convention above; decouples producers from Notifications availability)
- Notifications consumes, persists feed entry, calls **Edge's SSE push API** (gRPC) to push a `notification.created` SSE event to recipient's connections
- REST API: `GET /api/v1/notifications`, `PATCH /api/v1/notifications/{id}/read`, `PATCH /api/v1/notifications/read-all`
- Aggregation rules live in Notifications (it owns the feed shape)
- Notifications does **not** decide whether to also send email/SMS — that's the producer's call (publish to `d2.notifications.requests` AND call Courier explicitly)

#### DcsvIo.D2.Private.Audit (Phase 3.5 — separate service)

Append-only audit store for impersonation sessions, sign-in events, security events, cross-service action audit.

**Why a separate service**:

- Different retention policy from operational data
- Different access control (compliance / legal can be granted read-only without touching anything else)
- Append-only easier to enforce in dedicated DB (revoke `UPDATE`/`DELETE` from the service role; only `INSERT` allowed)
- Cross-service audit (Files actions, Auth actions, Courier actions) all flow into one query surface
- Optional later upgrade to tamper-evident immutable bucket (S3 Object Lock) without changing producers

**Schema (rough)**:

- `audit_event` — `id`, `event_type`, `actor_user_id`, `actor_org_id`, `actor_org_type`, `actee_user_id`, `actee_org_id`, `action`, `resource_type`, `resource_id`, `metadata` (JSONB), `source_ip`, `source_fingerprint`, `correlation_id`, `created_at`
- `support_session` — denormalized row per impersonation start/end (duration, kind consent/force, OTP id)

**Write path**: every service publishes `AuditEvent` to the `d2.audit.events` exchange (fanout, fire-and-forget). Audit service consumes, writes to `d2-audit`. **Telemetry stays clean** — OTel spans carry only correlation IDs, never the audit payload itself.

**In-transit opacity**: all audit events are encrypted at the publisher via `DcsvIo.D2.Encryption` — see the next subsection.

#### Payload encryption (DcsvIo.D2.Encryption)

Sensitive RabbitMQ message bodies (`audit`, `notifications`, `courier` domains) are encrypted per-payload at the publisher via AES-256-GCM and decrypted at the consumer. Routing keys and headers stay cleartext. `[Encrypted(Domain.X)]` on the message type triggers transparent encrypt/decrypt in the bus wrapper — call sites see no difference. Keys (AES-256-GCM, per-domain, JWKS-style overlap rotation during the grace window) are KeyCustodian-managed. Active kids are pulled by `KeyringClient`; archive kids (retired/compromised) load only on-demand via the ops CLI for DLQ forensics. Frame format is self-contained (version byte + kid + GCM nonce + ciphertext + auth tag) so the kid travels with the ciphertext to backups and future bus migrations. Full wire format, library shape, two-tier key model, and key-distribution design: [public/packages/dotnet/messaging/rabbitmq/README.md](../../public/packages/dotnet/messaging/rabbitmq/README.md).

### 5.8 SvelteKit BFF

**Pure SSR, nothing else.** SvelteKit binds to private network; only Edge can reach it. Browser → Edge → SvelteKit. Header spoofing impossible (no external path).

**What's deleted from today's pattern**:

- ❌ All `+server.ts` endpoints (auth proxy, account proxy, etc.)
- ❌ All form actions
- ❌ All proxying — SvelteKit doesn't see auth-state mutations, account mutations, file uploads
- ❌ Most of `@dcsv-io/d2-auth-bff-client` (SessionResolver, JwtManager, AuthProxy, route guards)
- ❌ `getAuthContext()` accessor

**What's kept**:

- ✅ SSR rendering of Svelte components
- ✅ `+page.server.ts` `load()` functions for SSR data fetching
- ✅ `superForm + SPA: true` pattern (already in use; no new browser-side AJAX flows; just retargeted at Edge endpoints)

**Outbound from `load()` functions**:

- **gRPC by default** (joining the existing internal mesh; same generated stubs from `contracts/protos/` work in both .NET and Node clients via `@grpc/grpc-js`)
- HTTP allowed per call site only when measurably faster
- Going back through Edge stays HTTP

**Header contract from Edge → SvelteKit (and re-forwarded unchanged by the BFF on its outbound internal calls)**:

| Header                       | Type              | Source                                           | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------- | ----------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Authorization`              | `Bearer <jwt>`    | Edge mints once at the boundary; forwarded unchanged downstream | Carries identity (`sub`, `aud`, `scope`, `act` chain, `d2_session_id`, `d2_username`, `d2_org_id`, `d2_org_type`, `d2_org_role`, `d2_fp`). BFF receives identity by VALIDATING this token, not by reading separate spoofable headers. Custom claims are spec-defined in `contracts/jwt-claims/jwt-claims.spec.json`; constants live in the codegen-emitted `DcsvIo.D2.Auth.Abstractions.JwtClaimTypes` (.NET) and `@dcsv-io/d2-auth-abstractions` `JwtClaimTypes` (TS) catalogs.                                                                                       |
| `x-d2-context`               | base64url-of-JSON | Edge constructs from the inbound user request    | Carries the small cross-hop subset of `IRequestContext` that downstream consumers can't recompute — `RequestId`, original `RequestPath`, `SessionFingerprint`, `CurrentFingerprint`, `RiskScore`, `WhoIsHashId`. Spec-driven via `contracts/request-context/IRequestContext.spec.json` `propagate: true` annotations; codegen emits `DcsvIo.D2.Context.Abstractions.PropagatedContextSerializer` (.NET) and `@dcsv-io/d2-request-context-abstractions` `PropagatedContextSerializer` (TS). Identity fields are NEVER in here — they rebuild from the JWT at every hop. |
| `traceparent` / `tracestate` | W3C Trace Context | Edge propagates from inbound (or starts new)     | Per the W3C Trace Context spec — distributed tracing context. Same header on HTTP, gRPC, AMQP. Constants live in the codegen-emitted `DcsvIo.D2.Headers.Common` (.NET) and `@dcsv-io/d2-headers-common` (TS) catalogs (also re-emitted in every per-transport catalog at identical wire values).                                                                                                                                                                                                                                                                       |
| `X-D2-Internal-Token`        | JWT               | A genuinely-external client of Edge presents it | Internal boundary token (audience `d2.edge`, 15-min TTL) for the surviving `oauth_client` boundary-token model. **Not used by the SvelteKit BFF** — the BFF-specific round-trip is retired (2026-07-03 mesh-member ruling; [ADR-0023](../adrs/0023-mtls-workload-identity.md) 2026-07-02 amendment landed): a mesh-member BFF forwards the Edge-minted transaction token unchanged over its mTLS leaf on direct internal calls, not a re-minted boundary token back to Edge. The header constant survives in `DcsvIo.D2.Headers.Http` (.NET) and `@dcsv-io/d2-headers-http` (TS) for external clients.                                                                                                                                                                |

**Defense in depth for Edge-bypass prevention** — both layers always on (dev + prod):

1. **Network-level**: SvelteKit attached only to `internal` overlay network in Swarm; only Edge can reach it
2. **Application-level**: thin hook validates the inbound `Authorization` JWT signature and the `x-d2-context` envelope shape via the codegen-emitted serializer; rejects malformed / unsigned requests (HTTP 400 / 401 as appropriate)

**The header catalog is spec-driven**: `contracts/headers/headers.spec.json` is the single source of truth for every wire-protocol header D² emits or consumes (across HTTP / gRPC / AMQP). Codegen emits per-transport catalogs (`DcsvIo.D2.Headers.{Common,Http,Amqp,Grpc}` / `@dcsv-io/d2-headers-{common,http,amqp,grpc}`) on each language side; cross-transport headers (e.g. `traceparent`, `x-d2-context`) appear in every applicable catalog at identical wire values, codegen-guaranteed. The same model drives the JWT claim names (`contracts/jwt-claims/jwt-claims.spec.json` → `JwtClaimTypes`) and the in-process slot keys (`contracts/in-process-keys/keys.spec.json` → `D2HttpContextItems` + `D2GrpcUserStateKeys`).

**Browser-side `authClient`**: thin typed `fetch()` wrappers around Edge's auth endpoints (`signIn`, `signOut`, `requestPasswordReset`, `verifyOtp`, etc.). Lives in `private/services/web/src/lib/client/auth/` as plain TypeScript modules — **NOT a separate package** (no pnpm workspace in v2; SvelteKit is standalone).

The browser calls Edge directly for all auth state mutations (no SvelteKit proxy). After a successful sign-in, Edge sets the cookie; browser doesn't manage cookies. After a sign-out, the browser-side helper calls SvelteKit's `invalidateAll()` to refetch all `load()` data so the UI reflects the now-anonymous state.

**Server-side helpers** for SSR auth gates (used inside `+page.server.ts` / `+layout.server.ts` `load()` functions). Lives in `private/services/web/src/lib/server/auth/` as plain TypeScript modules — **NOT a separate package**. Five synchronous helpers that read from `event.locals` (populated by the thin hook from `X-D2-*` headers Edge sets):

```ts
function requireAuth(event): asserts event has authenticated locals
function requireOrg(event, ...types?: OrgType[]): asserts ...
function requireRole(event, ...roles: string[]): asserts ...
function requireScope(event, ...scopes: string[]): asserts ...
function redirectIfAuthenticated(event, to: string): void
```

Each throws `redirect()` or `error()` on failure. No I/O. Synchronous. Replaces the entire v1 `@dcsv-io/d2-auth-bff-client` package — the v1 package's other concerns (SessionResolver, JwtManager, AuthProxy) all become Edge concerns in v2.

**Local dev**: Edge runs alongside SvelteKit. Browser hits Edge on `localhost:5000`, Edge handles `/api/*` in-process and forwards page-render requests to SvelteKit on `localhost:5173`. `make dev` starts everything together. Vite HMR works through Edge's WS upgrade pass-through.

#### BFF Trust & Privilege Boundary (LOCKED)

**LOCKED architectural decision** (2026-07-03 mesh-member ruling; foundation for the BFF lib forecast in the next subsection): the SvelteKit BFF is a **privileged backend workload — a full mesh member**, not "just a frontend" and not an external client of Edge. It sits behind Edge on the private internal network; by the time a request reaches the BFF, Edge has already resolved the session and established auth. The BFF therefore:

- **holds a KeyCustodian-issued mTLS leaf** for its workload identity ([ADR-0023](../adrs/0023-mtls-workload-identity.md)). Its issuance path is the **Node `WorkloadLeafClient` twin** (`@dcsv-io/d2-private-key-custodian-client`) — a fresh P-256 keypair per rotation, a PKCS#10 CSR whose private key never leaves the workload, and a returned leaf the client verifies pairs with its local key before use.
- **makes direct mTLS calls to internal services** and **forwards the Edge-minted transaction token unchanged** ([ADR-0022](../adrs/0022-service-auth-mint-once-forward.md)) — the BFF is the **first internal hop**. Looping back through Edge after Edge already established auth is rejected as a redundant extra hop.
- holds **least privilege**: the leaf is *all* it holds — **zero KeyCustodian grants** (no keyrings, no signing keys). It never mints a boundary token, never decrypts a sensitive RMQ payload. It may use the shared TS caching stack (`@dcsv-io/d2-caching-*`) for **Node-owned** cache keys and must not write Edge-owned authority keys (session dual-write rows, rate-limit counters) unless it is the documented owning writer.

**Live wiring is Edge-host-phase-gated.** The Node leaf client and the generated TS gRPC clients are built and tested; the running BFF host that presents the leaf on real internal channels lands with the Edge-host phase — the same host-gating the .NET workload-cert path carries (see [PHASE_3.md](PHASE_3.md) §Deferred-work checklist).

**Auth model on the inbound render path**: browser → Edge → SvelteKit over the private network (only Edge can reach the BFF). Edge validates the session and mints the one internal transaction-token on the inbound pass, then proxies the page-render request to the BFF with that token attached. The BFF receives identity by VALIDATING the forwarded `Authorization` JWT (plus the `x-d2-context` operational envelope, decoded via `DcsvIo.D2.Context.Abstractions.PropagatedContextSerializer`), never by reading separate spoofable headers, and never touches the user's signed session cookie. On its own outbound calls it forwards that same token unchanged and presents its mTLS leaf, so Edge and every backing service see a known mesh workload; audit + telemetry can still tag `source: bff` vs `source: browser`.

**BFF cache posture (T1 / deliverable 0028 — supersedes the earlier “no TS cache packages” drop):** multi-instance BFF replicas are mesh-member Node workloads and **may** hold L1 + use L2 Redis + the shared invalidation backplane (`d2:cache:invalidations`, same channel as .NET `DcsvIo.D2.Caching`). The TS twin is the full ADR-0008 surface under `public/packages/typescript/caching/` (`@dcsv-io/d2-caching-abstractions` · `@dcsv-io/d2-caching-local-default` · `@dcsv-io/d2-caching-distributed-redis` · `@dcsv-io/d2-caching-tiered`) — markers, Basic/Atomic/Broadcast/Set, tiered L2-first writes, universal “everyone acts.” **Per-request memoization** within a single SSR render still uses SvelteKit's native `load()` parent-dedup (`parent()`) — that path is not replaced by Redis. Cross-replica / process-lifetime coherence uses the caching stack. Edge remains the owner of session dual-write and rate-limit Redis keys; BFF/Node use Node-owned key namespaces.

**Why the BFF stays a thin mesh member**:

- **Least blast radius.** The leaf is the only credential the BFF holds — zero KeyCustodian grants, no backend `client_secret`, no keyring. A compromise gets the attacker only what the forwarded user token already permits, gated by per-operation scope enforcement at every hop.
- **Horizontal scale without sticky sessions.** New replicas subscribe the shared invalidation backplane and re-populate L1 on demand (TTL + at-most-once backplane; no sticky-session requirement).
- **Uniform per-hop security.** Every internal call — whether it originates at a browser-driven Edge request or at the BFF — carries the same forwarded transaction-token re-validated at each hop plus mTLS workload identity; there is no transport-trust fast path ([ADR-0023](../adrs/0023-mtls-workload-identity.md) — mTLS is strictly additive to JWT re-validation, never a validation skip).

**SSR-vs-CSR matrix** (typical dashboard surface — defaults; per-page exceptions are explicit at the call site):

| Concern                                        | Default                            | Reasoning                                                                                                                                                             |
| ---------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 5.9 Production Deployment

**Orchestration**: Docker Swarm + Portainer (until ~$50K/month MRR).

- **Cluster shape**: 3 Swarm manager nodes (Raft quorum). All services run on these 3 nodes. Each backend service runs 2-3 replicas distributed across the cluster via Swarm placement constraints.
- **Two overlay networks**:
  - `ingress` — Edge instances attach here; faces L7 LB (Cloudflare)
  - `internal` — everyone else (SvelteKit, Files, Courier, Notifications, Audit, future services, infra). Edge attaches to both.
  - SvelteKit on `internal` only → cannot be reached from outside Edge.
- **Secrets**: `docker secret` mounts OAuth `client_secret` bootstrap creds (and other long-lived secrets) into each service at `/run/secrets/...`. Each service reads on startup. Rotation via dual-secret window.
- **Configs**: `docker config` for non-secret per-environment configuration.
- **Stack deployment**: `docker stack deploy -c stack.yml d2` from CI, or via Portainer UI.
- **Portainer**: ops UI for stack health, container logs, image management, deploy operations.
- **Infrastructure co-location**: Postgres (primary + 2 replicas), Redis (Sentinel/Cluster), RabbitMQ (3-node cluster), SeaweedFS (1 Master initially → 3 for HA; Volume + Filer per node) all on the same 3 Swarm nodes.

**Upgrade path**: when revenue justifies > 3 machines and operational complexity is worth it, K8s migration unlocks NetworkPolicy and more sophisticated autoscaling, and would be the natural point to adopt SPIFFE/SPIRE as a standard, interoperable workload-identity layer. (Workload identity itself is **not** gated on that move — mTLS workload identity via KeyCustodian-issued certificates is adopted now per [ADR-0023](../adrs/0023-mtls-workload-identity.md), with SPIFFE-compatible naming so a later SPIFFE adoption needs no re-architecting.) Until then, Swarm gives 90% of what we need with 20% of the operational surface.

## 9. Dev DX

### Docker Compose Watch + `dotnet watch` inside containers

Per [Docker Compose Watch docs](https://docs.docker.com/compose/how-tos/file-watch/) and Compose 2.25+ (Sept 2025 added `initial_sync`). Built INTO Docker Compose itself.

**Why this over Aspire**:

- **Maximum dev↔prod parity** (Compose syntax = Swarm `stack.yml` syntax — same shape between dev and prod, just different override files)
- No new tool to learn beyond what Compose already gives us
- `sync` action avoids `obj`/`bin` pollution that bind mounts cause
- Compose 2.25+ multi-service watch is now production-ready
- We don't lose anything Aspire would give us — our LGTM stack already provides the dashboard
- Aspire is its OWN orchestration model that doesn't match Swarm; adopting it means dev in one paradigm, prod in another

**Configuration shape** (`infra/compose/compose.dev.yml`):

```yaml
services:
  edge:
    build:
      context: ../..
      dockerfile: infra/docker/Dockerfile.edge
      target: dev # use the SDK image with dotnet watch
    environment:
      - DOTNET_USE_POLLING_FILE_WATCHER=1
      - ASPNETCORE_ENVIRONMENT=Development
    develop:
      watch:
        - action: sync
          path: ../../private/services/edge
          target: /src/private/services/edge
          ignore: [bin/, obj/]
        - action: sync
          path: ../../public/packages
          target: /src/public/packages
          ignore: [bin/, obj/]
        - action: rebuild
          path: ../../private/services/edge/**/*.csproj
        - action: rebuild
          path: ../../server/Directory.Packages.props
```

`dotnet watch` runs inside the container; Compose `sync` action copies file changes into the running container; `dotnet watch` picks them up via polling watcher.

**For SvelteKit**: standard Vite HMR, no special handling needed beyond exposing the HMR port.

### Audit framework anti-cheat tooling (design intent)

**Status: design only — implementation deferred to future deliverable.**

The current audit framework (`docs/dev/process.md` + `docs/dev/rules.md` + the 3-artifact markdown journal model) relies on agent discipline + structural sub-agent separation + adversarial framing to enforce evidence quality. The design intent below describes a JSON-first tooled successor that would mechanize the anti-cheat layer. None of the tooling described here is built; the markdown journal model remains canonical until/unless this lands.

**JSON-first artifact model.** The audit output becomes JSON, not markdown. Markdown views are GENERATED from JSON by a renderer for human readability, but JSON is the source of truth. Schemas live in `tools/audit/schemas/` (JSON Schema, or zod TS definitions). Sub-agents producing malformed JSON get rejected before output enters the journal.

Directory layout per step (design):

```
docs/wip/<deliverable>/<NN>-<step>/
├── README.md                          # plan, decisions, prerequisites (human-authored)
├── audit/
│   ├── round-1/
│   │   ├── implementer-report.json
│   │   ├── auditor-1-of-6.json       # partial big-table chunk
│   │   ├── auditor-2-of-6.json
│   │   ├── ...
│   │   ├── big-table.json             # aggregated canonical
│   │   └── validator-report.json      # output of validator script
│   ├── round-2/
│   │   └── ...
│   ├── findings/
│   │   ├── §1-tests.json              # category-indexed, append-only across rounds
│   │   ├── §3-pii.json
│   │   └── ...
│   ├── fix-log.json                   # chronological, append-only
│   └── README.md                      # rendered human-readable summary (auto-generated)
```

Big table row schema (JSON, design):

```json
{
  "section": "§3.1",
  "predicate": "[LoggerMessage] no Exception parameter",
  "status": "PASS",
  "verification": {
    "type": "recipe",
    "recipeId": "no-exception-in-loggermessage",
    "evidenceLocator": {
      "file": "public/packages/dotnet/auth/Telemetry/AuthLog.cs",
      "lineRange": [30, 92]
    },
    "evidenceContent": "[LoggerMessage(EventId = 1001, Level = LogLevel.Warning, ...)]",
    "evidenceHash": "sha256:abc123..."
  },
  "reason": null,
  "finding": null
}
```

**Three-layer mechanical anti-cheat (design):**

- **Layer 1 — Schema validator**: `tools/audit/validate-schema.js <json-file>` parses + schema-validates. Catches missing required fields, bad status enums, malformed evidenceLocator.
- **Layer 2 — Evidence verifier**: `tools/audit/verify-evidence.js <big-table.json>` walks every row and re-runs recipes / checks evidence claims against disk. If verification fails, the entire audit round is rejected.
- **Layer 3 — Recipe runners (proactive scanning)**: `tools/audit/run-recipes.js --step <NN>` runs every recipe-verifiable predicate against the step's files and produces a draft big table. Auditors START with this auto-generated draft and only need to manually walk the judgment-required predicates. Decimates auditor cognitive load.

**`rules.md` transformation — recipe / judgment / process buckets (design).** Each numbered subsection in `rules.md` gets classified:

- **Recipe-verifiable (~70% expected)** — checkable by a script. Each gets a `recipeId` + recipe definition file.
- **Judgment-required (~25% expected)** — requires agent judgment that no script can check. Stays as agent-walked predicates but FLAGGED as `judgment-required`.
- **Process-discipline (~5% expected)** — about HOW the audit runs, not WHAT the code looks like. Moves OUT of the auditor's checklist and INTO the orchestrator's logic.

Tooling layout (design):

```
tools/audit/
├── README.md                        # how to invoke + dev guide
├── schemas/                          # JSON Schema definitions
├── recipes/                          # one recipe file per recipe-verifiable predicate
├── orchestrate.js                    # state machine; main entry point
├── run-recipes.js                    # produces draft big-table.json
├── validate-schema.js                # JSON schema validation
├── verify-evidence.js                # re-runs recipes, checks evidence claims
├── render.js                         # JSON → markdown for human review
└── tests/                            # jest / vitest
```

**Buildout phases (design):**

| Phase | Task                                                                                         | Estimated effort |
| ----- | -------------------------------------------------------------------------------------------- | ---------------- |
| 1     | Build `validate-schema.js` + `verify-evidence.js` + JSON schemas. Baseline anti-cheat infra. | 1-2 days         |
| 2     | Convert `rules.md` predicates: classify into recipe/judgment/process buckets.                | 2-3 days         |
| 3     | Author recipe files for the recipe-verifiable bucket (~70% of predicates).                   | 3-5 days         |
| 4     | Build `orchestrate.js` state machine + `run-recipes.js` + `render.js`.                       | 1-2 days         |
| 5     | Update `CLAUDE.md` / `process.md` to reference JSON-tooled flow as canonical.                | 1 day            |
| 6     | Live-test on a real step. Iterate.                                                           | ongoing          |
| 7     | Backfill recipes for predicates that prove flaky in live tests.                              | ongoing          |

Recommended approach if work resumes: ship Phase 1 opportunistically — it would catch fabricated PASS rows in the current markdown journals immediately, even before the rest of the JSON-first artifact model lands.

**Open design decisions:**

1. **TypeScript vs vanilla JS** — TS gives schema definitions for free (zod) + better DX, but adds build step. Lean TS given the rest of the Node side is TS.
2. **Tie-breaker mechanism** when 2 Auditors disagree on a row — spawn 3rd Auditor as tie-breaker, OR escalate to user. Lean tie-breaker first, escalate if tie-breaker also conflicts.
3. **Recipe authoring incentive** — should recipe authors get to declare effort scaling? Probably yes for performance.
4. **Backwards compat with current journal markdown** — should the renderer produce markdown identical to current journal layout, or break compat with cleaner format? Lean break compat, optimize for new layout.
5. **What happens if a recipe itself has a bug** — false positive? false negative? Need a recipe-test suite.
