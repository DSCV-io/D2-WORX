# KeyCustodian

> Parent: [`server/services/edge/`](../README.md)

For engineers working on the KeyCustodian module or integrating with the key lifecycle from other Edge modules. The KeyCustodian is Edge's key-lifecycle authority. It owns the lifecycle of every long-lived secret the platform uses — JWKS signing keys (RS256), RabbitMQ payload-encryption keys (AES-256-GCM), session-cookie signing secrets, service-identity client secrets, and the internal certificate-authority key (`X509CaCertificate`) that issues per-workload mTLS leaf certificates. KeyCustodian is the internal CA: it seeds the root + issuing intermediate certificate authority, issues short-lived workload leaf certificates on demand, and rotates the CA key through the same overlap lifecycle all managed keys use. It is the single point that generates, activates, rotates, retires, and compromises managed keys, ensuring that no other module holds or controls key material lifecycle.

Key operations are persisted to a dedicated `keycustodian_db` (independent of `auth_db`) using an EF-as-DDD flat-record + pure-mapper pattern (no per-op Repository handlers — direct DbContext + aggregate access per [ADR-0017](../../../../docs/adrs/0017-ef-as-ddd-persistence.md)). Rotation coordination uses PostgreSQL advisory locks — leaderless, no Redis dependency for a rare, non-latency-sensitive operation. The root key that protects all managed key material at rest is file-backed (`secrets/keycustodian/root.key`), loaded at startup via `FileRootKeyProvider` in the Infra layer.

## Key design decisions

- **Sum-type state machine**: the domain models key lifecycle as an `abstract record EncryptionKey` base + five sealed per-state records (`PendingKey` / `ActiveKey` / `RetiringKey` / `RetiredKey` / `CompromisedKey`). Illegal transitions are uncompilable. See [ADR-0016](../../../../docs/adrs/0016-keycustodian-lifecycle-store.md).
- **Flat record + pure mapper (EF-as-DDD Shape B)**: the immutable sum type is persisted as a single non-polymorphic `KeyRecord`; a pure static mapper bridges domain ↔ record. See [ADR-0017](../../../../docs/adrs/0017-ef-as-ddd-persistence.md).
- **File-backed root key (multi-key)**: the 32-byte root key lives at `secrets/keycustodian/root.key`, loaded once at startup and never persisted to the database. An optional `root-next.key` in the same directory loads as a decrypt-only kid for zero-downtime root rotation.
- **PG advisory lock rotation coordination**: leaderless; no Redis dependency for key rotation.
- **Capability-general workload authority**: one pure domain rule (`WorkloadCapabilityAuthority`) answers "may workload W use capability C (sign / seal-encrypt / seal-decrypt) on target D?", keyed on the locally-established request `RequestOrigin` (recomputed by the receiving boundary from its own unforgeable transport facts — never a propagated wire value) plus the validated mutual-TLS peer workload identity (`ImmediateCaller`). Signing is layered + fail-closed: an unestablished origin denies (`KEYCUSTODIAN_REQUEST_ORIGIN_UNESTABLISHED`); the cluster-signing root `jwks-signing` is STRUCTURALLY unreachable on the general signing surface (`IKeyCustodianApi.SignAsync`) for EVERY established origin (`KEYCUSTODIAN_MINTER_CAPABILITY_REQUIRED`) — it is signable only through the dedicated minter capability `IJwtSigningCapability`, registered solely in the JWT minter's (auth-module's) composition via `AddD2JwtSigningCapability()` (possession of the resolved seam plus the in-process-module plane check is the authority). Every other domain signs cross-process only, per the caller's allowed-signing-domains policy (`KEYCUSTODIAN_SIGNING_AUTHORITY`): a domain outside the set is a policy-scope denial (`KEYCUSTODIAN_SIGNING_DOMAIN_NOT_AUTHORIZED`); a cross-process hop with no authenticated peer is denied (`Forbidden`); and the boot-time config validator still refuses to grant `jwks-signing` to any cross-process workload. The general `sign` op (the `internal.kc.sign` scope) is the first production consumer — the KC app stays gRPC-free, reading the established `IRequestContext.Origin` / `.ImmediateCaller`. Seal-encrypt is broad within its served planes (cross-process + in-process module — any scoped producer fetches any public key); seal-decrypt is self-only AND cross-process-only (the op carries no target — the key is selected by the authenticated mTLS peer identity, which is unforgeable only on the cross-process plane, so an in-process private-key fetch is refused at the plane arm). Two security counters (`d2.keycustodian.cross_process_signing_rejections` — pages on any non-zero value, fired when a caller tries to reach the cluster root on the general surface — and `d2.keycustodian.authority_rejections`, tagged `capability` + `reason`: `origin-unestablished` / `minter-required` / `not-in-allowed-set` / `identity-absent` / `not-in-process`) and the `AuthorityRejected` log delegate record denials. The dedicated in-process minter capability (`IJwtSigningCapability`) emits the same `authority_rejections` counter (`capability = sign`) + `AuthorityRejected` log on its own deny arms — an unestablished origin (`origin-unestablished`) or an established-but-wrong-plane invocation (`not-in-process`) — so a minter deny is never silent.
- **Keyring distribution authority**: the `getKeyring` op serves a payload domain's Active + Retiring `AesPayload` keyring to authorized callers through the same capability-general rule (`WorkloadCapabilityAuthority.AuthorizeKeyringFetch`), fail-closed and layered on the locally-established `RequestOrigin` plus the mTLS-or-module `ImmediateCaller`: an unestablished origin denies first; the surface serves ONLY the cross-process-hop + in-process-module planes (`EdgeInbound` / `System` denied); an authorized plane with no caller identity is `Forbidden`; and the target must be in the caller's per-workload allowed-keyring-domains policy (`KEYCUSTODIAN_KEYRING_AUTHORITY`). The plane deny and the policy miss return one uniform 403 (`KEYCUSTODIAN_KEYRING_DOMAIN_NOT_AUTHORIZED`) so a caller cannot probe which domains exist; telemetry distinguishes them (`unauthorized-plane` vs `not-in-allowed-set`) without an oracle. A keyring is a full encrypt+decrypt capability, so the boot validator refuses to grant ANY non-payload domain (`jwks-signing` / `cookie` / `client-secret` / `mtls-ca-*`) — only payload domains (`audit` / `notifications` / `courier`) are keyring-grantable, and the `internal.kc.keyring` scope only gates reaching the surface (the policy decides which domains; holding the scope alone never releases a keyring).

## Database

`keycustodian_db` — owned by this module. Tables: `key_record`, `key_audit_record`, `leaf_issuance_audit_record`.

## Operations

KeyCustodian is a module within Edge — it is composed into the Edge host via `AddD2KeyCustodian(...)` and has no standalone process. It ships the key-lifecycle engine (persistence, rotation, vault, health) plus the generated well-known discovery surface below; the Edge host wires the routes into its composition root.

### Well-known endpoints (generated)

The contract (`contracts/typespec/key-custodian/key-custodian.tsp`) declares two anonymous (`@d2Harmless`) `GET` operations served at the OIDC-canonical paths; both are GENERATED end-to-end (route registration + DTOs + in-process façade) by the TypeSpec emitter fleet:

| Path                                | Operation              | Body                                                                                                                                          |
| ----------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `/.well-known/jwks.json`            | `GetJwks`              | The RFC 7517 JWKS document (active signing key(s) first). Empty signing-key store → `503` (fail-secure).                                     |
| `/.well-known/openid-configuration` | `GetOidcConfiguration` | Minimal OIDC discovery document — `issuer`, `jwks_uri`, `id_token_signing_alg_values_supported: ["RS256"]`, and the spec-required placeholders. |

Any HTTP JWKS / OIDC client (including .NET's `ConfigurationManager<OpenIdConnectConfiguration>`, which the shared `HttpJwksProvider` wraps) auto-discovers `jwks_uri` from the discovery document and fetches the JWKS.

### Internal signing (generated gRPC + in-process)

The contract also declares the `sign` operation — a read-only Query (`@d2Query`) exposed in-process (`@d2InProcess`) and over gRPC (`@d2GrpcMethod("KeyCustodianSigner", "Sign")`), gated by the `internal.kc.sign` scope on the `d2.internal` audience. NO REST surface (a raw HTTP sign endpoint would be an attack surface). It loads a key domain's active `RsaSigning` key, decrypts the private key via root crypto, signs the input (RS256 / PKCS#1 v1.5 over SHA-256) in the pure `RsaSigning` domain rule (zeroing the unwrapped key in a `finally`), and returns `{ signature, kid }`. The signing input carries `[RedactData]` so it never appears in logs. The general surface signs every domain EXCEPT the cluster-signing root `jwks-signing` (reachable only through the dedicated minter capability `IJwtSigningCapability`); a cross-process caller signs per its allowed-signing-domains policy, gated through `WorkloadCapabilityAuthority.AuthorizeSigning` on the established `RequestOrigin`. Two sign-specific failures join the catalog: `KEYCUSTODIAN_SIGNING_KEY_UNAVAILABLE` (503 — no active signing key for the domain, retryable) and `KEYCUSTODIAN_EMPTY_SIGNING_INPUT` (400). The generated `KeyCustodianSignerService` is a thin façade-delegate to `IKeyCustodianApi.SignAsync` with no auth/authority logic; the live host wiring (the CrossProcessHop + scope-enforcing interceptors + `MapGrpcService<KeyCustodianSignerService>().RequireAnyScope("internal.kc.sign")`) is wired by the Edge composition root.

### Keyring distribution (generated gRPC + in-process)

The contract also declares the `getKeyring` operation — a read-only Query (`@d2Query`) that fetches a payload-encryption key domain's distributable keyring, exposed in-process (`@d2InProcess`, `IKeyCustodianApi.GetKeyringAsync`) and over gRPC (`@d2GrpcMethod("KeyCustodianKeyring", "GetKeyring")` — a service DISTINCT from `KeyCustodianSigner`), gated by the `internal.kc.keyring` scope on the `d2.internal` audience. NO REST surface (a raw keyring endpoint would hand out key material). It serves the domain's Active + Retiring `AesPayload` keys only (Pending / Retired / Compromised excluded), root-unwraps each, and returns `{ activeKid, entries, aadContext }` where each `entries` element is a `{ kid, keyBytes }` pair: `activeKid` is the single DB-enforced Active key, and the entries are ordered active-first then retiring newest-activated-first. `keyBytes` (the raw AES-256 key) carries `[RedactData(SecretInformation)]` so it never appears in logs; custody of the raw bytes transfers to the caller (which assembles a `PayloadCryptoKeyring`) — KeyCustodian does NOT zero them. `aadContext` is the domain's AEAD additional-authenticated-data — the UTF-8 bytes of `"d2/<domain>"`, authenticated-not-secret (GCM AAD is public context by construction) and DELIBERATELY not redacted so operators can debug a cross-service AAD disagreement; it is stable-per-domain-for-life (changing it breaks decryption of everything already encrypted under the domain).

No Active key → `KEYCUSTODIAN_KEYRING_KEY_UNAVAILABLE` (503, retryable) even when Retiring rows exist, incrementing the `d2.keycustodian.empty_keyring_served` counter (`SR_EmptyKeyringServed`) and logging `KeyringKeyUnavailable` (EventId 9513, Warning — names the domain only, no key material, no exception). Authority is the dedicated fail-closed arm `WorkloadCapabilityAuthority.AuthorizeKeyringFetch` on the established `RequestOrigin` + `ImmediateCaller`: an unestablished origin denies first (403); the surface serves ONLY the cross-process-hop + in-process-module planes (`EdgeInbound` / `System` denied); an authorized plane with no caller identity is `Forbidden`; and the target must be in the caller's allowed-keyring-domains set. Both the plane deny and the policy miss return the SAME uniform 403 `KEYCUSTODIAN_KEYRING_DOMAIN_NOT_AUTHORIZED` (no domain-existence oracle); the deny reuses the `AuthorityRejected` log + `d2.keycustodian.authority_rejections` counter with the NEW `capability = keyring` tag value, distinguishing the plane deny (`reason = unauthorized-plane`) from the policy miss (`reason = not-in-allowed-set`) for telemetry only. The per-workload policy binds from `KEYCUSTODIAN_KEYRING_AUTHORITY` (below); the boot validator refuses any non-payload grant (`jwks-signing` / `cookie` / `client-secret` / `mtls-ca-*`) because a keyring is a full encrypt+decrypt capability, so only payload domains (`audit` / `notifications` / `courier`) are keyring-grantable. The `internal.kc.keyring` scope gates WHETHER a caller may reach the keyring surface at all; the per-workload domain policy decides WHICH domains it may fetch — holding the scope alone never releases a keyring. The handler ALSO has a sharp 400 `KEYCUSTODIAN_KEY_TYPE_DOMAIN_MISMATCH` key-type fork, but that fork is defense-in-depth only and unreachable in production (authority runs first, and no caller can hold a validator-forbidden non-payload grant). The generated `KeyCustodianKeyringService` is a thin façade-delegate to `IKeyCustodianApi.GetKeyringAsync` with no auth/authority logic; the live host wiring (interceptors + `MapGrpcService<KeyCustodianKeyringService>().RequireAnyScope("internal.kc.keyring")`) is wired by the Edge composition root.

### Workload leaf issuance (generated gRPC + in-process, CSR flow)

The contract declares the `issueLeaf` operation — a Command (`@d2Command`, it writes the issuance audit row) exposed in-process (`@d2InProcess`, `IKeyCustodianApi.IssueLeafAsync`) and over gRPC (`@d2GrpcMethod("KeyCustodianCertificateAuthority", "IssueWorkloadCertificate")` — its OWN service; one gRPC service per op so each carries its own transport scope policy), gated by the `internal.kc.issue` scope on the `d2.internal` audience. NO REST surface. The flow is **CSR-based, all-public wire material**: the workload generates its own ECDSA P-256 keypair and submits a DER PKCS#10 certificate-signing request; KeyCustodian verifies the CSR's proof-of-possession + the P-256 curve OID (the pure `CsrVerification` rule — a named size cap before any parse; every failure class folds into the coarse 400 `KEYCUSTODIAN_INVALID_CSR` so nothing leaks which check failed), IGNORES the CSR's subject/SAN, and signs the extracted public key into a leaf whose SPIFFE SAN is ALWAYS the authenticated mTLS peer identity (`IRequestContext.ImmediateCaller`) — structural self-issue: an impersonation request is unrepresentable because no subject travels on the D2 wire. The output is the leaf + issuing-intermediate DER + validity window — **the leaf private key never crosses the wire and never exists inside KeyCustodian**; the root trust anchor deliberately does NOT ride issuance (it distributes via `getCaCertificate`). Authority is the fail-closed `WorkloadCertificateAuthority.AuthorizeIssuance` rule: an unestablished origin denies first; issuance is CROSS-PROCESS ONLY (the in-process plane's `ImmediateCaller` is caller-supplied and can never authorize minting an identity) with the uniform 403 `KEYCUSTODIAN_ISSUANCE_NOT_AUTHORIZED`; an absent peer is `Forbidden`. Every deny fires `AuthorityRejected` + `d2.keycustodian.authority_rejections` (`capability = issuance`; the log target is the closed-set `none` marker — issuance carries no key-domain target). Ordering is load-bearing: authority precedes CSR validation precedes the CA load, so an unauthorized prober gets no CSR-parse or CA-state oracle. The signing itself routes EXCLUSIVELY through the isolated `ICaLeafSigningCapability` (registered ONLY by `AddD2CaLeafSigningCapability()` from the composition root that serves the issuance surface — never by `AddD2KeyCustodianApp()`), which loads the active intermediate, unwraps its private key, signs, and zeroes the unwrapped material; no active intermediate → 503 `KEYCUSTODIAN_NO_ACTIVE_ISSUING_CA`. The mesh trust anchor gets the SAME §9.44 discipline through a sibling seam: `ICaRootSigningCapability` (registered ONLY by `AddD2CaRootSigningCapability()` from the System-worker host's composition) is the SOLE holder of every stored `mtls-ca-root` private-key plaintext use — the intermediate-minting SIGN path (`CaSuccessorFactory` delegates the root→intermediate unwrap+sign) AND the root-domain SMOKE-VERIFY path (`ActivateKey` / `RotateKey` route a pending/successor `mtls-ca-root` smoke through it; every other domain keeps the inline generic smoke). All four lifecycle-mutation handlers take it, so the general registration alone cannot even construct them; every use fires one chokepoint (`d2.keycustodian.ca_root_key_uses{operation}` + `CaRootKeySigningUsed` 9518 / `CaRootKeySmokeTested` 9519 — kids + operation only, never key material). The System-plane lifecycle authority stays as defense-in-depth beneath the structural isolation. A successful issuance writes the durable audit row, increments `d2.keycustodian.leaf_certificates_issued`, and logs `LeafCertificateIssued` (EventId 9515). The generated `KeyCustodianCertificateAuthorityService` is a thin façade-delegate through the generated `IssueLeafHandler` shell; the hand-written `IssueWorkloadCertificateHandler` is the single chokepoint BOTH planes flow through. Live host wiring (`MapGrpcService<KeyCustodianCertificateAuthorityService>().RequireAnyScope("internal.kc.issue")`) is wired by the Edge composition root.

### CA-chain distribution (generated gRPC + in-process)

The contract declares the `getCaCertificate` operation — a read-only Query (`@d2Query`, empty input) exposed in-process (`IKeyCustodianApi.GetCaCertificateAsync`) and over gRPC (`@d2GrpcMethod("KeyCustodianCaCertificate", "GetCaCertificate")` — its OWN service), gated by the `internal.kc.cacert` scope on the `d2.internal` audience. It returns the full CA chain — the active root (the trust anchor a workload pins) + the active issuing intermediate — as DER-encoded PUBLIC certificate material (deliberately unredacted: trust material presented on the wire in every TLS handshake). Authority is `WorkloadCertificateAuthority.AuthorizeCaCertificateFetch`: an unestablished origin denies first; the served planes are cross-process + in-process module ONLY (the internal anchor never rides the public `EdgeInbound` plane; `System` workers have the CA provider) with the uniform 403 `KEYCUSTODIAN_CA_CERTIFICATE_NOT_AUTHORIZED`; a served plane with no identity is `Forbidden`; within the served planes the authority is broad — public material, no per-workload policy map. Both tiers are REQUIRED: a missing / inactive / malformed root OR intermediate is the retryable 503 `KEYCUSTODIAN_NO_ACTIVE_ISSUING_CA` (a partial chain is not "the chain"), incrementing `d2.keycustodian.no_active_issuing_ca` and logging `CaCertificateUnavailable` (EventId 9514). Denies fire the same authority telemetry with `capability = ca-cert`. Live host wiring (`MapGrpcService<KeyCustodianCaCertificateService>().RequireAnyScope("internal.kc.cacert")`) is wired by the Edge composition root.

### Seal-key distribution (generated gRPC + in-process, lazy provisioning)

The contract declares the two sealed-encryption key ops, each a Command (`@d2Command` — the first request provisions a keypair, a persistent write) on its OWN gRPC service, exposed in-process and over gRPC, on the `d2.internal` audience. NO REST surface. Per-service sealing keys are `EcdhSealing` (P-256 ECDH) keypairs under the pattern-based `seal:<serviceId>` key-domain family (the service-id suffix is validated against the shared workload-identity grammar; the family is unbounded, so it is resolved by prefix rather than the closed catalog — `KeyDomain.Create` / `FromTrusted` both resolve it, so the lifecycle ops (rotate / compromise / retire) work on seal domains under the `Default` rotation policy).

- **`getOrLazyProvisionSealPublicKey(serviceId)`** (`@d2GrpcMethod("KeyCustodianSealPublicKey", "GetOrLazyProvisionSealPublicKey")`, scope `internal.kc.seal.encrypt`) returns the target service's Active + Retiring PUBLIC sealing keys — `{ activeKid, entries: [{ kid, publicSpki }] }`, active first then retiring newest-activated-first, served straight from the plaintext-at-rest SPKI column (no root-decrypt). Authority is the fail-closed `WorkloadCapabilityAuthority.AuthorizeSealEncrypt` on the established `RequestOrigin` + `ImmediateCaller`: unestablished denies first; the served planes are cross-process + in-process module (Edge itself seals on publish); within them the authority is BROAD — any authenticated caller fetches ANY service's public key (public material is harmless to over-share; the scope gates whether the caller may seal at all). The gate runs BEFORE the serviceId validation so an unauthorized prober gets no validation oracle.
- **`getOrLazyProvisionOwnSealPrivateKey()`** (`@d2GrpcMethod("KeyCustodianOwnSealPrivateKey", "GetOrLazyProvisionOwnSealPrivateKey")`, scope `internal.kc.seal.open`) returns the CALLER'S OWN Active + Retiring PRIVATE sealing keys, root-unwrapped — `{ activeKid, entries: [{ kid, privatePkcs8 }] }` with `privatePkcs8` carrying `[RedactData(SecretInformation)]`. The op has NO target parameter: the key is selected purely from the authenticated identity (`IRequestContext.ImmediateCaller`), so impersonation is structurally unrepresentable. Authority is `WorkloadCapabilityAuthority.AuthorizeSealDecrypt` — CROSS-PROCESS ONLY (the hard gate): on the only served plane `ImmediateCaller` IS the unforgeable validated mTLS peer id (the interceptor establishes Origin + ImmediateCaller atomically); no unforgeable in-process identity exists, so an in-process private-key fetch is refused at the plane arm and never reaches key selection.

Both deny paths share the uniform 403 `KEYCUSTODIAN_SEAL_NOT_AUTHORIZED` (no plane / service-existence oracle) and fire `AuthorityRejected` + `d2.keycustodian.authority_rejections` (`capability = seal-encrypt` / `seal-decrypt`; the log target is the closed-set `none` marker — the denies precede target resolution).

**Lazy provisioning.** The first request for a service's seal domain generates a P-256 keypair, smoke-tests it (a real self-seal→self-open round-trip through the sealed-encryption core), and inline-activates it via a back-dated `CreatedAt` (the soak's purpose — never serve an unproven key — is satisfied by the inline smoke test, the same sanctioned pattern the CA seeder uses), writing the Active row + its audit entries in one transaction and incrementing `d2.keycustodian.seal_keypairs_provisioned` (+ `SealKeypairProvisioned`, EventId 9516 — names the service, kid, and triggering caller; never key bytes). Concurrent first-requests converge on ONE winner: the one-Active DB EXCLUDE absorbs the race and the loser re-reads and serves the winner's key — no conflict escapes to any caller. A no-active-key window (a lost race whose winner is not yet visible, or a live Pending blocking provisioning) is the retryable 503 `KEYCUSTODIAN_SEAL_KEY_UNAVAILABLE` (+ `SealKeyUnavailable`, EventId 9517). **Operator note — orphaned Pending:** if a crashed provisioner leaves an orphaned Pending seal key, the one-Pending index blocks new provisioning (a persistent 503 for that service); recover via the existing System-plane lifecycle ops — `ActivateKey` once the soak has elapsed, or `RetireKey` / `CompromiseKey` to clear it so lazy provisioning can run again.

The generated `KeyCustodianSealPublicKeyService` / `KeyCustodianOwnSealPrivateKeyService` are thin façade-delegates; live host wiring (`MapGrpcService<…>().RequireAnyScope("internal.kc.seal.encrypt" / "internal.kc.seal.open")`) is wired by the Edge composition root.

### Configuration

App options bind from the `KEYCUSTODIAN_APP` section (prefix `KEYCUSTODIAN_APP__`), validated at host startup (`ValidateDataAnnotations` + `ValidateOnStart`):

| Option            | Env var                          | Required | Notes                                                                                                                                                       |
| ----------------- | -------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `IssuerBaseUrl`   | `KEYCUSTODIAN_APP__ISSUERBASEURL` | Yes      | The Edge external base URL — the OIDC `issuer` and the prefix of the published `jwks_uri`. Empty/unset crashes the host at startup (fail-loud).             |
| `RsaKeySizeBits`  | `KEYCUSTODIAN_APP__RSAKEYSIZEBITS` | No (2048) | RSA modulus size for generated signing keys (minimum 2048).                                                                                                |
| `SecretLengthBytes` | `KEYCUSTODIAN_APP__SECRETLENGTHBYTES` | No (64) | Opaque-secret length (minimum 16).                                                                                                                         |
| `Default` / `Policies` | `KEYCUSTODIAN_APP__DEFAULT__*` / `…__POLICIES__<DOMAIN>__*` | No | Rotation policy (cadence / grace / smoke-soak) — default + per-domain overrides. `RootCaValidity` / `IntermediateCaValidity` / `LeafValidity` govern mTLS CA windows (leaf < intermediate < root, startup-enforced). |

The signing-domain authority policy binds from its own `KEYCUSTODIAN_SIGNING_AUTHORITY` section (prefix `KEYCUSTODIAN_SIGNING_AUTHORITY__`), validated fail-loud at startup (`ValidateOnStart`):

| Option | Env var | Required | Notes |
| --- | --- | --- | --- |
| `AllowedSigningDomainsByWorkload` | `KEYCUSTODIAN_SIGNING_AUTHORITY__ALLOWEDSIGNINGDOMAINSBYWORKLOAD__<WORKLOAD>__<i>` | No (empty = deny-all) | Per-workload allowed cross-process signing domains. Key = lowercase SPIFFE workload id (e.g. `edge`); value = the signing key domains that workload may sign with. **No never-cross-process-signable domain (`jwks-signing`, `mtls-ca-root`, `mtls-ca-intermediate`) may EVER appear under any workload — the host refuses to boot if one is granted (fail-loud).** Empty-string keys and non-catalog domain values also fail at startup. An empty policy is valid (every lookup returns the empty set ⇒ deny-all ⇒ fail-closed). |

The keyring-domain authority policy binds from its own `KEYCUSTODIAN_KEYRING_AUTHORITY` section (prefix `KEYCUSTODIAN_KEYRING_AUTHORITY__`), validated fail-loud at startup (`ValidateOnStart`):

| Option | Env var | Required | Notes |
| --- | --- | --- | --- |
| `AllowedKeyringDomainsByWorkload` | `KEYCUSTODIAN_KEYRING_AUTHORITY__ALLOWEDKEYRINGDOMAINSBYWORKLOAD__<WORKLOAD>__<i>` | No (empty = deny-all) | Per-caller allowed payload keyring domains. Key = a bare lowercase caller id — a cross-process SPIFFE workload id (e.g. `audit`) OR an in-process module id (e.g. `edge`), both sharing the bare `[a-z0-9-]` grammar; value = the payload key domains that caller may fetch a keyring for. **Only payload (`AesPayload`) domains are grantable — the host refuses to boot if any non-payload domain (`jwks-signing` / `cookie` / `client-secret` / `mtls-ca-*`) is granted to any caller (fail-loud), because a keyring is a full encrypt+decrypt capability.** Empty-string keys and non-catalog domain values also fail at startup. An empty policy is valid (every lookup returns the empty set ⇒ deny-all ⇒ fail-closed). |

**Host prerequisite — workload identity.** The host must also supply its own workload identity: bind `D2WorkloadIdentityOptions.ServiceId` (the module's establishment-boundary registration owns the bind). `AddD2KeyCustodian` does not re-bind it — it registers a fail-loud presence gate, so an unset `ServiceId` fails `ValidateOnStart` at host start rather than booting anonymously. The gate exists because the CA-seeding and key-rotation System workers establish their `RequestOrigin.System` request context from that self-id; seeding + rotating under an empty self-id would fail late and message-stripped. Bind it before / alongside `AddD2KeyCustodian`.

### Run locally

KeyCustodian runs as part of Edge via Docker Compose. Start the full stack with `docker compose up edge` from `infra/compose/`.

### Health check / debugging

The Infra layer registers a readiness health check (`keycustodian`) reporting whether each configured domain has an active key — Healthy when all do, Degraded during the first-boot soak window, Unhealthy when the database is unreachable or the root key cannot load. The `GetRotationPlan` query handler inspects the lifecycle actions due across all domains. See [`infra/README.md`](infra/README.md) for the composition + configuration details and [`app/README.md`](app/README.md) for handler details.
